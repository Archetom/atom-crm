# Architecture

The generated project uses Domain-Driven Design with explicit ports and adapters. Business rules stay in `domain`; HTTP, persistence, cache, and authentication remain at the boundaries.

## Dependency rule

Dependencies point inward:

```text
infra/rest ───────┬──────────────────────────────> domain policy vocabulary
                  │
infra/facade ─────┼──> application ──> domain
infra/persistence ┘          │
                             └──> api and shared

infra/external ─────────────────────> application output ports
infra/security ─────────────────────> domain security ports
start ──────────────────────────────> all runtime adapters
```

- `domain` does not depend on `api`, `application`, `shared`, or `infra`.
- `application` contains use-case orchestration, not servlet, MyBatis, Redis, or vendor code.
- Infrastructure modules implement inward-facing ports.
- `start` is the composition root and contains no business rules.
- `shared` contains small technical primitives, not domain concepts.

## Modules

| Module | Owns | Must not own |
| --- | --- | --- |
| `api` | Public contracts and explicit authenticated subject contexts | Domain behavior, persistence models |
| `domain` | Aggregates, value objects, policies, domain services, events, repository ports | Spring MVC, SQL, Redis, API DTOs |
| `application` | Use cases, authorization, transactions, output ports | HTTP parsing, mapper XML, vendor clients |
| `shared` | Boundary result and error primitives | User or tenant behavior |
| `infra/rest` | HTTP transport, authentication, status mapping | Business decisions |
| `infra/persistence` | PO mapping, MyBatis, Flyway, cache adapters | Caller discovery, use-case orchestration |
| `infra/external` | Third-party output-port adapters | Application workflow |
| `infra/security` | Password hashing and other security adapters | Domain policy |
| `infra/facade` | Facade implementation and API/application mapping | Persistence |
| `start` | Runtime assembly and end-to-end tests | Reusable business logic |

## Human request flow

```text
HTTP request
  -> Spring Security verifies or rejects identity
  -> AuthenticatedCallerMapper creates AuthenticatedCaller
  -> a facade maps the public contract
  -> a use-case service selects CommandServiceTemplate or QueryServiceTemplate
  -> application checks authority and derives TenantId
  -> aggregate or domain service enforces business rules
  -> tenant-scoped repository queries or persists
  -> facade maps the result to an API response
  -> REST maps stable errors to HTTP status codes
```

`AuthenticatedCaller` is an explicit input. Identity and tenant ownership are not read from a domain `ThreadLocal`.

## Browser password authentication boundary

Browser authentication has one narrow pre-tenant path: `AuthenticationService` uses an exact `(tenantId, username)` user lookup and a `PasswordVerifier` port to validate credentials, then signs a short-lived `PasswordLoginChallenge` through `AuthenticationTokenCodec`. Only after successful verification does it enumerate the user's active tenant memberships. A second command verifies that signed challenge and selected current membership, then issues a signed `BrowserSession`; `infra/rest` alone places the token in an HttpOnly cookie and restores an `ActorPrincipal` on later requests. The application revalidates the user aggregate version, user state, and selected membership before accepting each session, so password changes and status changes invalidate existing cookies without an identity cache.

Password-reset issue/consume is an application command boundary backed by `PasswordResetTokenStore`: plaintext tokens exist only long enough to compose post-commit delivery and the persistence adapter stores a purpose-separated digest, expiry, and consumed state under a row lock. The optional SMTP adapter is an output port, not an application dependency; missing configuration fails closed with a stable delivery-unavailable error. REST owns same-origin double-submit CSRF checks for cookie-authenticated unsafe methods. Domain entities never receive browser cookies, raw passwords, reset tokens, email URLs, servlet requests, or SMTP configuration.

Fresh-system installation has a dedicated public pre-tenant boundary. `SystemInstallationService` first exposes and rechecks a read-only installation marker, then uses one MySQL singleton-row claim in the same transaction as initial-user creation. The winner creates only tenant 1 and its owner identity through the ordinary user, organization and default-provisioning rules before a browser session is issued after commit; a concurrent or later request receives a stable conflict and cannot create another tenant or account. A completed installation means an active login user with an active `TENANT_OWNER` membership, not merely a historical tenant, membership or role row; Flyway repairs older marker rows that lack that usable administrator. Requests never supply a tenant ID, authority, role or initial password hash.

## Contract list summary boundary

`POST /api/v1/contracts/summary` shares the exact validated `ContractQuery` construction used by the contract list and returns a server-calculated count, contract total, received amount, and outstanding amount. The application resolves both the contract and receivable read scopes from the verified caller, and requires unmasked access to both monetary fields before delegating to the tenant-scoped contract repository. The repository applies the contract predicate to the contract amounts and independently applies the resolved receivable visibility predicate to its correlated received-amount aggregate; browser-provided identifiers or cached totals never participate in either scope decision.

## Finance-list atomic batch command boundary

`PUT /api/v1/receivables/batch/owner` and `POST /api/v1/receivables/batch/delete` accept at most 100 unique observed targets, sort IDs to keep a consistent locking order, and lock/validate every visible target before changing any one. Invoice owner transfer, issue-result reset and delete follow the same boundary through `PUT /api/v1/invoices/batch/owner`, `PUT /batch/reset`, and `POST /batch/delete`; reset requires every invoice to remain `ISSUED`, delete requires every invoice to remain `PENDING`. Each command re-resolves its independent authority scope, validates every optimistic version, and checks applicable field policy and active-member assignment before one save, attachment withdrawal, or file-field withdrawal occurs. A stale, missing, out-of-scope, invalid-state or field-policy target rolls back the complete command.

Lead and Contact lists use the same 1–100 target atomic boundary through `PUT /api/v1/leads/batch/owner`, `POST /api/v1/leads/batch/delete`, `PUT /api/v1/contacts/batch/owner`, and `POST /api/v1/contacts/batch/delete`. They acquire the matching customization guard, sort and lock every requested aggregate, re-resolve record visibility and owner scope, then preflight every optimistic version and active-child constraint before changing an owner or withdrawing attachments and governed file fields. A single stale, hidden, invalid, or unauthorized target leaves every selected lead or contact unchanged.

Opportunity lists use the same owner-scope, 1–100 target boundary through `PUT /api/v1/opportunities/batch/owner` and `POST /api/v1/opportunities/batch/delete`. The command takes every target row lock in numeric order, validates the complete optimistic-version set before updating one owner or withdrawing one attachment/file field, and rechecks the active replacement member, assignment scope, and owner field policy. A stale, hidden, invalid, or unauthorized target rolls back the entire selection.

Contract team operations use the matching bounded boundary through `PUT /api/v1/contracts/batch/collaborators` and `DELETE /api/v1/contracts/batch/collaborators`. The add command upserts only the named active collaborators with `READ`/`WRITE` and nullable inclusive `effectiveUntil`, while preserving every unrelated collaborator on each contract; the remove command never permits an owner to be named and is a no-op where that collaborator is absent. A null deadline is unlimited; an expired deadline is excluded from every collaborator read/write visibility predicate. Both routes sort and lock every target, validate every observed version, owner-scope visibility, active member, and non-past deadline before one root is saved, and keep all selected contracts in the same command transaction.

`POST /api/v1/receivables/summary` shares the exact validated `ReceivableQuery` construction used by the receivable list and returns only its count and total amount. The application resolves the verified caller's `receivables:read` visibility, fields, saved view and relation checks before it requires unmasked RECEIVABLE `amount` access. The repository uses the same tenant/data-scope, keyword, owner, relation and typed-condition predicate for both pagination and aggregation; page and sort inputs cannot alter totals, while browser-provided identifiers and cached client money never influence scope.

## Receivable-plan list summary boundary

`POST /api/v1/receivable-plans/summary` shares the exact validated `ReceivablePlanQuery` construction used by the plan list and returns its count, planned amount, receipt amount and remaining amount. The application first resolves the caller's plan visibility and unmasked RECEIVABLE_PLAN `planned_amount`, then separately resolves `receivables:read` and unmasked RECEIVABLE `amount`. The repository applies the plan predicate to the outer plan aggregate and a fixed correlated receipt aggregate to the independently resolved receipt visibility; it never treats a plan's materialized progress, a browser list row or a client money cache as evidence of a caller-visible receipt.

`POST /api/v1/receivable-plans/export/csv` is an aggregate-specific synchronous projection. The application resolves independent `receivable-plans:read` and owner-derived `receivable-plans:export` access, verifies both refer to the same active tenant member, then asks the repository to append the export scope to the already validated list predicate. The resulting SQL therefore intersects—not substitutes—read and export visibility before a stable due-date/installment/id order and a fixed 5,001-row probe. Field codes are closed to the RECEIVABLE_PLAN catalog and must remain readable and unmasked; CSV cells derive only from the already policy-filtered plan projection. A shared non-queueing admission slot, 5,000-row/16-MiB encoder limit, RFC 4180 escaping and formula protection bound the request before the REST adapter supplies fixed no-store attachment headers. No CSV artifact, job, file relation or caller-provided SQL/filename crosses the architecture boundary.

The plan list and summary accept either an explicitly authorized `ownerActorId` or `subordinateOwnerOnly`, never both. The latter resolves a server-owned membership set from the verified caller's current department subtree and resolved plan scope; an empty set becomes a false predicate. That predicate is shared by pagination and every plan aggregate, so neither a query parameter nor an amount summary can widen the caller's actor scope.

The same plan predicate can include either one member-owned RECEIVABLE_PLAN saved view or up to 50 temporary typed conditions, never both. The application rechecks active searchable field metadata, current unmasked access, operator/value compatibility, and visible customer or contract relation targets before persistence receives a fixed column or custom-field condition. The repository applies that predicate to pagination and the correlated-receipt money aggregate together; no browser row, field code, relation identifier, or cached total can affect authorization or aggregation outside that validated path.

## Normalized connector ingress flow

B22a implements the identity and control-plane foundation for a second, non-human application entry path; later B22 batches will add normalized adapter facts:

```text
provider/PBX input
  -> private adapter verifies the original provider transport
  -> connector-specific core credential authenticates the adapter-to-core hop
  -> ConnectorPrincipal carries authenticator-issued AuthenticatedConnector evidence
  -> ConnectorGuard verifies the evidence and resolves the current active opaque registration
  -> application derives TenantId and internal connector identity
  -> tenant/connector-scoped inbox and interaction rules execute
```

`AuthenticatedConnector` is not a subtype or synthetic instance of `AuthenticatedCaller`. Its only identity value is `connectorRef`; an opaque same-authenticator evidence object prevents a direct in-process constructor call from becoming an authenticated subject. It contains no tenant, actor, member, role, authority, provider account, or connection generation. The globally unique opaque `connectorRef` is established only by connector authentication; core registration maps it to exactly one immutable tenant binding. Normalized fact bodies cannot select or override either value.

The authentication/identity layer has two narrowly separated pre-tenant lookups: credential verification uses exact `(connectorRef, keyId)` lookup and the application guard uses exact `connectorRef` lookup. Each returns its own minimal single-row projection and cannot list, prefix-search, or expose provider configuration; either lookup's infrastructure failure has an explicit retryable `503` boundary. Once resolved, every repository and cache call remains explicitly tenant scoped; future ingress writes must also lock and recheck the tenant-scoped registration inside an active transaction so concurrent disable/retire has a total order with fact acceptance. B22a exposes a body-free probe through this path and implements the reusable lock contract; it does not yet accept call facts or create an inbox/interaction. Full rationale, lifecycle, failure semantics, and acceptance evidence are in [B22 section 12](../batch-B22.md#12-integration-principal-与-connector-tenant-解析设计闭合) and [B22a acceptance](acceptance/B22a.md).

B22b adds a separate, disposable real-PBX transport harness rather than composing a provider adapter into the CRM process. It obtains an ephemeral ARI password only at run time, keeps Asterisk and two SIPp endpoints inside an isolated Docker network, binds ARI HTTP only to loopback, opens a real ARI WebSocket, originates both endpoints, and proves their two `StasisStart`/bridge-entry events and actual common mixing-bridge membership before writing a value-free mode-`0600` manifest. This proves only `CONTRACT_CLOSED`: a bridge is not B22-S bidirectional-media proof, and channel IDs, PBX route metadata, SIP endpoints, and the harness body cannot select a connector or tenant. The result cannot assert durable application semantics. Until a private adapter supplies a fenced Stasis stream owner, tenant/connector-partitioned journal and ledger, exact two-leg media proof, `AMBIGUOUS` reconciliation, sensitivity/media retention, and the CP/PC/PD/PM oracle against durable state, its result remains `PBX_REAL=BLOCKED_RUNTIME_CONFORMANCE`. `LINE_REAL=BLOCKED_EXTERNAL` remains separate until an authorized external trunk/account can be exercised. See [B22b acceptance](acceptance/B22b-asterisk-transport-canary.md).

B22c begins the core runtime without accepting provider input: V82 holds only tenant/connector-bound opaque identities, binary digests, fixed state and lease metadata for interaction/request binding/start outbox/fact inbox/observation gap. Composite foreign keys force each reliability record back to an immutable connector registration, while request and interaction references remain tenant scoped. `CallFactInboxService` receives only a verified `AuthenticatedConnector` and two exact 32-byte opaque values; `ConnectorGuard` resolves identity before the command transaction and locks the exact active registration inside it before the transaction-required repository write. MySQL `(tenant, connector, deliveryRef)` uniqueness settles cross-replica replay as apply, duplicate, or safe conflict. The schema deliberately has no party-address, raw frame, recording, provider-error or credential field. This focused MySQL lane is `DURABLE_SIMULATED`, not a B22 readiness signal: command delivery, provider ingress, adapter journal/fence, encrypted payload and media behavior remain unavailable until their transactions and private-adapter conformance are implemented. See [B22c acceptance](acceptance/B22c-runtime-reliability-foundation.md).

B22d supplies the private-adapter CP/PC/PD/PM durable oracle without widening the production surface. Its test-only persistence reconstructs connector-partitioned state across a fenced reconnect, journal and distinct-leg proof; turns a previously dispatched ledger entry into `AMBIGUOUS` without a second start; encrypts only synthetic sensitive material with connector-separated AES-GCM/HMAC and deadline deletion; and verifies full/single-range/cancel/confirmed-absence media behavior. The runner emits only fixed check names and a source digest at `DURABLE_SIMULATED`. It is not an ARI/Stasis implementation, PBX media proof, PBX sink audit, or recording storage integration, so it cannot change `PBX_REAL=BLOCKED_RUNTIME_CONFORMANCE`, `LINE_REAL=BLOCKED_EXTERNAL`, B22-SPLIT, or production readiness. See [B22d acceptance](acceptance/B22d-private-adapter-durable-oracle.md).

`b22-conformance-matrix.sh` composes only the owner-only B22b, B22c and B22d reports after checking their fixed profiles and evidence fields. Its digest-bound, value-free matrix preserves every layer separately and fixes `productionReady=false`, `PBX_REAL=BLOCKED_RUNTIME_CONFORMANCE` and `LINE_REAL=BLOCKED_EXTERNAL`; report aggregation is not an adapter, not a readiness snapshot, and cannot elevate a synthetic SIP transport or private test oracle. See [B22e acceptance](acceptance/B22e-evidence-matrix.md).

B22 reliability deliberately composes local guarantees instead of claiming end-to-end exactly-once dialing. A caller-scoped request binding, interaction, and typed start outbox commit together; the core may redeliver only the same `commandId`, and the private adapter must durably ledger that command before provider I/O. Provider uncertainty becomes `AMBIGUOUS` and permits reconciliation, never automatic redial. Verified provider facts first enter an adapter-owned durable journal, then a tenant/connector-scoped core inbox whose result and monotonic projection commit in one short transaction. Provider-to-adapter gaps, reconciliation cases, session correlation, leases, fencing, capacity, retention, and crash tests are frozen in the [B22-R reliability design](B22-R-reliability.md). This remains a later runtime contract; B22a implements connector identity and control only, not call delivery or reliability storage.

## Planned call-sensitive-data boundary

B22-D freezes a second planned boundary around dial targets, inbound party addresses, and recording references. A human originate request selects a currently visible CUSTOMER, CONTACT, or LEAD field; it never supplies a number or connector. The command transaction rechecks active membership, record scope, and current unmasked field access, conservatively normalizes the authoritative value to E.164, and atomically saves an encrypted immutable snapshot with the interaction/outbox. Subsequent CRM edits cannot rewrite that snapshot, and the ordinary outbox, domain event, API, log, trace, metric, and Activity paths never carry the plaintext.

Present inbound numbers use tenant- and purpose-separated authenticated encryption plus a full HMAC-SHA-256 equality token. Tokens support only bounded exact candidate lookup and are never exposed. A connector ingress cannot resolve candidates or synthesize a caller; any suggestion or association runs later under an explicit `AuthenticatedCaller`, reloads the current CRM value, and reapplies owning-domain visibility and `READ` plus unmasked field access. Ordinary call output exposes at most one fixed last-four display and never reveals a historical complete number.

An external recording reference is itself encrypted connector-scoped sensitive data, not a provider URL or media credential. Recording bytes and transcripts stay outside the core. Media access intersects active membership, call participation/management, current linked-record visibility, a separate recording capability, the snapshotted tenant policy, expiry, availability, and adapter read/delete capabilities. B22-M chooses a same-origin server-controlled proxy stream whose every full or byte-range request repeats those checks; long media I/O occurs outside the authorization transaction, and provider redirects and URLs remain forbidden.

Production call enablement requires an explicit key provider, deployment retention ceilings, and a versioned tenant policy. Expiry stops access first, then a durable adapter deletion command removes media; only confirmed deletion becomes `REMOVED`. Address ciphertext/HMAC, recording references, masks, audits, and operational tombstones each have separate deadlines, and backup restores run the retention sweep before serving. Full data classification, AEAD/HMAC/key rotation rules, access matrix, failure semantics, and tests are frozen in [B22 section 14](../batch-B22.md#14-b22-d-敏感数据录音访问与保留设计闭合). This is a design contract; no B22 storage, key, or media adapter is implemented yet.
## Call interaction state boundary

B22-S plans `CallInteraction` as the tenant/connector-scoped aggregate root and admits exactly two normalized participant legs in its first topology: one `AGENT` and one `REMOTE_PARTY`. These legs are not a mirror of every provider Call, PBX channel, bridge, or endpoint. Native control legs, Local channels, holding bridges, IVR, and device sessions remain in the private adapter's durable session registry; a connector that cannot reduce its native graph to the two stable participant legs cannot advertise first-phase readiness.

First-phase outbound is agent-first: the adapter must make the private agent leg media-ready before it creates or alerts the remote leg. First-phase inbound leaves IVR, queueing, and endpoint selection private, then observes the final agent leg and remote leg. An interaction becomes `CONNECTED` only after both normalized legs are media-ready and an authenticated adapter supplies explicit proof that those exact roles are in the expected bidirectional two-party media relationship. Early media, one answered/up leg, two individually ready but unrelated legs, a holding bridge, or one provider Call's completed status is insufficient.

Lifecycle milestones derive `PREPARING`, `RINGING`, `CONNECTED`, and `TERMINATED` without destructive state replacement. Dispatch confirmation, observation/reconciliation quality, and recording availability are orthogonal state dimensions, so a terminated interaction may still be `OBSERVATION_INCOMPLETE` and a recording callback cannot change call lifecycle. Structurally valid out-of-order facts may wait for bounded prerequisites; contradictory terminal classifications, cross-interaction leg reuse, or an unsupported third normalized leg fail closed rather than using last-write-wins.

CRM members, connector agent bindings, and devices remain separate. The core may govern an immutable connector-scoped opaque external-agent binding to an active tenant member and request a minimal endpoint configuration/presence projection. Extensions, device identifiers, SIP URIs, registrations, tokens, IPs, codecs, and provider errors stay private. Capability or presence never grants a CRM authority, and a caller cannot select a connector, external agent, or device through an ordinary call request. The complete state vocabulary, topologies, connected proof, and contract fixtures are frozen in [B22-S](spikes/B22-state-and-topology.md).

## Call recording media-transfer boundary

B22-M plans at most one public recording object per interaction. Provider segments, tracks, live recordings, recording names, filesystem paths, URLs, temporary credentials, and transcoding artifacts remain private. Recording observation projects only `UNAVAILABLE`, `PROCESSING`, `AVAILABLE`, and `REMOVED`; a call terminal fact never implies media availability, ordinary read failure never proves confirmed deletion, and recording callbacks do not alter call lifecycle.

The first-phase human transport is an authenticated same-origin `GET` through the core. Its target contains only a local recording or interaction identity and no media grant. Every full or seek/resume request rechecks current membership, call and recording capabilities, participation/management, linked-record visibility, policy/deadline, availability, and connector readiness. Full responses use a normalized WAV or MP3 representation; a connector may expose one byte range only when it can prove immutable bytes, stable length, and native range reads. The core never returns a provider redirect, URL, path, credential, header map, external recording reference, or media-specific browser token.

Authorization and the minimal access attempt commit in a short transaction before any external I/O. The private adapter receives a typed, short-lived, non-serializable open command and returns a closeable, cancelable, backpressured byte source rather than a URL, file, buffer, provider response, or SDK type. Provider I/O runs outside database transactions and is bounded by open/idle/stream deadlines, maximum bytes, active-stream admission, client cancellation, and the recording deletion cutoff. Successful responses use `no-store`, same-origin and `nosniff` headers, while acknowledging that an authorized endpoint can still retain or re-record bytes. The complete wire contract, failure semantics and cloud/PBX fixtures are frozen in [B22-M](spikes/B22-media-transfer.md).

## Call adapter readiness and isolation boundary

B22-A separates connector lifecycle, adapter readiness, and member endpoint capability. An active registration is not automatically callable, a ready adapter has no CRM authority, and an available endpoint is only a short-lived hint. The core plans one persisted, provider-neutral readiness projection per connector and private binding revision. It reports fixed operations independently, carries adapter contract/build evidence, a monotonic probe sequence, an exact B22-R start guarantee, reconciliation coverage, and a positive lifetime capped at five minutes. Missing, expired, reordered, incompatible, or under-evidenced snapshots fail closed. New outbound admission, core outbox claim, and the adapter's pre-provider dispatch gate each recheck their own current evidence; no check substitutes for another.

Every provider input is assigned to one logical connector by a governed callback route or fenced stream owner before its body is interpreted. Provider account fields, Stasis arguments, PBX variables, caller IDs, and extensions may only corroborate that binding. The private adapter keeps a durable native-resource ownership registry and connector-partitioned credentials, ledgers, journals, sessions, query state, capacity, quarantine, retention, and observability. One trusted adapter process may serve multiple tenants only when cross-connector negative fixtures prove this isolation. Dedicated provider boundaries, provider-scoped resources, and adapter-enforced trust zones remain distinct evidence levels rather than being mislabeled as equivalent provider authorization.

Configuration or subscription drift invalidates affected operations before new start work is claimed. Observation-path drift conservatively opens a B22-R gap from the last proven-ready point; a later healthy snapshot cannot erase that evidence or redial an ambiguous command. Asterisk connectors require an isolated Stasis app or equivalent route, `subscribeAll=false`, minimal subscriptions, and one fenced owner. FreeSWITCH ESL exposes a broad command surface after authentication, so a shared node can claim only adapter-enforced trust-zone isolation unless a dedicated node or policy-enforcing proxy supplies a stronger boundary. Readiness probes are read-only and must never place a real call, hang up a call, read real media, or delete a recording. B22-M format/range/resource evidence is part of recording readiness. Full operation gates, cloud/PBX profiles, drift semantics, and fixtures are frozen in [B22-A](B22-A-adapter-readiness.md).

B22-CW composes the cloud side of those planned boundaries into one deterministic oracle. Native callbacks stay behind governed route selection, exact signature validation, ownership resolution, and durable adapter journaling; the core sees only normalized deliveries. Seven scenario families cover duplicate/conflicting delivery, out-of-order evidence, callback-before-start-response, the two normalized legs and explicit media proof, late recording availability, cancelable media streaming, and readiness drift with a conservative observation gap. Every checkpoint jointly inspects adapter/core durability, monotonic interaction state, sensitive-value exclusion, resource cancellation, one-time effects, and readiness evidence. The same scenario IDs must run against the model, a durable MySQL/simulator composition, and a real cloud adapter conformance environment. This closes the cloud fixture contract only; PBX composition remains a separate profile. See [B22-CW](B22-CW-cloud-callback-fixture.md).

B22-CP composes the PBX portions of B22-R, B22-S, and B22-A in one deterministic two-connector conformance trace. A dirty stream replacement must durably open a gap before the new generation is ready; the stale fence cannot write the journal, checkpoint, session registry, or native ownership registry. Restarted adapters recover the same external interaction and exactly two normalized legs. Early media, either answered leg alone, two media-ready legs without an exact relationship, bridge creation, holding bridges, and unrelated members all remain non-connected. Only authoritative bidirectional media proof for the exact `AGENT` and `REMOTE_PARTY` pair produces one connected milestone. Wrong-stream and wrong-ownership frames fail before normalized fact construction, while an active-resource snapshot never masquerades as replay. The full trace, crash points, independent store/projection oracle, and bounded conformance report are frozen in [B22-CP](B22-CP-pbx-composed-contract.md).

B22-PC composes the separate PBX start-command path across the core outbox, adapter command ledger, provider effect, governed event stream and durable reconciliation. A core transport retry reuses one command and digest. The adapter commits `DISPATCHING` before provider I/O; after that boundary, `AT_MOST_ONCE_START` never invokes start again, while `IDEMPOTENT_START(window)` may reuse only the exact provider key and digest inside the original window and must still create at most one logical object. An event may confirm dispatch before the command response, but it does not synthesize lifecycle. `AMBIGUOUS` atomically settles the start outbox and creates a read-only case; only capability-bound, post-window, full-coverage authoritative absence may reject it. Active snapshots and ordinary not-found results never trigger redial. The two-connector crash matrix and independent core/adapter/provider oracle are frozen in [B22-PC](B22-PC-pbx-command-contract.md).

B22-PD composes the PBX sensitive-data path across the core number envelope/HMAC, adapter command and ingress payloads, quarantine, PBX-controlled CDR/CEL/log/spool surfaces, key provider, retention workers, and backup restore gate. Ordinary outbox, ledger, journal, session, quarantine metadata, observability and conformance artifacts contain no complete or masked numbers. A governed stream selects the connector before a fixed address field is extracted; all other caller, destination, extension, variable, SIP, command and error data are discarded before ordinary journaling. Optional raw replay data lives only in a separately keyed, bounded encrypted store with an absolute deadline. Key rotation prioritizes expiry over re-encryption, gaps and unresolved reliability state never extend sensitive retention, and old backups are swept before service. Deletion evidence remains split across core, adapter, PBX-controlled surfaces, final key destruction and backup expiry rather than collapsing into a misleading boolean. The complete two-connector oracle is frozen in [B22-PD](B22-PD-pbx-sensitive-data-contract.md); real-provider and implementation fixtures remain open.

B22-PM composes the PBX recording-specific seams that B22-CP and B22-PC deliberately omit. Live recording, interaction termination, recording-finished/stop input and stored-object readiness remain separate checkpoints; only an exact connector-scoped object that is closed, readable, format-valid, stable, immutable for the declared profile and within hard limits becomes `AVAILABLE`. Every full or single-range request repeats human and linked-record authorization before opening a typed stream outside the transaction. Range support requires native exact offset reads; invalid or unsupported ranges never fall back to full reads. Client disconnect, open/idle/stream deadlines, byte limits, retention cutoff and removal all cancel upstream without transparent reopen, while bounded source/member/tenant/connector/process admission preserves a separate deletion control reserve. Expiry, durable delete and authoritative absence confirmation are distinct stages; read failures and delete responses do not create `REMOVED`. The six-scenario crash and isolation oracle is frozen in [B22-PM](B22-PM-pbx-media-contract.md); real-provider canary and implementation fixtures remain open.

## Planned registered-identity boundary

B23-XI separates a registered identifier's uniqueness namespace from the subject's legal jurisdiction and from the provider that observed it. The normalized identity key is `(identityScope, registryScheme, canonicalValue)`: scope selects a governed registry namespace, scheme selects its exact validation/canonicalization rules, and the complete canonical value preserves meaningful prefixes and leading zeros. Legal jurisdiction, names, addresses, entity status, identifier standing, provider/account/connector, source locator and observation metadata never enter the key. Unknown scope/scheme pairs fail closed, and generic NFKC/lowercase normalization cannot be reused for registry identity.

Entity status is only `ACTIVE`, `INACTIVE`, or `UNKNOWN`; identifier standing independently distinguishes `CURRENT`, `STALE`, `TRANSITIONING`, `SUPERSEDED`, `INVALID`, `RETIRED`, and `UNKNOWN`. Neither axis grants CRM authority or mutates Customer lifecycle. A stale, superseded, invalid, retired, inactive or temporarily unavailable external record cannot automatically release, replace, delete, lock or move a Customer association.

The current tenant relationship is Customer one-to-many registered identities, with every exact identity key assigned to at most one non-deleted Customer. `ACTIVE` and `IN_POOL` both retain the claim; Customer soft deletion releases it in the same command transaction while durable adoption provenance remains. A dedicated bounded ASCII/binary relation and MySQL unique key `(tenant, identityScope, registryScheme, canonicalValue)` arbitrate concurrent claims. Pre-checks are advisory only; inserts are ordered by the normalized key, never ignore or overwrite a conflict, and a losing command rolls back Customer values, identity and provenance without revealing the occupying Customer. Different tenants remain independent. Full rationale and the concurrency oracle are frozen in [B23-XI](B23-XI-registered-identity.md); B23a implements only the read kernel and adds no identity relation or schema.

B23a queries run behind `enterprise-data:read` plus an active tenant membership. ## Secure-file inspection boundary

B24-I keeps storage integrity, media-type identification, malicious-content inspection, and publication policy as four independent proofs over one immutable content version. A native scanner `OK`, object tag, filename extension, declared `Content-Type`, or `application/octet-stream` is never itself `CLEAN`. The core emits `CLEAN` only when exact length/integrity identity, an allowlisted identified type, no-threat evidence, fresh readiness/definitions, and every byte/deadline limit agree. Positive threat or deterministic type-policy conflict is `REJECTED`; unknown format, password protection, scanner/container limit, timeout, protocol/schema drift, stale definitions, or object-version mismatch is `INDETERMINATE`. Only `CLEAN` can later participate in `STORED + active link -> AVAILABLE`.

The streamed-engine profile reads quarantine bytes through a typed, cancelable stream and binds each attempt to a fenced engine/catalog generation; paths, URLs, shell commands and provider errors remain private. The object-event managed profile requires an exact versioned object and validates duplicate or out-of-order results against its fixed account/region/binding/schema. It records managed-definition channel evidence rather than fabricating a per-scan signature version, and deployments that require an exact catalog keep that profile `NOT_READY`. Object tags are reconciliation hints, not publication authority.

Prefix/magic detection may consume a bounded prefix. Container-aware detection or parsing runs only in a separate least-privilege process with CPU, memory, pids, temporary bytes, entry/depth/expansion and time limits; parser crashes and partial results fail closed. Quarantine is isolated by storage and process permissions: upload, scanner, publication, cleanup and ordinary-download principals have distinct exact-object capabilities, and neither the web process nor a browser can list or read uninspected bytes. Durable job leases and attempt fences keep all scanner I/O outside MySQL transactions and reject stale workers after crashes. The `I-01..I-14` two-profile oracle is frozen in [B24-I](B24-I-content-inspection.md); B24a implements the bounded-magic plus fenced streamed-engine profile, while managed object-event inspection remains a conformance-only profile.

## Organization membership boundary

`MemberProfile` is global data bound to the verified actor identifier. `OrganizationMembership` and `Department` are tenant-owned aggregates. Tenant-bound organization operations use `OrganizationAccessGuard`, which requires both the route authority and an active membership for the caller's verified tenant before a repository access.

Membership requests may name a `targetTenantId`, but that value is only a review destination. Target validation and the accessible-tenant list return data; they do not change `AuthenticatedCaller`, install a tenant context, or mint a new credential. Department parent lookups always carry the current tenant, and move validation walks the in-tenant ancestor chain to reject cycles.

The applicant-owned membership-request page is a separate `organization:request` query. It derives the applicant only from the verified caller, passes that `MemberId` into the repository, and orders bounded records by creation time; it does not use the caller tenant as an implied target filter or expose a target-tenant directory. Administrator review remains a distinct active-membership plus `organization:write` query scoped to the current target tenant. The applicant can only withdraw an exact request resolved by the same verified applicant.

Every initialized tenant has one `organization_tenant` row. Department creation, moves, deactivation, deletion, membership approval, and target-tenant membership submission acquire that row with `FOR UPDATE` before their first target-tenant database read. This serializes structural changes per tenant, so two opposing moves cannot validate stale paths and form a cycle, and submission cannot retain a stale pre-bootstrap eligibility check. Deactivation rejects active children or memberships; deletion is stricter and rejects every child or member assignment, including inactive records. A generated-column unique key permits at most one `PENDING` membership request for one applicant and target tenant; the application pre-check improves the message but the database is authoritative under concurrency.

Department-member reads first reject a `DELETED` department, then page active profiles with one tenant-and-department-scoped join. This keeps deleted resources invisible and avoids loading an unbounded membership list or issuing one profile read per member.

Region reference data is not part of organization membership or tenant ownership. `RegionReferenceCatalog` is an application output port and `/api/v1/reference/regions` is its independent read contract; the bundled adapter is intentionally empty until a deployment supplies a curated data set.

## Authorization, navigation, and customization boundary

Tenant roles grant only capabilities declared by `AuthorityCatalog`. The tenant-owner role is evaluated dynamically and is not reduced to mutable grant rows. Navigation is derived from the same effective capabilities, then filtered by the current member's bounded preference; hiding an item never grants or revokes a capability.

The customization engine uses stable `BusinessObjectType` and `CustomFieldType` enums. `FieldDefinition` owns metadata only; values for customers, contracts, and later business aggregates remain in their owning modules. Field codes, types, and uniqueness are immutable after creation, select-option values cannot be removed, and deactivation preserves metadata for future value interpretation. Deactivation is rejected while a layout or saved view references the field; disabling search is rejected while a saved view references it.

`customization_object_guard` supplies one database serialization row per `(tenant, objectType)`. Field-definition commands, layout writes, and saved-view writes acquire its exclusive record lock with one `INSERT ... ON DUPLICATE KEY UPDATE` statement before reading the field catalog or dependency state. The atomic upsert creates a missing guard or directly locks an existing one without a shared-lock-to-exclusive-lock upgrade. This makes the lifecycle dependency check and every operation that can create such a dependency one serial history: a writer that follows a lifecycle change must re-read the committed catalog and reject inactive or non-searchable fields instead of persisting a newly stale configuration.

Field access is a second, restrictive layer after use-case authorization. A tenant owner dynamically receives `WRITE` for every active field. Other active roles contribute only explicit access entries, missing entries resolve to `HIDDEN`, inactive memberships resolve entirely to `HIDDEN`, and multiple roles merge to the most permissive explicit access. This policy cannot create an HTTP or application authority. Business modules consume `EffectiveFieldAccessResolver` before exposing or accepting field values.

Keyword search is field-policy aware. Each object's field catalog exposes a fixed `searchCandidates` map; the application intersects it with the current active/searchable definitions and effective access, excluding every hidden or masked field. `SearchKeyword` supplies shared Unicode-safe bounds and blank semantics, while persistence adapters translate only the selected fixed candidates through `SqlLikePattern`. An empty candidate intersection becomes an explicit false predicate. The resulting OR group is always nested inside the repository's existing verified-tenant, data-scope, active/non-deleted predicate; ordinary customer and contact queries also retain their public-pool exclusion. Product and contract identifiers are compared through their normalized keys, while a receivable-plan keyword is parsed as an exact positive installment and invalid text becomes a false predicate. No request can provide a column or SQL expression.

Field layouts and saved views are scoped by tenant, verified member, and object type. Layouts reference only active fields and have bounded ordering, pinning, hiding, and widths. Layout reads intersect stored preferences with the current active catalog. Saved views store typed `fieldCode`, operator, bounded values, and an explicit per-condition browser-exposure flag validated against active searchable metadata; list and default-selection reads revalidate the filtering metadata and fail closed for stale conditions. Aggregate query adapters receive only the derived typed filter conditions, never the browser-exposure flag, and normalize saved values against the current field type before SQL translation, so database coercion cannot reinterpret malformed numeric, temporal, boolean, identifier, or choice input. They never store SQL, scripts, table names, or arbitrary query expressions. Each member has at most one default view per object.

Contract, invoice, receivable, and return-visit queries accept either a member-owned saved view or one bounded set of temporary typed conditions. The application rejects requests that combine both modes, revalidates field access and cross-aggregate relation targets for either source, and passes only fixed catalog columns and parameterized custom-value predicates to persistence before the existing tenant and data-scope predicates.

Embedded pages are tenant-managed client links, not server-side integrations. The domain accepts only HTTPS templates without user information or unknown placeholders, substitutes only `{recordId}`, and never performs a network request. Only active pages are rendered to ordinary readers; management writes remain versioned and require explicit capabilities.

## Customer aggregate boundary

`Customer` is the first business aggregate that consumes both authorization data scopes and customization metadata. It owns core details, deal and lock state, tags, addresses, collaborators, one optional parent, and typed custom-field values. A repository save updates the root with its optimistic-lock version and replaces the bounded child collections in the same command transaction. Reconstitution restores the named snapshot without events, and soft deletion uses only `CustomerStatus.DELETED`.

The four customer capabilities (`customers:read`, `customers:write`, `customers:delete`, and `customers:assign`) each resolve their own data scope. SQL predicates combine owner department visibility with explicit collaboration: `SELF` includes owned and collaborated records, department scopes expand through the active owner's membership, and `TENANT` remains tenant bounded. A `READ` collaborator never gains write access; delete and assignment use owner-scope visibility rather than collaboration. Cross-tenant misses and out-of-scope records have the same not-found result.

Field policy is applied after record visibility. Built-in and custom fields require explicit effective access for non-owner roles, masking occurs at the application output boundary, and only unmasked readable fields may drive saved-view, duplicate, name, owner, nearby, or tag predicates. A masked `deal_status`, `created_time`, or `updated_time` suppresses its exact time value. Customer repositories translate validated saved-view conditions into a fixed built-in column catalog or parameterized custom-value subqueries. No API accepts SQL, a column identifier, or an arbitrary expression. Persisted canonical strings are checked against their final representation: URL bounds apply after ASCII conversion, while NFKC-normalized unique reservation diagnostics use a non-indexed text column and uniqueness remains anchored by the SHA-256 key. ## Customer-pool boundary

`CustomerPool` is a versioned tenant aggregate. Its administrator, eligible-member, eligible-department, and automatic-release-rule collections are bounded typed relations. Claim history is append-only and supplies the daily limit boundary without relying on Redis.

Catalog visibility is resolved by tenant-scoped database predicates for administrators, eligible members, and eligible departments before results are returned; a persisted tenant-owner decision switches that query to all active pools. Pool customer mapping resolves parent IDs only through membership in the same accessible pool.

The same transaction changes the customer to `IN_POOL`, clears ownership/collaboration, saves the aggregate by version, and inserts membership. Claim and assignment take the guard, pool lock, and membership lock in a fixed order, validate active tenant membership and pool access, restore one owner, remove membership, and append history. Pool queries hydrate customers through tenant-scoped membership predicates and then apply the same CUSTOMER field policy, masks, and typed saved-view validation as ordinary customer queries. Automatic release is a bounded, repeatable application coordinator. Its human diagnostic entry point still receives a real `AuthenticatedCaller`; B26a's system entry receives only the claimed tenant, fixed evaluation time and fence verification callback. A tenant-scoped database row stores the last scanned pool ID. Each invocation resumes after that cursor, wraps once, scans pages of at most 25 pools, and locks at most 50 distinct pools before persisting the new cursor in the same transaction. This prevents a busy low-ID pool from starving later pools across invocations and bounds the duration of the CUSTOMER customization guard. Active configuration is rechecked under the same database locks as manual release.

## Scheduling and automation boundary

B26a provides one composition-root wake-up surface with two deliberately different durability lanes. Scheduled automations use an application-owned closed kind catalog plus MySQL schedule/run rows; existing durable workers such as B24 register only a bounded pump and retain their own job identity, lease, deadline, effect evidence, readiness and recovery protocol. The common scheduler controls wake-up frequency, local lane isolation and shutdown, but it cannot interpret a file job, copy it into a generic run, or make a non-ready adapter ready.

The first B26a scheduled kinds are Customer and Contact pool automatic release. A run's tenant comes only from an exact claimed row that is foreign-keyed to its durable schedule and `organization_tenant`; `AutomationExecutionContext` contains no actor, authority, human caller, connector principal or arbitrary payload. After claim, every business operation is explicitly tenant scoped. A pool write that can alter automatic release takes the owning object guard, then the derived schedule, then the pool root in one transaction; background execution consumes current active configuration without impersonating an administrator.

Due materialization and lease transitions use shared MySQL UTC. One short transaction preserves the schedule's due time, freezes a stable evaluation time, creates one unique occurrence and advances the next due; long downtime coalesces to one current occurrence rather than replaying every missed interval. Claim writes a boot-scoped owner and increasing fence. The owning object guard, schedule, exact run, existing pool cursor, pool roots and customer/contact roots are then locked in that order inside one `CommandServiceTemplate` transaction, so the business effect and run terminal state commit together. Retry reuses the same run and evaluation time; business timestamps use actual database commit time. These guarantees cover local MySQL effects only and do not claim exactly-once external delivery.

No public automation API, caller-defined cron/timezone, script, condition tree, Work recurrence, notification, timed announcement or provider job is part of B26a. `V65` provides the schedule/run schema and active-slot constraint; `V66` adds one global monotonic cadence-revision control row. Startup reconciliation holds that row, upgrades drifted schedules by generation, cancels their stale active runs and prevents an older mixed-version replica from claiming or rolling the control plane backward. Health is `NOT_READY` until the enabled revision is reconciled. Invalid scheduling configuration still fails only the automation lane closed, while terminal history is physically retained in bounded batches. The remaining multi-replica crash and B24 adapter conformance gates are documented in the [B26 plan](../batch-B26.md).

## Work recurrence and reliable-notification boundary

B27a implements a Work-owned `WorkTaskSeries` rather than adding cron or rule payloads to B26. A claimed run supplies tenant and stable evaluation time; every effect locks tenant, recurrence control, schedule/run and series in that order, then either creates one ordinary `WorkTask` plus an immutable recurrence origin or advances the series as a bounded skip. Long downtime coalesces, and a generated-open database slot limits each series to one TODO/IN_PROGRESS generated task. A higher revision can replace an interrupted target from its first batch, while unknown rule or zone data aborts the batch rather than ending a series. Editing, pausing or deleting a series affects only future occurrences and never rewrites an existing task. Creator or assignee authorization is re-resolved from current tenant grants without synthesizing a caller; a revoked requirement pauses the series, while invalid followers are omitted from only the new task snapshot. B27b adds task-local reminder steps and current-member in-app notifications; it does not add an automation kind, cron rule, external payload, or synthesized caller.

Task reminders are a second durable boundary. A task or series template can define at most eight BEFORE_DUE/AT_DUE/OVERDUE steps addressed only to the current assignee, creator or followers. A dedicated notification projection version changes with title, priority, assignee, followers, due time, task state or reminder policy. The in-app `Notification` is a tenant/member fact with its own idempotent read time. Worklist acknowledgement, notification read, task completion and delivery state remain independent.

External notification delivery uses B27c's typed transactional outbox and its own bounded pump, not an after-commit event or a B26 automation run. Readiness is preflighted before claiming a delivery and rechecked under admission locks with current membership, `notifications:read`, task visibility, member preference and a server-resolved profile endpoint before external I/O; `UNSUPPORTED` or a transient readiness gap leaves the row claimable for a later current adapter. First dispatch freezes the guarantee, original idempotency window, and a tenant/purpose-domain-separated HMAC endpoint binding plus key version; an endpoint or binding-key change turns a historic attempt `AMBIGUOUS` rather than reusing its key for a different command. Persisted effect certainty is conservative: `IDEMPOTENT_SEND(window)` may retry only the exact frozen command in its original window, and ambiguity survives retry exhaustion, deadline expiry, stale-task handling and admission recovery. `AT_MOST_ONCE_SEND` turns an uncertain post-dispatch result into `AMBIGUOUS` and does not redeliver automatically. The adapter receives only the remaining `min(lease, deadline)` budget after a settlement reserve and must respond to cancellation; a lost settlement is a lane failure. Delivery deadline/retention maintenance remains active when provider dispatch is disabled, while invalid or disabled deployments create no new EMAIL rows and terminal delivery retention is clamped to the notification-content retention ceiling. `ACCEPTED` means only provider acceptance, never mailbox arrival or human read. Production EMAIL remains disabled without current adapter evidence, and the sample `UserNotificationPort` logging path is explicitly outside this guarantee. `Product` is a versioned tenant-shared catalog aggregate with an active member owner, optional category, NFKC/lowercase code key, availability, price, and typed PRODUCT custom values. `products:read`, `:write`, `:delete`, and `:assign` require active membership but deliberately do not support record data scopes; the owner is responsibility metadata, not a visibility grant. Product writes acquire the PRODUCT customization guard before reading field definitions, then the catalog guard before saving. MySQL finally arbitrates active code and unique custom-field reservations, while reads apply current field access and masking after catalog visibility.

Product list ordering is either a closed static field enum or one active, non-built-in scalar PRODUCT field resolved by the application from `customSortFieldCode`. The two input modes are mutually exclusive. Before persistence, the application requires current readable, unmasked field access and converts custom metadata to only its definition ID and scalar type; the repository uses that trusted ID in a parameterized correlated value subquery, casting canonical INTEGER and DECIMAL values numerically. No request field code, column name, or expression can become SQL.

`OpportunityProductLine` is owned by the opportunity aggregate and contains a product snapshot, not a live product reference for display. Replacement locks the opportunity through its normal optimistic save path, requires unmasked write access to the OPPORTUNITY `products` relation, and requires unmasked PRODUCT reads for name, code, category, unit, and list price before exposing or freezing them. It acquires the product catalog guard before the transaction's first consistent read, then locks requested tenant products in numeric order, so product and category data cannot come from different repeatable-read snapshots. Every target must remain active and available. The request supplies a positive quantity and optional unit price; discount and line amount are calculated by the domain with fixed scales. At most 100 distinct product lines are stored, and later category/product edits, withdrawal, or soft deletion cannot rewrite their name, code, category, unit, list-price, sale-price, or amount history.

## Contract and invoice boundary

`Contract` is a versioned tenant-owned aggregate with independent read, write, delete, and assignment data scopes. Owner creation and replacement validate the target membership against the resolved assignment scope. Its customer is required; optional opportunity and contact relationships are independently visibility-checked and must belong to that customer, with tenant/relation/customer composite foreign keys preventing later relation moves from breaking the invariant. Every query and mutation response rechecks those relationship predicates and PRODUCT snapshot field access. The normal contract projection can hide collaborator information, so it is never a replacement baseline: the dedicated `GET /contracts/{id}/collaborators` requires `contracts:assign` with owner scope and returns the unmasked aggregate version, every persisted collaborator's actor ID, access level, nullable inclusive `effectiveUntil`, plus the caller's `OWNER`/`READ`/`WRITE`/`NONE` relationship state. A null expiry is unlimited; expired entries remain manageable in that baseline but are omitted from collaborator-derived query and mutation visibility. Product rows are aggregate-owned immutable snapshots built from locked available products after PRODUCT field-policy checks. The dedicated `GET`/`PUT /contracts/{id}/products` boundary is the complete product-relation baseline: both recheck readable unmasked contract/product snapshot fields, the replacement also requires `contracts:write`, locks the contract and catalog, recalculates totals from server-owned prices and quantities, and cannot lower the total beneath committed invoices, receipts, or active plans. Its narrow response includes only line identity/display snapshot, quantity, unit price, and version; it never exposes derived discounts or contract totals. Versioned `PATCH` requests, and the equivalent `PUT` requests, merge only submitted non-`null` fields; omitted and `null` values preserve stored data, so masked output cannot clear a relationship, sensitive attribute, or immutable-history field. Requests cannot provide catalog display values, discounts, subtotals, totals, tenant, or audit identity. Contract number uniqueness uses an NFKC/lowercase tenant key, both normalized length and every line/aggregate `DECIMAL(22,2)` amount are validated before persistence, and all dates are limited to MySQL's `1000-01-01` through `9999-12-31` range.

Contract batch owner transfer and batch delete are separate commands, not browser-side loops over single-record endpoints. Each accepts 1–100 unique `{contractId, version}` targets, resolves the caller's current assignment or deletion scope, locks the normalized ID order, and version-checks the complete target set before changing any row. Owner transfer also requires `owner_actor` write access and an active member within that scope. Batch delete preflights every invoice, receipt, and receivable-plan dependency before deleting a root or withdrawing attachments, so any stale target, scope denial, invalid owner, or dependency failure rolls the complete command back. Selected contract CSV export is a separate, non-mutating boundary: it intersects current `contracts:read` and `contracts:export` visibility, rejects unavailable or stale selected rows, derives a fixed field-policy-filtered column set server-side, formula-guards text cells, and returns one bounded, one-shot, `no-store` stream without relationships or custom fields.

`Invoice` is a versioned invoice-application aggregate with its own read, write, delete, assignment, and issue capabilities. Creation derives customer identity from a visible active contract while holding the contract row lock, but every response still suppresses that customer ID unless the caller independently retains `customers:read` visibility. Amount replacement locks that same contract before the invoice root and sums all other non-deleted invoice applications. Contract detail replacement also locks the root before checking the committed sum, rejects a customer change once any historical invoice exists, and rejects a total below that sum; deletion is rejected while a non-deleted invoice remains. The database repeats the customer invariant with a tenant/contract/customer composite foreign key. Requested and issued dates use the same MySQL-safe range as contracts. These rules serialize invoice creation, invoice amount changes, and contract reductions instead of relying on a preflight-only check.

Contract and invoice list ordering is either a closed static field enum or one active, non-built-in scalar CONTRACT or INVOICE field resolved by the application from `customSortFieldCode`; the two modes are mutually exclusive. The application requires current readable, unmasked access, then passes only the resolved definition ID, scalar type, and direction to the repository. Each repository owns its parameterized correlated custom-value expression and casts canonical INTEGER and DECIMAL values numerically, so request field code, column name, and expression cannot become SQL.

`InvoiceProfile` belongs to a customer but never grants customer visibility. Every list, create, update, and delete re-resolves `customers:read` for the target customer inside the actual read or write transaction; list and create do so before querying or inserting profiles, while update and delete do so after the tenant-scoped lookup and before mutation. Every repository operation requires an explicit tenant, and soft deletion is represented only by `InvoiceProfileStatus.DELETED`. A customer retains at most 100 active profiles; create holds the tenant INVOICE customization guard across visibility, count, and insert, and list queries use the same hard limit. Versioned profile and invoice edits obey the same non-`null` merge contract as contracts, so an omitted or masked sensitive field is retained rather than cleared. Personal profiles clear organization-only bank and tax fields. CONTRACT and INVOICE built-in fields are provisioned both by V38 for existing tenants and by organization bootstrap for every newly created tenant.

## Receivable boundary

`Receivable` and `ReceivablePlan` are separate tenant-scoped versioned aggregates with independent data-scoped capability families. Both derive customer identity from their contract, and persistence repeats this relation through tenant/contract/customer composite foreign keys. Their versioned `PATCH` and `PUT` updates merge only submitted non-`null` fields and retain omitted or `null` values, including a receipt's existing plan reference. Receipt create and amount replacement lock the visible active contract before the receipt root, then calculate the active receipt total and, when applicable, the active plan total; no receipt can exceed either its contract or plan. Plan create, batch create, and amount replacement take the same contract lock and prevent active planned totals above the contract. A plan becomes immutable after any receipt history, including soft-deleted receipts, so the historical allocation cannot be rewritten. Its received, remaining, and progress values are output projections computed from active receipts rather than stored counters. Contract total changes use the same lock and cannot fall below received amount; contracts with receipt or plan history cannot be deleted. RECEIVABLE approval facts are authoritative projections of the persisted receipt, and customer, contract, and plan IDs are omitted from approval results whenever their current relationship scope is absent. RECEIVABLE and RECEIVABLE_PLAN built-in fields are backfilled by V40 and provisioned for new tenants by organization bootstrap.

Receivable list ordering is either a closed static field enum or one active, non-built-in scalar RECEIVABLE field resolved by the application from `customSortFieldCode`; the two modes are mutually exclusive. The application requires current readable, unmasked access, then passes only the resolved definition ID, scalar type, and direction to the repository. The repository owns its parameterized correlated custom-value expression and casts canonical INTEGER and DECIMAL values numerically, so request field code, column name, and expression cannot become SQL.

After a receipt or return-visit query has admitted its final scoped records, output support may batch-project the latest tenant/object/subject approval state onto exactly those IDs. This read-only projection is separate from each aggregate lifecycle `status` and contains neither approval participants nor routing facts.

## Work-task boundary

B21 introduces `WorkTask` as an independent tenant aggregate for manually created collaboration work. It does not reuse `ApprovalTask`, `StageTaskDefinition`, `Activity`, or `WorklistItemVO`, and it does not mirror their state. The root owns one current assignee, at most 50 followers, one optional CRM record reference, fixed priority and lifecycle, optional UTC due time, immutable first-start time, terminal times, an optimistic aggregate version, and a separate worklist-projection version. `DONE` and `CANCELLED` are terminal; `DELETED` is restricted soft deletion of a never-started task with no comment history.

`work-tasks:read`, `work-tasks:write`, and `work-tasks:manage` have no CRM data scope and do not imply one another. Read is only an entry permission: ordinary SQL visibility still requires the active caller to be creator, current assignee, or current follower, while tenant-wide visibility requires read plus manage. Participation, active membership, tenant, soft-delete, relationship, and fixed status/priority/due predicates are applied before both count and pagination. Cross-tenant and invisible IDs share not-found semantics. Structure, reassignment, follower replacement, cancellation, and deletion require the creator or a write-capable task manager; progress transitions require the current write-capable assignee. A visible write-capable participant may clear the task-owned CRM relationship, or set a non-null relationship only after the owning domain independently accepts the explicit new target's write scope and tenant.

V53 binds creator and assignee through tenant-composite membership foreign keys and supplies separate creator-list, assignee/due, and fixed-filter indexes. V56 adds the tenant/task/member follower relation, an independently versioned comment table, the paired checked polymorphic CRM reference, and relationship/comment indexes. Comments are never hydrated into the task aggregate; active rows page by tenant/task before output, while any historical comment row—including a soft-deleted one—blocks draft deletion. Every collaboration command locks the organization tenant guard before the task root and then the relevant follower/comment rows, rechecking active members after the guard. Relationship replacement validates only an explicit non-null replacement after locking the task; clearing or overwriting never resolves the previous target, preventing hidden-link existence probes and allowing stale or deleted links to be detached. A relationship-filter query performs its owning-domain read check inside the same `REPEATABLE_READ` snapshot as task count and page slicing. CRM relationship output batches references by owning type and reapplies read scope; access loss hides only the relationship fields. The relational state remains authoritative and no Redis state participates. Only title, priority, current assignee, due time, or lifecycle changes advance the worklist projection version; descriptions, followers, comments, and CRM links do not. B21c consumes that dedicated version without changing the B21b collaboration semantics.

B21c exposes that version only through a lightweight repository projection owned by the Work-task boundary. The SQL requires the verified tenant, current actor as assignee, an active current membership, `TODO` or `IN_PROGRESS`, the requested due-time range, and the per-source `(dueTime, taskId)` cursor before its limit. The application additionally requires `worklist:read` and `work-tasks:read`. It does not call `BusinessRecordAccessGuard`, inspect the optional CRM link, hydrate followers/comments, or treat read+manage as an assignee. The resulting item points to `WORK_TASK` itself, and acknowledgement persists only the existing tenant/member/version/due fingerprint.

## Reporting boundary

B17 reports are application queries, not a tenant-wide read bypass or a materialized reporting store. Every read route first verifies `reports:read` and active membership. B17a resolves all three source scopes for its combined overview; each B17b trend or ranking resolves only the selected opportunity, contract, or receivable source. The three owning repositories expose fixed date-bucket and owner-ranking projections while reusing their existing tenant-scoped visibility predicates; there is no shared cross-object report repository or report-specific data scope.

The application requires unmasked access to every exposed value and every field that influences a bucket, predicate, date range, or ordering. It rejects the whole requested projection when the selected source or a required field cannot be read, preventing counts, monetary totals, dates, and rankings from becoming an oracle for hidden records. B17b accepts only server-owned metric and granularity enums, caps trends at 120 buckets and ten years, and caps rankings at 100 rows and 366 days. Rankings use the fixed `amount DESC, count DESC, ownerActorId ASC` order. Field-policy reads and source aggregation run in the same read-only `REPEATABLE_READ` transaction; source-specific date indexes keep the bounded range predicates indexable.

B17c adds a separate `ReportDefinition` aggregate and repository for tenant/member-owned metadata; it does not give that repository access to business tables. `reports:write` controls personal definition mutation but grants no record scope. Create/update take the same `(tenant, objectType)` database customization lock used by B05 field lifecycle changes, so capacity, active-name uniqueness, dependency checks, and field deactivation cannot race into dangling configuration. The persisted JSON contains only bounded typed filters and COUNT/SUM descriptors and is decoded through `ReportDefinitionPOConverter` into a named aggregate snapshot; malformed stored JSON fails closed.

For catalog, detail, and every run, the application resolves the selected source capability, exact source visibility, and current active/searchable/readable/unmasked field intersection. A run passes a fully resolved `CustomReportQuery` to that source's repository. `MySqlCustomReportQuery` selects only hard-coded root columns or parameterized custom-value joins; request and stored strings never become SQL identifiers or expressions. It preserves the source's owner/department/collaborator visibility rules and expresses lifecycle as exact indexable sets (`ACTIVE` for opportunities and receivables; `ACTIVE`/`VOIDED` for contracts). Built-in ranges retain native DATE/DATETIME parameters, canonical custom DATE/DATETIME strings range directly over the field-value search index, and V51 adds missing `(tenant_id, status, time)` indexes for every supported root time field. Execution is bounded to 120 periods/ten years and a 501-row database probe, rejects results above 500 without truncation, and performs grouping and SUM/COUNT inside MySQL. Definition lookup, field-policy reads, and aggregation remain in one read-only `REPEATABLE_READ` snapshot.

B18a dashboard defaults are a separate current-member preference aggregate keyed by `(tenant, member)`. The aggregate stores a typed relative or bounded custom time range, a typed presentation data scope, and a bounded set from a server-defined display-module catalog, all under optimistic locking. A missing row is represented by the application defaults `CURRENT_MONTH`, `SELF`, and no hidden modules; reads do not create state. The current catalog contains only `CUSTOMER_CONTACT_REMINDER`, and hiding it is consumed solely by the presentation layer after the independently authorized overview response is assembled. The preference cannot carry source authorities, arbitrary predicates, member/department IDs, SQL, scripts, or arbitrary module names. In particular, its data-scope value is not the `RoleGrant` fact used by access resolvers.

B18b applies that preference in `DashboardOverviewServiceImpl` without introducing a cross-object repository. One injected UTC clock resolves the request window and automatic granularity once. `FixedReportQuerySupport` is shared with B17b and delegates each fixed metric to its owning repository; `DashboardVisibilityNarrower` intersects the independently resolved source visibility with the saved maximum and reloads the current active department/subtree when a tenant-wide source must be narrowed. Each card reads its required B05 policy and aggregate in the same query-template snapshot. Its matching Top 10 ranking resolves the same narrowed source and date window but additionally requires the source owner field, so a hidden owner makes only that ranking opaque. Only known `ACCESS_DENIED` outcomes become opaque `UNAVAILABLE` cards or rankings; all other failures abort the overview. Totals are summed from the same zero-filled trend projection, preventing a separate summary query from drifting from card points.

The same response has a closed 16-value `dataSummary` layout for the reference workbench. It may only reuse facts already resolved in that same snapshot: the sales-brief sources provide new customers, new opportunities, opportunity amount, signed contracts, contract amount and receivable amount; a customer conversion aggregate independently resolves and narrows `customers:read`, requires unmasked deal-status and status fields, then counts visible active `WON` customers whose durable `deal_time` is in the window; the permission-filtered won-opportunity card supplies its count; a separately permission-checked opportunity outcome aggregate counts only visible active `LOST` records whose immutable `outcome_time` is in the dashboard window; the contract-expiration aggregate independently resolves and narrows `contracts:read`, requires unmasked end-date and status fields, then divides visible active contracts ending in the window at the request-fixed UTC as-of date; the customer follow-up aggregate independently requires active `activities:read`, resolves and narrows `customers:read`, requires unmasked customer created-time and status fields, then counts visible customers with a current-window direct active follow-up and new visible customers with no active direct follow-up; and the receivable-plan aggregate independently resolves and narrows `receivable-plans:read`, requires unmasked due-date, planned-amount and status fields, then sums visible active plans due in that window. Customer-pool entry now appends immutable release history in the same manual or automatic command transaction, while the existing claim history records both direct claims and assignments. The dashboard independently requires `customer-pools:read` and `customers:read`, limits both histories to the current accessible pool catalog, counts releases by former owner and only non-assigned claims by claimant, then narrows those actors with the dashboard customer scope. It never treats current customer-pool membership as release history and never widens a pool event through collaborator access or a UI preference. Historical events from before this durable source exists remain absent rather than guessed. `UNAVAILABLE` is therefore an intentional fail-closed state, not a zero or a client-computed omission.

The same snapshot also owns `customerContactReminder`, a fixed aggregate rather than a customer or activity list. It independently requires active `activities:read` membership, resolves and narrows `customers:read` visibility, and checks the unmasked customer created-time and status fields before `CustomerRepository` emits six counts. Five thresholds compare the maximum active direct `CUSTOMER/FOLLOW_UP` occurrence (or the customer creation time when none exists) against one request-fixed UTC timestamp. The overdue count evaluates only the newest active direct follow-up's past next-contact timestamp, so a subsequent customer follow-up clears an earlier overdue plan. Expected access denial yields no buckets; an inconsistent tenant or an unknown persistence failure remains a whole-overview failure. No activity content, customer ID, or mutable reminder state is exported.

`PerformanceTarget` is a separate versioned aggregate for one member, one calendar month, and the server-defined `ACTIVE_CONTRACT` measure. The migration enforces its tenant/member foreign keys and natural key, so target rows cannot be repurposed across tenants or double-created for a month. Target administration always rechecks the subject's active membership and uses an independent `dashboard-targets:read/write` authority; it neither accepts nor broadens data scope. `NavigationCatalog` exposes the `/administration/performance-targets` entry only when the same read authority resolves, while the browser's route guard remains a defense-in-depth check rather than a source of menu visibility. The dashboard may project the target only for the caller's effective `SELF` selection. It sums only the affected calendar-month rows and reuses the already authorized active-contract card for actual value, returning opaque `UNAVAILABLE` instead of attempting a department or tenant roll-up. No configured rows is an explicit `EMPTY` state, not a zero-valued target.

`DepartmentPerformanceTarget` is a distinct versioned aggregate rather than a member-target roll-up. It records one active department's explicit `ACTIVE_CONTRACT` amount for `YEAR/1`, `QUARTER/1..4`, or `MONTH/1..12`; the migration's `(tenant_id, department_id)` foreign key, unique period key, and service-layer active-department recheck prevent cross-tenant, duplicate, inactive, or deleted-subject changes. The `/batch` command accepts at most the complete 17-period calendar set, rejects duplicate period tuples, locks each existing natural key, and treats every supplied version as a mandatory optimistic baseline; inserts, replacements, and their output occur in the same command transaction, so a stale/deleted row or concurrent unique insert rolls the full batch back. `dashboard-targets:read/write` remains the management authority, but does not grant `organization:read`, report visibility, or a department dashboard projection. Annual, quarterly, and monthly values coexist as independently maintained management inputs; no client or server computes one from the others, and no actual/completion result is emitted until a future server-side department aggregate defines its own source visibility and field policy.

The member `POST /dashboard/performance-targets/import` and department `POST /dashboard/department-performance-targets/import` commands intentionally are not file-upload endpoints. A browser-owned CSV parser emits at most 200 generated typed rows and immediately discards the source; the server never accepts source bytes or attachment metadata. Each import command uses the write authority, normalizes and de-duplicates incoming natural tuples, sorts them to reduce lock inversion, rechecks every target subject in the tenant, locks each existing natural key, and creates or changes only its amount inside one `CommandServiceTemplate` transaction. Its concurrency model is explicit: unlike interactive edits there is no caller-supplied version baseline, so a complete valid import succeeds as one unit or any validation, subject, or unique-key failure rolls back all earlier rows. The safe completion projection carries only `importedCount` and cannot be mistaken for an authoritative dashboard aggregate.

## Marketing-form boundary

B19a marketing forms are tenant-managed versioned aggregates with ordered field children and an immutable `LEAD` or `CUSTOMER` target type. Their field codes reference the current target field catalog; field type and options are resolved from B05 on each management or public read so stale metadata is not persisted. Configuration and target field lifecycle changes share the matching customization lock, and an active form is a database-checked dependency that blocks field deactivation. Activation builds the persisted owner's server-derived caller and invokes the matching Lead or Customer access resolver, so active membership, effective target write scope, and department-scope prerequisites are resolved rather than approximated from a non-null grant. It also requires current `WRITE` access to the target name, owner and every configured field. Every currently required public-safe scalar target field must be configured as required; unsafe relation, member, department and address fields remain unavailable in B19. B29b implements FILE only for `LEAD` through a separate anonymous draft credential and structured candidate path without relaxing the scalar public-value whitelist; `CUSTOMER` forms reject FILE input.

Marketing-activity creation may coordinate the existing form aggregate through
`MarketingFormCreationCoordinator`: a nested `MarketingFormCreateRequest` is authenticated with
`marketing-forms:write`, validated under the matching LEAD or CUSTOMER customization lock, saved as INACTIVE, and linked
before the activity is persisted in the same outer command transaction. The create request accepts
either that nested form or an existing `marketingFormId`, never both. Updates reject nested form
creation instead of silently ignoring it. The form target must match the activity relation, so
`CONTACT` activities do not have a public form path and this is not a generic custom-object form
protocol.

`MarketingActivityType` is a server-owned closed catalog published through the activity
configuration-options query after current membership and `marketing-activities:read` validation.
New activity commands accept only its stable codes; the persistence column stays a string so a
pre-catalog type can remain unchanged during a later edit, but it cannot be introduced as a new
value. This makes the browser's dropdown an API-driven interaction rather than a client-side
copy of type labels, without forcing a lossy migration of historical activities.

`MarketingActivityBatchDeleteRequest` is a bounded command of 1–100 unique
`MarketingActivityVersionRequest` pairs. Its command template validates deletion authority and
all request-shape invariants, then locks the normalized ID order and version-checks the complete target set before
deleting any aggregate or withdrawing attachments. Root deletes and attachment withdrawals happen
only after that preflight in the same transaction, preserving all-or-nothing lifecycle semantics.

The anonymous identifier is a canonical tenant locator plus a random form key. It narrows a tenant-scoped repository lookup but grants no authenticated tenant context. Public submission deserialization is a strict whitelist: tenant, owner, status, unknown top-level properties, and unconfigured field codes are rejected, while public output omits internal owner, tenant, version, and success-message data. Rendering and submission revalidate current owner membership, capability, resolved target scope, and B05 write policy, so later revocation fails closed without republishing. Submission locks the active form root in its outer command transaction, maps only the locked configuration, and invokes the matching reused Lead or Customer creation coordinator inside that transaction. It does not nest another `REQUIRES_NEW` command while retaining the form lock, preventing connection-pool starvation and making the created target record roll back with the coordinating command. Expected target-creation failures and wrapped internal failures therefore retain the sole client-facing `MARKETING_FORM_SUBMIT` error scene. Form update, status change, and deletion acquire the same root lock before the matching customization lock. This ordering makes a submission either finish before a concurrent change or observe the committed changed state; a completed deactivation cannot be followed by a target record created from its old snapshot. Deactivation remains available to form administrators even when the persisted owner has lost target write access, providing a fail-safe shutdown path.

B19b records the successful result as one immutable row in `crm_marketing_form_submission`, separate from the bounded `MarketingForm` aggregate. The public command appends the row only after the target coordinator returns the persisted Lead or Customer identity and while the same form-lock transaction is still active; either both the target record and ledger commit or neither does. Tenant-composite foreign keys bind the row to its form and the matching target record, separate target-scoped uniqueness prevents duplicate attribution, and `(tenant, form, idempotency key)` returns the same receipt only when its SHA-256 canonical request digest and form version match. A changed replay fails before it can consume a FILE capability or create another target record. No cascade removes historical success facts after a soft delete. The insert uses MySQL `UTC_TIMESTAMP(6)` and reloads that persisted value, so application-node clocks cannot change bucketing or ordering. The row contains only form identity/version, target type and record identity, idempotency key, request digest, and database UTC time—never submitted values, request metadata, IP addresses, or free-form attribution data.

Submission trends read only the tenant-scoped ledger after proving active membership, `marketing-forms:read`, and form ownership by tenant. They use fixed UTC DAY/WEEK/MONTH expressions, inclusive calendar inputs, zero-filled application buckets, a 120-bucket limit, and a ten-year limit; no target aggregate or target field is read. Visible-link pages additionally resolve the querying caller's current target-specific read visibility. Persistence applies current active target status plus SELF, department, subtree, tenant, and collaborator predicates inside a correlated SQL existence condition before both count and page slicing. Consequently historical accepted counts remain stable while soft-deleted, cross-tenant, or currently hidden target records neither occupy a page nor contribute to its total. INACTIVE and DELETED forms retain both management history queries.

Anonymous POST admission runs in the REST security chain before application or database work. The filter percent-decodes the application path once, validates its public-ID segment with `MarketingFormPublicId.parse`, regenerates the canonical identifier for the bucket key, and rejects malformed or non-canonical decoded paths. Direct submission, the `/submissions` alias, and equivalent percent-encoded path variants therefore share one quota. One atomic fixed-window decision consumes both a per-public-form and resolved-source quota. Both bucket maps are bounded, expire idle entries, and fail closed when full; defaults are 60 submissions per form per minute and 20 per source per minute. Source resolution shares the B09 trusted-proxy rules, so untrusted `X-Forwarded-For` values cannot create new buckets. This is per-replica local protection rather than a distributed global quota; multi-replica deployments use a gateway or shared limiter when global enforcement is required.

## OA form and request boundary

B20a introduces `OA_REQUEST` as a stable B05 and B11 object type. New-tenant bootstrap and V52 existing-tenant backfill create the same five built-ins: writable `request_title`, plus server-derived `form_code`, `applicant_actor`, `applicant_department`, and `submitted_time`. A tenant may add governed custom fields through the existing B05 APIs. `OaFormDefinition` persists only an NFKC/lowercase-normalized code, presentation metadata, one same-tenant OA approval reference, and ordered `(fieldCode, required, sortOrder)` children; field type, options, status, and role access are never copied.

Management reads require `oa-forms:read`, resolve current field metadata, omit HIDDEN fields, and never return deleted forms. The available catalog also requires `oa-requests:submit`, an active caller membership, an active matching approval whose initiator scope admits the member, and current `WRITE` access to every configured field. Missing, inactive, server-derived, or non-writable inputs fail closed; B24c handles FILE through its separate draft/value shape rather than scalar facts. `request_title` remains required; each form has at most 100 unique inputs and each tenant at most 200 non-deleted forms. The database repeats tenant identity through composite creator, approval, form, and field foreign keys and enforces live normalized-code uniqueness.

Create, update, status change, delete, B05 field lifecycle mutation, and relevant B11 approval-definition mutation share the `(tenant, OA_REQUEST)` customization guard. OA form commands acquire that guard before hydrating the root and its children, so a waiting transaction cannot retain a pre-guard `REPEATABLE_READ` snapshot. Approval-definition update and status change use the same guard-before-definition-row order; status preparation reads only the immutable object type outside its command transaction, then the transaction acquires the guard and reloads the definition with `FOR UPDATE`. Activation rechecks the active approval and requires every approval condition field to belong to the configured inputs or server facts. An active form blocks field deactivation, searchability removal, and approval deactivation or incompatible condition updates. Deactivation and later soft deletion deliberately avoid those dependency checks, preserving a fail-safe shutdown path even after referenced configuration becomes invalid.

B20b adds immutable `OaRequest` roots without drafts or post-submit field mutation. The submit command locks the tenant serialization row, rechecks active membership, acquires the OA customization guard, locks and reloads the active form, resolves current field metadata/access and the active approval, normalizes exact configured inputs, and derives applicant, department, form code, and submission time on the server. It inserts the request and unique-field reservations before invoking the internal `ApprovalSubmissionCoordinator`, whose fact supplier reads that persisted request; the resulting B11 instance uses `oa:<requestId>` and is linked back before the single outer transaction commits. The path never calls the public `ApprovalService` command or opens a nested connection. A failure at any point rolls back both roots and all children. The `(tenant, applicant, idempotencyKey)` constraint is serialized before lookup, and a deterministic digest of form/version/normalized submission distinguishes equivalent retries from conflicting reuse.

OA visibility is a SQL union of applicant, historical task assignees, snapshotted managers, snapshotted watchers, or a current member with `oa-requests:manage`; `oa-requests:read` is only the entry capability. That predicate runs before count and page slicing. `BusinessRecordAccessGuard` uses the same adapter for B11 details and mutations, so approval participation cannot bypass current active membership and OA entry authority. Both request and approval outputs apply current OA field hiding/masking, including top-level OA approval title/applicant/time projections; the request envelope does not duplicate raw server facts outside `values`. The request root stores no approval status mirror: B11 remains the only status source. B15 sees the same approval task through its existing `APPROVAL_PENDING` source only when `request_title` remains readable without masking, while B21 Work remains a separate object/API/capability boundary.

B20c keeps `OaAnnouncement` outside the B05/B11 object model. Draft presentation and typed `TENANT`, `DEPARTMENT_SUBTREE`, or `MEMBER` selectors are versioned until publication; after publication content and selectors are immutable and only withdrawal followed by optional soft deletion is allowed. Publication acquires `organization_tenant` before the announcement root, rechecks the manager's active membership and every selector, expands active department descendants, intersects active same-tenant memberships, de-duplicates, and reads at most 10,001 candidate IDs. A result above 10,000 aborts the transaction. The root transition and chunked recipient inserts commit together, while concurrent publication is serialized by the root lock and optimistic version.

Inbox count, pagination, detail, and read writes require `oa-announcements:read` and apply published status, recipient snapshot, verified tenant, and current active membership in SQL. Organization changes never add recipient rows; suspension closes access even when a historical snapshot remains. A read command first takes a shared lock on the current membership and then on the visible announcement root, ordering it against concurrent suspension and withdrawal without exclusively serializing every recipient of a popular announcement. A unique-key insert-if-absent preserves and returns the first `(tenant, announcement, member)` UTC receipt under concurrent retries. Management pages map root-only `OaAnnouncementSummary` rows, and inbox page/detail/read-lock paths map root-only `OaAnnouncementInboxItem` rows; none queries department or member selector children. Full aggregate hydration remains isolated to managed detail and aggregate mutations. Management page/statistics and detail/statistics operations recheck active membership as the first read inside their `REPEATABLE_READ` query transaction, so authorization and all paged/count data share one snapshot. Static inbox/unread/receipt HTTP matchers require read authority before the broader write-only announcement matcher, while application guards independently repeat current membership and capability checks. Manager statistics batch only recipient and receipt counts. V55 repeats tenant identity through creator, selector, snapshot, and receipt foreign keys; V57 removes its redundant `deleted_time` mirror so `status=DELETED` is the only soft-deletion representation. Redis, B15 acknowledgements, Work tasks, outbox events, and external notification are not involved.

## Approval and stage workflow boundary

`ApprovalDefinition` is tenant-owned, versioned configuration over a stable `BusinessObjectType`. Its conditions reference only active searchable `FieldDefinition` codes and bounded typed values; no table, column, SQL, script, or arbitrary query expression enters the domain. Fixed members, active role assignments, manager fallback, and applicant-selected members resolve to at most 100 active tenant memberships, and normalized applicant-selected step keys cannot collide. Public routing facts are read from the persisted customer, contact, lead, opportunity, contract, invoice, or receivable inside the submission transaction. OA preview/submission instead enters through the form-bound B20b service and reads its just-persisted authoritative request; callers cannot use general B11 submission to inject OA facts. A validated internal stage snapshot may override supported business values only after B05 write authorization. A submission stores the definition version, normalized fact snapshot, submission-time manager set, step names and modes, and the final assignee route. Later definition status, managers, or metadata changes therefore cannot alter an existing `ApprovalInstance`.

`ApprovalInstance` owns at most 5,000 review tasks across the initial route and transfer history. `ALL` requires every assignee and rejects on the first rejection; `ANY` approves on the first approval and rejects only after all assignees reject; `SEQUENTIAL` activates one assignee at a time. `ONCE` skips an assignee who already approved an earlier step and rejects transfers back to such a member. Transfer checks total capacity before completing the original task, then appends a linked replacement to preserve the timeline. Every action locks the tenant-scoped root and uses root/task optimistic versions; persistence inserts replacements and updates only tasks whose state changed. A batch contains at most 50 unique instances, locks them in ID order, commits atomically, and returns typed all-or-none results. Approval lists and counts scan lightweight root references for business-record visibility; list pages then hydrate the final-page roots only to calculate caller-specific `allowedActions`. Receivable and return-visit projections first apply their own business visibility, then batch-read only the latest closed instance state for those already-admitted subject IDs; they never join tasks, people, routing facts, or action capabilities. Public instance and summary projections contain the display title, status, version, action capabilities and identity-free task timeline, never applicant/assignee identity, approval facts, business-object metadata, manager or watcher data. Detail and mutation behavior rechecks current business-record visibility; a client must use the returned capability rather than infer action eligibility from identity. Idempotency is unique per tenant and is accepted again only for the same definition, subject, object, and applicant.

`StageWorkflowDefinition` stores bounded stages, required field codes, tasks, applicability, and optional approval-definition references. For every gate, the union of stage-required and approval-condition fields is validated against the 100-field instance snapshot limit when the workflow is saved or activated and again when a referenced approval definition changes. Generated gate titles are bounded to the approval-instance title limit. Once any runtime record references a definition its stage configuration is immutable. A definition can soft-delete only when no `ACTIVE` or `AWAITING_APPROVAL` runtime record still uses it, preserving field and approval-definition dependencies until every run is terminal; it separately exposes only its domain-allowed next statuses when the caller has `CHANGE_STATUS`. `StageWorkflowRecord` binds only a stable business object type and numeric record ID. Every public read or write first reapplies that object's current customer, contact, lead, or opportunity data scope. Its canonical HTTP resource is `/api/v1/stage-workflow-records/{workflowRecordId}`; the projection includes the current stage, gate status, `allowedActions`, writable field codes, allowed task codes, structured ADDRESS current value and visible FILE metadata. A stage-origin `FileFieldDraft` additionally stores the exact tenant workflow-record scope; consuming it requires the same record, draft, field, complete non-expired staged file set and current B05 write access. Snapshot assembly removes hidden fields and masks readable values for the current caller. An approval gate records its pending instance and resumes only after a terminal result; approval advances the stage, while rejection, cancellation, or withdrawal is consumed by one call that only restores `ACTIVE`. A later explicit advance captures fields and increments the attempt. Comments are tenant/record scoped, versioned, soft-deleted, exposed with caller-specific `canDelete`, and removable only by their author.

## Transactions and events

`CommandServiceTemplate` runs state changes through:

```text
validate -> prepare -> execute -> onSuccess
```

`CommandServiceTemplate` runs `validate` and `prepare` before opening an independent transaction for `execute` and `onSuccess`. Slow preparation such as password hashing therefore does not hold a database connection. A failure rolls that transaction back before it is converted to a `Result`, so an outer transaction is neither marked rollback-only nor surprised by `UnexpectedRollbackException`. Treat each command as its own atomic use case; do not use it when several commands must share one transaction. `QueryServiceTemplate` keeps the same validation/preparation boundary, then runs `execute` and `onSuccess` in an independent read-only `REPEATABLE_READ` transaction. Multi-query aggregate hydration therefore observes one database snapshot instead of mixing a root version with children from a later commit.

The relational database is the source of truth. `AfterCommitExecutor` delays cache writes, cache invalidation, and in-process event publication until commit. Events and cache actions use separate registrations so one callback failure cannot skip the other. Cache invalidation installs a short refill fence before eviction so a concurrent stale reader cannot repopulate a 30-minute entry after the write commits.

Events are already published from the post-commit phase. Use ordinary `@EventListener` consumers; an `@TransactionalEventListener(AFTER_COMMIT)` would be registered too late and will not receive this publication path.

Post-commit callbacks are not durable delivery. Use a transactional outbox when an event must survive process failure after commit.

B22 call start is stricter than a generic event outbox: it uses the typed command outbox and adapter command ledger defined by B22-R. A core transport timeout retries the same command identity; it never creates a replacement command or infers whether the provider was called.

Redis is optional and implements an application output port. Cache keys include tenant identity. Selecting the no-op adapter must not change authorization or query correctness.

## Aggregate persistence

Aggregates own their state transitions. Persistence restores them through named snapshots and `reconstitute`, including identity, tenant, timestamps, and optimistic-lock version, without raising new domain events. Converters map persistence state explicitly; MapStruct is used only where mechanical mapping stays unambiguous. Customer, contact, and lead child collections are synchronized by natural key, so unchanged child rows retain their creation audit time and updates do not incur unconditional delete/reinsert cycles. Opportunity relationship, custom-value, and product-snapshot collections are replaced inside the same root transaction and never become visible independently of its optimistic-lock update.

Tenant-owned repository constraints (actor-global and control-plane exceptions remain explicit in their owning ports and tests):

- every tenant-owned business operation requires a non-null `TenantId`;
- update predicates include tenant and aggregate identity;
- MyBatis-Plus compares and increments the persisted `version`;
- zero updated rows produce a version conflict;
- save synchronizes and returns the same aggregate instance so pending events remain available;
- physical deletion is not part of the domain repository contract.

Soft-deletable aggregates use their own `status=DELETED`; for users this is `UserStatus.DELETED`. Deleted-user visibility is an explicit query policy, not a hidden SQL rewrite. For locally created users, the application command persists the user first, then uses that durable ID to create the global member profile, active current-tenant membership, and baseline member role in the same transaction. `ACTIVE` resumes the linked membership/profile; `INACTIVE`, `LOCKED`, and `DELETED` close them. Authorization cache invalidation is registered after the same successful commit, so an account lifecycle write cannot leave a usable member entry with stale tenant authority.

## Schema changes

Flyway is the only schema initializer. Migrations live in `infra/persistence/src/main/resources/db/migration` and use `V<version>__<description>.sql` names.

Do not add `schema.sql` or container initialization SQL, and do not edit an applied migration. Test migrations against an empty MySQL database and, when relevant, the previous schema. Keep migration columns, PO types, converter mappings, mapper XML, and aggregate reconstruction in the same change. Bounded JSON columns may persist validated metadata or preferences, but they are not an escape hatch for executable queries or unbounded domain state.

## Security boundaries

- Authenticated business APIs reject anonymous requests. Authentication, initial installation and public marketing forms use their dedicated, bounded admission paths described above; they do not grant general business access.
- Human HTTP routes and application use cases both check authorities; connector ingress uses an independent authenticated connector and has no CRM authorities.
- Authenticated tenant identity comes from verified human authentication or an exact active opaque connector registration, never ordinary request data. Public-form locators/capabilities and background claims resolve only their narrow operation context under the owning contract.
- A connector principal never represents an actor, member, owner, administrator, or external agent, and connection generation never participates in identity.
- Production cannot install the trusted-header development adapter.
- Request headers cannot grant authorities or administrator state.
- Passwords, reset tokens, authentication credentials, and full request objects must not be logged.
- Planned B22 call paths also exclude complete or masked phone values from logs/metrics, and exclude phone HMACs, ciphertext metadata, recording references, provider URLs, raw callbacks, and provider exception messages from every ordinary observability path.
- Tenant-owned repository and cache calls without a tenant fail closed. Existing authentication, installation, actor-global, public-form, background-work and global reference/control-plane ports retain only their documented narrow exceptions; connector resolution remains limited to the two exact security projections above. All tenant-owned business access after resolution is tenant scoped.

See [configuration](configuration.md) for profile and security settings, and [development workflow](usage-guide.md) for adding behavior.

`ArchitectureBoundaryTest` uses ArchUnit bytecode analysis to enforce inward dependencies across application, domain, API, shared, and infrastructure classes. It also rejects controller-to-repository/VO coupling, public entity setters, missing core layers, and naming violations for Request, Response, VO, PO, and repository types.

## Controlled CRM CSV import boundary

`CrmImportDraft` is a tenant/member-owned, short-lived `LEAD|CONTACT|PRODUCT` state machine. It stores only lifecycle state, version, deadline and final imported-row count; the source is a single `IMPORT_DRAFT` controlled attachment relation, never a DTO blob or domain value. The target adapter requires fresh `files:write`, active membership, object-specific write authority and the original uploader on every attachment operation, so a generic attachment capability cannot be used to import CRM records or read another member's source. Only `text/csv` is admitted for this target; strict UTF-8 parsing, fixed server-defined columns, the 1 MiB/200-row limits and Jakarta field validation execute after clean publication. Product uses the fixed `name,code,categoryId,unit,listPrice,description,availability` columns. Preview projects only a count plus row number/stable code and no source value.

Confirmation locks tenant, import root and attachment relation in the shared attachment order, reparses the immutable available bytes, and invokes the existing Lead, Contact, or Product creation coordinator inside one `CommandServiceTemplate` transaction. Lead and Contact row validation, data-scope, field-policy, relation or unique-key failure rolls the entire import back. Product first normalizes each code and skips an existing active code or a repeated code in the same source; every remaining Product creation is transactional and any non-duplicate validation, scope, field-policy or relation failure rolls those creations back. A successful confirmation consumes the draft, records the actual created-row count, withdraws the source and schedules its ordinary controlled deletion; the same version may replay only the completion projection after a lost response. Withdrawal applies the same root lock and source cleanup. Unconfirmed source bytes and their derived error-report eligibility have a fixed seven-day retention: a bounded attachment-lane worker re-locks each due root, marks it `EXPIRED`, withdraws its private relation, and schedules exact byte reclamation. It retains only the non-sensitive lifecycle audit row; raw CSV bytes, file names, cells and failed raw requests are excluded from database payload columns, logs and public responses.

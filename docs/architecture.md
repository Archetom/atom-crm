# Architecture

The generated project uses Domain-Driven Design with explicit ports and adapters. Business rules stay in `domain`; HTTP, persistence, cache, and authentication remain at the boundaries.

## Dependency rule

Dependencies point inward:

```text
infra/rest ───────┬──────────────────────────────> domain policy vocabulary
                  │
infra/facade ─────┼──> application ──> domain
infra/persistence ┘          │
                             └──> api and shared

infra/external ─────────────────────> application output ports
infra/security ─────────────────────> domain security ports
start ──────────────────────────────> all runtime adapters
```

- `domain` does not depend on `api`, `application`, `shared`, or `infra`.
- `application` contains use-case orchestration, not servlet, MyBatis, Redis, or vendor code.
- Infrastructure modules implement inward-facing ports.
- `start` is the composition root and contains no business rules.
- `shared` contains small technical primitives, not domain concepts.

## Modules

| Module | Owns | Must not own |
| --- | --- | --- |
| `api` | Public contracts and explicit authenticated subject contexts | Domain behavior, persistence models |
| `domain` | Aggregates, value objects, policies, domain services, events, repository ports | Spring MVC, SQL, Redis, API DTOs |
| `application` | Use cases, authorization, transactions, output ports | HTTP parsing, mapper XML, vendor clients |
| `shared` | Boundary result and error primitives | User or tenant behavior |
| `infra/rest` | HTTP transport, authentication, status mapping | Business decisions |
| `infra/persistence` | PO mapping, MyBatis, Flyway, cache adapters | Caller discovery, use-case orchestration |
| `infra/external` | Third-party output-port adapters | Application workflow |
| `infra/security` | Password hashing and other security adapters | Domain policy |
| `infra/facade` | Facade implementation and API/application mapping | Persistence |
| `start` | Runtime assembly and end-to-end tests | Reusable business logic |

## Human request flow

```text
HTTP request
  -> Spring Security verifies or rejects identity
  -> AuthenticatedCallerMapper creates AuthenticatedCaller
  -> a facade maps the public contract
  -> a use-case service selects CommandServiceTemplate or QueryServiceTemplate
  -> application checks authority and derives TenantId
  -> aggregate or domain service enforces business rules
  -> tenant-scoped repository queries or persists
  -> facade maps the result to an API response
  -> REST maps stable errors to HTTP status codes
```

`AuthenticatedCaller` is an explicit input. Identity and tenant ownership are not read from a domain `ThreadLocal`.

## Browser password authentication boundary

Browser authentication has one narrow pre-tenant path: `AuthenticationService` uses an exact `(tenantId, username)` user lookup and a `PasswordVerifier` port to validate credentials, then signs a short-lived `PasswordLoginChallenge` through `AuthenticationTokenCodec`. Only after successful verification does it enumerate the user's active tenant memberships. A second command verifies that signed challenge and selected current membership, then issues a signed `BrowserSession`; `infra/rest` alone places the token in an HttpOnly cookie and restores an `ActorPrincipal` on later requests. The application revalidates the user aggregate version, user state, and selected membership before accepting each session, so password changes and status changes invalidate existing cookies without an identity cache.

Password-reset issue/consume is an application command boundary backed by `PasswordResetTokenStore`: plaintext tokens exist only long enough to compose post-commit delivery and the persistence adapter stores a purpose-separated digest, expiry, and consumed state under a row lock. The optional SMTP adapter is an output port, not an application dependency; missing configuration fails closed with a stable delivery-unavailable error. REST owns same-origin double-submit CSRF checks for cookie-authenticated unsafe methods. Domain entities never receive browser cookies, raw passwords, reset tokens, email URLs, servlet requests, or SMTP configuration.

Fresh-system installation has a dedicated public pre-tenant boundary. `SystemInstallationService` first exposes and rechecks a read-only installation marker, then uses one MySQL singleton-row claim in the same transaction as initial-user creation. The winner creates only tenant 1 and its owner identity through the ordinary user, organization and default-provisioning rules before a browser session is issued after commit; a concurrent or later request receives a stable conflict and cannot create another tenant or account. A completed installation means an active login user with an active `TENANT_OWNER` membership, not merely a historical tenant, membership or role row; Flyway repairs older marker rows that lack that usable administrator. Requests never supply a tenant ID, authority, role or initial password hash.

## Contract list summary boundary

`POST /api/v1/contracts/summary` shares the exact validated `ContractQuery` construction used by the contract list and returns a server-calculated count, contract total, received amount, and outstanding amount. The application resolves both the contract and receivable read scopes from the verified caller, and requires unmasked access to both monetary fields before delegating to the tenant-scoped contract repository. The repository applies the contract predicate to the contract amounts and independently applies the resolved receivable visibility predicate to its correlated received-amount aggregate; browser-provided identifiers or cached totals never participate in either scope decision.

## Finance-list atomic batch command boundary

`PUT /api/v1/receivables/batch/owner` and `POST /api/v1/receivables/batch/delete` accept at most 100 unique observed targets, sort IDs to keep a consistent locking order, and lock/validate every visible target before changing any one. Invoice owner transfer, issue-result reset and delete follow the same boundary through `PUT /api/v1/invoices/batch/owner`, `PUT /batch/reset`, and `POST /batch/delete`; reset requires every invoice to remain `ISSUED`, delete requires every invoice to remain `PENDING`. Each command re-resolves its independent authority scope, validates every optimistic version, and checks applicable field policy and active-member assignment before one save, attachment withdrawal, or file-field withdrawal occurs. A stale, missing, out-of-scope, invalid-state or field-policy target rolls back the complete command.

Lead and Contact lists use the same 1–100 target atomic boundary through `PUT /api/v1/leads/batch/owner`, `POST /api/v1/leads/batch/delete`, `PUT /api/v1/contacts/batch/owner`, and `POST /api/v1/contacts/batch/delete`. They acquire the matching customization guard, sort and lock every requested aggregate, re-resolve record visibility and owner scope, then preflight every optimistic version and active-child constraint before changing an owner or withdrawing attachments and governed file fields. A single stale, hidden, invalid, or unauthorized target leaves every selected lead or contact unchanged.

Opportunity lists use the same owner-scope, 1–100 target boundary through `PUT /api/v1/opportunities/batch/owner` and `POST /api/v1/opportunities/batch/delete`. The command takes every target row lock in numeric order, validates the complete optimistic-version set before updating one owner or withdrawing one attachment/file field, and rechecks the active replacement member, assignment scope, and owner field policy. A stale, hidden, invalid, or unauthorized target rolls back the entire selection.

Contract team operations use the matching bounded boundary through `PUT /api/v1/contracts/batch/collaborators` and `DELETE /api/v1/contracts/batch/collaborators`. The add command upserts only the named active collaborators with `READ`/`WRITE` and nullable inclusive `effectiveUntil`, while preserving every unrelated collaborator on each contract; the remove command never permits an owner to be named and is a no-op where that collaborator is absent. A null deadline is unlimited; an expired deadline is excluded from every collaborator read/write visibility predicate. Both routes sort and lock every target, validate every observed version, owner-scope visibility, active member, and non-past deadline before one root is saved, and keep all selected contracts in the same command transaction.

`POST /api/v1/receivables/summary` shares the exact validated `ReceivableQuery` construction used by the receivable list and returns only its count and total amount. The application resolves the verified caller's `receivables:read` visibility, fields, saved view and relation checks before it requires unmasked RECEIVABLE `amount` access. The repository uses the same tenant/data-scope, keyword, owner, relation and typed-condition predicate for both pagination and aggregation; page and sort inputs cannot alter totals, while browser-provided identifiers and cached client money never influence scope.

## Receivable-plan list summary boundary

`POST /api/v1/receivable-plans/summary` shares the exact validated `ReceivablePlanQuery` construction used by the plan list and returns its count, planned amount, receipt amount and remaining amount. The application first resolves the caller's plan visibility and unmasked RECEIVABLE_PLAN `planned_amount`, then separately resolves `receivables:read` and unmasked RECEIVABLE `amount`. The repository applies the plan predicate to the outer plan aggregate and a fixed correlated receipt aggregate to the independently resolved receipt visibility; it never treats a plan's materialized progress, a browser list row or a client money cache as evidence of a caller-visible receipt.

`POST /api/v1/receivable-plans/export/csv` is an aggregate-specific synchronous projection. The application resolves independent `receivable-plans:read` and owner-derived `receivable-plans:export` access, verifies both refer to the same active tenant member, then asks the repository to append the export scope to the already validated list predicate. The resulting SQL therefore intersects—not substitutes—read and export visibility before a stable due-date/installment/id order and a fixed 5,001-row probe. Field codes are closed to the RECEIVABLE_PLAN catalog and must remain readable and unmasked; CSV cells derive only from the already policy-filtered plan projection. A shared non-queueing admission slot, 5,000-row/16-MiB encoder limit, RFC 4180 escaping and formula protection bound the request before the REST adapter supplies fixed no-store attachment headers. No CSV artifact, job, file relation or caller-provided SQL/filename crosses the architecture boundary.

The plan list and summary accept either an explicitly authorized `ownerActorId` or `subordinateOwnerOnly`, never both. The latter resolves a server-owned membership set from the verified caller's current department subtree and resolved plan scope; an empty set becomes a false predicate. That predicate is shared by pagination and every plan aggregate, so neither a query parameter nor an amount summary can widen the caller's actor scope.

The same plan predicate can include either one member-owned RECEIVABLE_PLAN saved view or up to 50 temporary typed conditions, never both. The application rechecks active searchable field metadata, current unmasked access, operator/value compatibility, and visible customer or contract relation targets before persistence receives a fixed column or custom-field condition. The repository applies that predicate to pagination and the correlated-receipt money aggregate together; no browser row, field code, relation identifier, or cached total can affect authorization or aggregation outside that validated path.

## Normalized connector ingress flow

Connector registration, credential lifecycle, authentication and the durable normalized call-fact inbox are implemented. Production outbound calling and recording playback are not enabled. `AuthenticatedConnector` contains only the verified opaque reference; `ConnectorGuard` resolves its current active tenant registration, and commands lock that registration in their write transaction. The credential and identity projections are narrow authentication exceptions, not unscoped business repositories.

Native provider topology, endpoints, payloads and secrets stay in infrastructure. The core consumes typed, bounded normalized facts with stable identities. Durable inbox/outbox state, attempt fences and independent recovery evidence prevent retries or reconnects from inventing progress. Future provider I/O remains outside database transactions; ambiguous dispatch cannot be turned into redial without authoritative proof. Sensitive address and recording access require dedicated encryption, retention, current authorization and bounded stream contracts. See [connector integration](connector-integration.md) for the authentication, reliability, privacy and readiness requirements and the maintained conformance runners.

## Enterprise data and registered identities

The identity key is `(identityScope, registryScheme, canonicalValue)`. Names, legal jurisdiction, entity status, identifier standing and provider metadata are separate facts. Exact scheme validators govern LEI, USCC and Companies House values; meaningful prefixes and leading zeros are preserved. Unknown scope/scheme pairs fail closed.

Human queries require current membership and `enterprise-data:read`. Independent tenant policy gates technical source capability before provider I/O. The source returns only allowlisted organization observations; the application checks identity, source kind, standing, TTL, candidate limits and controlled attribution. Ordinary capability/search/lookup responses remain ephemeral and do not write Customer state. Bundled GLEIF and Companies House runtime adapters are default-off; Companies House production policy still remains unavailable pending independent live evidence.

The separate Customer adoption boundary requires explicit selected facts, a short-lived caller-bound preview, approved adoption rights, a fresh exact lookup and current Customer/field authorization. Customer save, exact tenant identity reservation and value-free provenance commit atomically. Active and pooled Customers retain identity claims; soft deletion releases the current claim. A durable tenant-scoped worker enforces provenance retention without impersonating a human caller. See [enterprise data integration](enterprise-data.md) for current support, default-off gates and verification.

## File and attachment boundary

`AttachmentFile` owns content identity and independent byte, inspection and publication state. Application ports own opaque immutable storage generations, typed evidence, closeable/cancelable streams and durable work claims. Provider paths, URLs, headers, scanner findings and SDK types terminate in infrastructure. No storage or scanner I/O runs inside a database transaction.

Public operations are target-first. The closed `AttachmentTargetAccessRegistry` intersects `files:read/write` with current owning-record capability, scope and lifecycle; it has no reflection or tenant-wide fallback. Each file stays bound to one same-tenant target, enforced by typed foreign keys and one-file/one-link uniqueness. Commands lock the owning root before file rows; OA Request additionally preserves approval-instance-first ordering. Current target authorization is repeated before publication and every download.

Ordinary attachments, structured `FILE` values, pre-create drafts, immutable evidence snapshots and public marketing drafts have separate relations and authorization. Anonymous upload uses an exact draft capability rather than a synthetic member. OA Request collaboration never modifies submission facts; OA Announcement publication freezes its available attachment set. Customer/Contact pool transitions suspend access; parent deletion atomically withdraws relations and creates exact-generation cleanup work. Work Task rejects deletion when attachment history exists.

The installed storage/inspection profiles are secure local NIO, bounded magic and streamed engine scanning. Production remains disabled until binding, quota, current build/scanner evidence and worker readiness agree. S3-like and managed inspection models are conformance evidence only. See [files and attachments](file-storage.md) for limits, crash recovery, streaming, deletion and deployment requirements.

## Organization membership boundary

`MemberProfile` is global data bound to the verified actor identifier. `OrganizationMembership` and `Department` are tenant-owned aggregates. Tenant-bound organization operations use `OrganizationAccessGuard`, which requires both the route authority and an active membership for the caller's verified tenant before a repository access.

Membership requests may name a `targetTenantId`, but that value is only a review destination. Target validation and the accessible-tenant list return data; they do not change `AuthenticatedCaller`, install a tenant context, or mint a new credential. Department parent lookups always carry the current tenant, and move validation walks the in-tenant ancestor chain to reject cycles.

The applicant-owned membership-request page is a separate `organization:request` query. It derives the applicant only from the verified caller, passes that `MemberId` into the repository, and orders bounded records by creation time; it does not use the caller tenant as an implied target filter or expose a target-tenant directory. Administrator review remains a distinct active-membership plus `organization:write` query scoped to the current target tenant. The applicant can only withdraw an exact request resolved by the same verified applicant.

Every initialized tenant has one `organization_tenant` row. Department creation, moves, deactivation, deletion, membership approval, and target-tenant membership submission acquire that row with `FOR UPDATE` before their first target-tenant database read. This serializes structural changes per tenant, so two opposing moves cannot validate stale paths and form a cycle, and submission cannot retain a stale pre-bootstrap eligibility check. Deactivation rejects active children or memberships; deletion is stricter and rejects every child or member assignment, including inactive records. A generated-column unique key permits at most one `PENDING` membership request for one applicant and target tenant; the application pre-check improves the message but the database is authoritative under concurrency.

Department-member reads first reject a `DELETED` department, then page active profiles with one tenant-and-department-scoped join. This keeps deleted resources invisible and avoids loading an unbounded membership list or issuing one profile read per member.

Region reference data is not part of organization membership or tenant ownership. `RegionReferenceCatalog` is an application output port and `/api/v1/reference/regions` is its independent read contract; the bundled adapter is intentionally empty until a deployment supplies a curated data set.

## Authorization, navigation, and customization boundary

Tenant roles grant only capabilities declared by `AuthorityCatalog`. The tenant-owner role is evaluated dynamically and is not reduced to mutable grant rows. Navigation is derived from the same effective capabilities, then filtered by the current member's bounded preference; hiding an item never grants or revokes a capability.

The customization engine uses stable `BusinessObjectType` and `CustomFieldType` enums. `FieldDefinition` owns metadata only; values for customers, contracts, and later business aggregates remain in their owning modules. Field codes, types, and uniqueness are immutable after creation, select-option values cannot be removed, and deactivation preserves metadata for future value interpretation. Deactivation is rejected while a layout or saved view references the field; disabling search is rejected while a saved view references it.

`customization_object_guard` supplies one database serialization row per `(tenant, objectType)`. Field-definition commands, layout writes, and saved-view writes acquire its exclusive record lock with one `INSERT ... ON DUPLICATE KEY UPDATE` statement before reading the field catalog or dependency state. The atomic upsert creates a missing guard or directly locks an existing one without a shared-lock-to-exclusive-lock upgrade. This makes the lifecycle dependency check and every operation that can create such a dependency one serial history: a writer that follows a lifecycle change must re-read the committed catalog and reject inactive or non-searchable fields instead of persisting a newly stale configuration.

Field access is a second, restrictive layer after use-case authorization. A tenant owner dynamically receives `WRITE` for every active field. Other active roles contribute only explicit access entries, missing entries resolve to `HIDDEN`, inactive memberships resolve entirely to `HIDDEN`, and multiple roles merge to the most permissive explicit access. This policy cannot create an HTTP or application authority. Business modules consume `EffectiveFieldAccessResolver` before exposing or accepting field values.

Keyword search is field-policy aware. Each object's field catalog exposes a fixed `searchCandidates` map; the application intersects it with the current active/searchable definitions and effective access, excluding every hidden or masked field. `SearchKeyword` supplies shared Unicode-safe bounds and blank semantics, while persistence adapters translate only the selected fixed candidates through `SqlLikePattern`. An empty candidate intersection becomes an explicit false predicate. The resulting OR group is always nested inside the repository's existing verified-tenant, data-scope, active/non-deleted predicate; ordinary customer and contact queries also retain their public-pool exclusion. Product and contract identifiers are compared through their normalized keys, while a receivable-plan keyword is parsed as an exact positive installment and invalid text becomes a false predicate. No request can provide a column or SQL expression.

Field layouts and saved views are scoped by tenant, verified member, and object type. Layouts reference only active fields and have bounded ordering, pinning, hiding, and widths. Layout reads intersect stored preferences with the current active catalog. Saved views store typed `fieldCode`, operator, bounded values, and an explicit per-condition browser-exposure flag validated against active searchable metadata; list and default-selection reads revalidate the filtering metadata and fail closed for stale conditions. Aggregate query adapters receive only the derived typed filter conditions, never the browser-exposure flag, and normalize saved values against the current field type before SQL translation, so database coercion cannot reinterpret malformed numeric, temporal, boolean, identifier, or choice input. They never store SQL, scripts, table names, or arbitrary query expressions. Each member has at most one default view per object.

Contract, invoice, receivable, and return-visit queries accept either a member-owned saved view or one bounded set of temporary typed conditions. The application rejects requests that combine both modes, revalidates field access and cross-aggregate relation targets for either source, and passes only fixed catalog columns and parameterized custom-value predicates to persistence before the existing tenant and data-scope predicates.

Embedded pages are tenant-managed client links, not server-side integrations. The domain accepts only HTTPS templates without user information or unknown placeholders, substitutes only `{recordId}`, and never performs a network request. Only active pages are rendered to ordinary readers; management writes remain versioned and require explicit capabilities.

## Customer aggregate boundary

`Customer` is the first business aggregate that consumes both authorization data scopes and customization metadata. It owns core details, deal and lock state, tags, addresses, collaborators, one optional parent, and typed custom-field values. A repository save updates the root with its optimistic-lock version and replaces the bounded child collections in the same command transaction. Reconstitution restores the named snapshot without events, and soft deletion uses only `CustomerStatus.DELETED`.

The four customer capabilities (`customers:read`, `customers:write`, `customers:delete`, and `customers:assign`) each resolve their own data scope. SQL predicates combine owner department visibility with explicit collaboration: `SELF` includes owned and collaborated records, department scopes expand through the active owner's membership, and `TENANT` remains tenant bounded. A `READ` collaborator never gains write access; delete and assignment use owner-scope visibility rather than collaboration. Cross-tenant misses and out-of-scope records have the same not-found result.

Field policy is applied after record visibility. Built-in and custom fields require explicit effective access for non-owner roles, masking occurs at the application output boundary, and only unmasked readable fields may drive saved-view, duplicate, name, owner, nearby, or tag predicates. A masked `deal_status`, `created_time`, or `updated_time` suppresses its exact time value. Customer repositories translate validated saved-view conditions into a fixed built-in column catalog or parameterized custom-value subqueries. No API accepts SQL, a column identifier, or an arbitrary expression. Persisted canonical strings are checked against their final representation: URL bounds apply after ASCII conversion, while NFKC-normalized unique reservation diagnostics use a non-indexed text column and uniqueness remains anchored by the SHA-256 key. Nearby, tag, summary, star, duplicate, and recursive hierarchy reads reuse the same tenant and visibility predicate so auxiliary queries cannot become record-existence or hierarchy-size oracles.

`crm_customer_guard` serializes hierarchy changes per tenant. Parent-bearing creates and parent updates lock the customization object guard before the hierarchy guard, then inspect the source subtree and target tree; opposing moves therefore observe one committed order and cannot form a cycle. The same write boundary rejects any attachment that would make the complete tree exceed 64 levels or 2,000 nodes, so the query-side recursive budget cannot be consumed by an otherwise valid hidden branch before visible nodes are reached. Every customer aggregate save holds the customization object guard so it cannot synchronize custom values against stale field metadata. Mutation mapping separately resolves visible parent IDs so a validated persisted parent is reflected without exposing an out-of-scope relation; collaborator collections are included only by assignment-authorized command mapping. Tags retain a binary-collated display value and persist a separate NFKC/lowercase `tag_key`; replacement, batch add/remove, per-customer uniqueness, and visible catalog grouping all use that same key. Custom unique values are normalized and reserved in a database unique key inside the aggregate transaction, while field uniqueness is immutable after creation, making the database authoritative under concurrent creates or updates.

## Customer business overview boundary

Customer overview is a fixed Customer-context query, not a cross-domain aggregate or reporting API. `CustomerBusinessOverviewService` resolves `customers:read` and exact Customer READ visibility inside its single read-only `REPEATABLE_READ` `QueryServiceTemplate` transaction; hidden, cross-tenant, pooled, and deleted customers fail before any source resolver or repository query runs. It then runs the seven fixed cards in that same snapshot. Each card separately intersects its own `*:read` authority, source READ scope, direct `customer_id`, lifecycle predicate, and required unmasked field policy. The source repositories retain their own typed customer-summary methods and fixed SQL; no generic repository, dynamic table catalog, controller composition, cache, or caller-defined grouping exists.

Only a recognized source `ACCESS_DENIED` becomes an opaque `UNAVAILABLE` card with no count, amount, or reason. Empty but authorized source data returns `AVAILABLE` with zero values, while unknown failures and tenant inconsistencies propagate normally. The public order is `CONTACT`, `OPEN_OPPORTUNITY`, `ACTIVE_CONTRACT`, `PENDING_INVOICE`, `ACTIVE_RECEIVABLE`, `ACTIVE_RECEIVABLE_PLAN`, and `RETURN_VISIT`; only the amount-bearing definitions expose `BigDecimal` totals. The matching Contact `customerId` drill-down proves Customer visibility and Contact's unmasked `customer` field before adding the tenant/scope/active contact SQL predicate, so customer visibility cannot widen Contact results.

## Bounded Customer CSV export boundary

Customer CSV export implements one synchronous Customer-only export rather than a generic data-migration or attachment API. Entry requires a scoped `customers:export` authority and the existing scoped `customers:read`; persistence applies both predicates for the same active member. Export scope is owner-derived and adds no collaborator union, while the read side retains ordinary Customer READ collaboration; satisfying one side can never replace the other. The query also retains ordinary active/non-pool Customer predicates and reuses the current keyword/name/owner/starred/saved-view validation. Export authority never widens ordinary read visibility.

Only `customer_id` and explicitly selected, current active, readable, unmasked scalar CUSTOMER fields enter the first format. Relations, members, departments, addresses, collections, FILE, attachments, registered identities and provenance remain excluded rather than being flattened into names, IDs, JSON or comma-separated cells. A dedicated typed Customer export projection stays in the Customer repository; there is no dynamic object/table/column registry or cross-domain export repository.

The application service obtains field metadata, policies, at most 5,001 candidate IDs and all selected cells inside one read-only `REPEATABLE_READ` transaction, emits at most 5,000 rows/50 fields/16 MiB in fixed `customer_id ASC` order, and completes the UTF-8 CSV before the HTTP body starts. The encoder uses stable field-code headers, typed locale-independent scalar encodings, RFC 4180 quoting and spreadsheet-formula hardening. Slow clients never hold the database snapshot, while the shared Customer/Contact/Lead bounded request admission slot remains held until body completion or cancellation so completed buffers cannot accumulate without bound. No export job, artifact, receipt, storage object, attachment file relation, public download or import contract is part of Customer CSV export; the complete frozen boundary is in the [Customer CSV export](architecture.md#bounded-customer-csv-export-boundary).

## Bounded Contact CSV export boundary

Contact CSV export implements a Contact-specific synchronous CSV route and a scoped `contacts:export` capability whose owner-derived predicate intersects the existing ordinary `contacts:read` predicate in SQL. Read collaboration can satisfy only the read side; it never widens export owner scope. Only active, non-pool Contacts enter the candidate set, and ContactPool capabilities or membership never substitute for either Contact authority.

The request retains Contact keyword, name, owner, customer, starred and caller-owned saved-view semantics. A Customer filter or saved-view Customer target requires the Contact `customer` field to be readable and unmasked plus current exact Customer visibility under `customers:read`; a parent-Contact target is rechecked under current Contact read visibility. Relationships may filter the query but never become CSV cells. The selected output remains limited to current active, readable, unmasked Contact scalar fields and a fixed `contact_id`; tags, addresses, owners, customers, parents, collaborators, pools, FILE and attachments are excluded.

Contact field metadata, policies, relationship targets, at most 5,001 candidate IDs, batched scalar cells and the completed bytes stay inside one read-only `REPEATABLE_READ` transaction. Output uses the same 5,000-row, 50-field and 16-MiB hard ceilings as Customer CSV export, fixed `contact_id ASC`, stable code headers, RFC 4180 quoting and formula hardening. Customer, Contact and Lead may share only format-level encoding and one process admission budget of one active export per member and four per replica; their requests, access resolvers, query projections and repositories remain separate. The complete implementation contract and non-goals are in the [Contact CSV export](architecture.md#bounded-contact-csv-export-boundary).

## Bounded Lead CSV export boundary

Lead CSV export adds one Lead-specific synchronous CSV route. `leads:export` resolves an owner-derived scope which is applied together with the independent ordinary `leads:read` visibility in the SQL candidate query; ordinary collaboration can satisfy only the read side and never widens export scope. Only the existing active or converted Lead lifecycle set is eligible, and the request retains the existing keyword, name, owner, subordinate-owner, personal-star, converted, saved-view, and temporary-condition semantics.

Customer and parent-Lead conditions remain predicates only: they require exact `EQ`/`IN` values, unmasked readable relationship fields, and current target visibility under the relevant Customer or Lead scope. The output is limited to `lead_id` plus selected active readable unmasked scalar Lead fields; tags, addresses, owner, relations, FILE values and attachments are deliberately not flattened. Lead field metadata, visibility, condition target checks, at most 5,001 IDs, 200-ID projections and the completed UTF-8 BOM document all remain inside one read-only `REPEATABLE_READ` transaction. The fixed result is `lead_id ASC`, 5,000 rows, 50 fields and 16 MiB at most; only encoding and the per-member/four-per-replica admission lease are shared with other completed CSV exports. No generic exporter, import flow, artifact, token, asynchronous job or file relation is introduced. See [Lead CSV export](architecture.md#bounded-lead-csv-export-boundary).

## Customer-pool boundary

`CustomerPool` is a versioned tenant aggregate. Its administrator, eligible-member, eligible-department, and automatic-release-rule collections are bounded typed relations. Pool membership is a separate current-state relation keyed by `(tenant, customer)`, so MySQL—not an application pre-check—enforces that one customer cannot occupy two pools. Claim history is append-only and supplies the daily limit boundary without relying on Redis.

Catalog visibility is resolved by tenant-scoped database predicates for administrators, eligible members, and eligible departments before results are returned; a persisted tenant-owner decision switches that query to all active pools. Its dedicated application read port selects only pool ID, name, status, and the current member's administrator marker, so administrator, eligibility, department, and rule collections are never hydrated for this endpoint. Pool creation locks `organization_tenant` before checking the 500 non-deleted-pool invariant, so concurrent creates cannot exceed the bound. Catalog reads defensively reject a 501st eligible root instead of truncating or hydrating an unbounded set. Customer counts are grouped in one aggregate query per catalog or management page. Pool customer mapping resolves parent IDs only through membership in the same accessible pool.

Releasing a customer first resolves the independent `customers:write` visibility, then acquires the `(tenant, CUSTOMER)` customization guard and pool row lock. The same transaction changes the customer to `IN_POOL`, clears ownership/collaboration, saves the aggregate by version, and inserts membership. Claim and assignment take the guard, pool lock, and membership lock in a fixed order, validate active tenant membership and pool access, restore one owner, remove membership, and append history. The pool lock serializes the daily-count check, while the membership key arbitrates competing pools. Transfer locks source and target pools in numeric ID order before changing membership rows. Deactivation and soft deletion require an empty pool.

Pool access widens record visibility only for `IN_POOL` customers in that pool; it does not grant ordinary customer visibility or field access. Pool queries hydrate customers through tenant-scoped membership predicates and then apply the same CUSTOMER field policy, masks, and typed saved-view validation as ordinary customer queries. Cross-tenant and inaccessible pool IDs both resolve as not found.

Automatic release is a bounded, repeatable application coordinator. Its human diagnostic entry point still receives a real `AuthenticatedCaller`; scheduled automation's system entry receives only the claimed tenant, fixed evaluation time and fence verification callback. A tenant-scoped database row stores the last scanned pool ID. Each invocation resumes after that cursor, wraps once, scans pages of at most 25 pools, and locks at most 50 distinct pools before persisting the new cursor in the same transaction. This prevents a busy low-ID pool from starving later pools across invocations and bounds the duration of the CUSTOMER customization guard. Active configuration is rechecked under the same database locks as manual release.

## Scheduling and automation boundary

Scheduled automation provides one composition-root wake-up surface with two deliberately different durability lanes. Scheduled automations use an application-owned closed kind catalog plus MySQL schedule/run rows; existing durable workers such as attachment workers register only a bounded pump and retain their own job identity, lease, deadline, effect evidence, readiness and recovery protocol. The common scheduler controls wake-up frequency, local lane isolation and shutdown, but it cannot interpret a file job, copy it into a generic run, or make a non-ready adapter ready.

The closed automation kinds include Customer/Contact pool automatic release and Work-task recurrence. Pool runs use the following ownership contract. A run's tenant comes only from an exact claimed row that is foreign-keyed to its durable schedule and `organization_tenant`; `AutomationExecutionContext` contains no actor, authority, human caller, connector principal or arbitrary payload. After claim, every business operation is explicitly tenant scoped. A pool write that can alter automatic release takes the owning object guard, then the derived schedule, then the pool root in one transaction; background execution consumes current active configuration without impersonating an administrator.

Due materialization and lease transitions use shared MySQL UTC. One short transaction preserves the schedule's due time, freezes a stable evaluation time, creates one unique occurrence and advances the next due; long downtime coalesces to one current occurrence rather than replaying every missed interval. Claim writes a boot-scoped owner and increasing fence. The owning object guard, schedule, exact run, existing pool cursor, pool roots and customer/contact roots are then locked in that order inside one `CommandServiceTemplate` transaction, so the business effect and run terminal state commit together. Retry reuses the same run and evaluation time; business timestamps use actual database commit time. These guarantees cover local MySQL effects only and do not claim exactly-once external delivery.

Automation has no public generic job API and accepts no caller-defined cron, script, condition tree or provider payload. Work-task recurrence owns its local-calendar rule and uses only a closed automation kind; notifications and timed announcements retain their own durable stores. `V65` provides the schedule/run schema and active-slot constraint; `V66` adds one global monotonic cadence-revision control row. Startup reconciliation holds that row, upgrades drifted schedules by generation, cancels their stale active runs and prevents an older mixed-version replica from claiming or rolling the control plane backward. Health is `NOT_READY` until the enabled revision is reconciled. Invalid scheduling configuration still fails only the automation lane closed, while terminal history is physically retained in bounded batches. Verification must cover multi-replica claims, revision drift and crash recovery; see the [testing guide](test-guide.md).

## Work recurrence and reliable-notification boundary

Work recurrence implements a Work-owned `WorkTaskSeries` rather than adding cron or rule payloads to automation. A series contains a bounded DAILY/WEEKLY/MONTHLY rule, IANA zone, fixed DST/month-end policy, task template, future nominal cursor, persisted resolved-UTC `next_due_at` cursor and generation; reads return that persisted UTC cursor rather than resolving the rule against the querying replica's tzdb. The REST adapter projects a caller-specific capability set rather than exposing creator identity as browser authorization: only `UPDATE`/`ACTIVATE`/`PAUSE`/`STOP` returned in `allowedActions` may be offered, and readiness or participant blockers are server calculated. Automation exposes only the closed `WORK_TASK_RECURRENCE` kind and a per-kind code policy. A claimed run supplies tenant and stable evaluation time; every effect locks tenant, recurrence control, schedule/run and series in that order, then either creates one ordinary `WorkTask` plus an immutable recurrence origin or advances the series as a bounded skip. Long downtime coalesces, and a generated-open database slot limits each series to one TODO/IN_PROGRESS generated task. V68 keeps a fixed control row in `RECONCILING` while it advances bounded, persisted cursor batches; this gates recurrence materialization/claim before the shared pump selects a run and only exposes the new policy after all active cursors are fenced. A higher revision can replace an interrupted target from its first batch, while unknown rule or zone data aborts the batch rather than ending a series. Editing, pausing or deleting a series affects only future occurrences and never rewrites an existing task. Creator or assignee authorization is re-resolved from current tenant grants without synthesizing a caller; a revoked requirement pauses the series, while invalid followers are omitted from only the new task snapshot. Work reminders provide task-local reminder steps and current-member in-app notifications; they do not add an automation kind, cron rule, external payload, or synthesized caller.

Task reminders are a second durable boundary. A task or series template can define at most eight BEFORE_DUE/AT_DUE/OVERDUE steps addressed only to the current assignee, creator or followers. A dedicated notification projection version changes with title, priority, assignee, followers, due time, task state or reminder policy. Exact reminder occurrences are claimed and fenced by their own store, then recheck the task under the task-root lock before atomically committing per-recipient in-app notifications. Escalation changes only notification kind and participant targets; it never changes task status, priority, assignee, Activity or worklist acknowledgement.

The in-app `Notification` is a tenant/member fact with its own idempotent read time. Inbox count and pagination apply current membership, recipient and Work-task visibility in SQL before slicing, so stale assignments or followers cannot use old notification rows to recover task IDs or titles. Worklist acknowledgement, notification read, task completion and delivery state remain independent.

External notification delivery uses a typed transactional outbox and its own bounded pump, not an after-commit event or an automation run. Readiness is preflighted before claiming a delivery and rechecked under admission locks with current membership, `notifications:read`, task visibility, member preference and a server-resolved profile endpoint before external I/O; `UNSUPPORTED` or a transient readiness gap leaves the row claimable for a later current adapter. First dispatch freezes the guarantee, original idempotency window, and a tenant/purpose-domain-separated HMAC endpoint binding plus key version; an endpoint or binding-key change turns a historic attempt `AMBIGUOUS` rather than reusing its key for a different command. Persisted effect certainty is conservative: `IDEMPOTENT_SEND(window)` may retry only the exact frozen command in its original window, and ambiguity survives retry exhaustion, deadline expiry, stale-task handling and admission recovery. `AT_MOST_ONCE_SEND` turns an uncertain post-dispatch result into `AMBIGUOUS` and does not redeliver automatically. The adapter receives only the remaining `min(lease, deadline)` budget after a settlement reserve and must respond to cancellation; a lost settlement is a lane failure. Delivery deadline/retention maintenance remains active when provider dispatch is disabled, while invalid or disabled deployments create no new EMAIL rows and terminal delivery retention is clamped to the notification-content retention ceiling. `ACCEPTED` means only provider acceptance, never mailbox arrival or human read. Production EMAIL remains disabled without current adapter evidence, and the dev/test `UserNotificationPort` logging path is explicitly outside this guarantee. See the [Work recurrence and notifications](architecture.md#work-recurrence-and-reliable-notification-boundary).

## OA announcement scheduling and reliable-notification integration

OA scheduled publication extends the OA announcement lifecycle with `SCHEDULED`, but keeps scheduling owned by OA. An exact one-shot publication occurrence stores `(tenant, announcement, publicationGeneration)`, database-UTC due/deadline, lease/fence, bounded retry and terminal reason. Because that row already owns the durable occurrence, its pump joins the common composition-root wake-up without adding an automation kind or generic payload. Schedule and cancel remain human commands. The due effect re-enters through `organization_tenant -> announcement -> occurrence`, rechecks the scheduling member's current active membership and `oa-announcements:write` through a tenant-scoped projection, and never fabricates a caller or falls back to the creator, owner, or worker identity.

Immediate and scheduled publication share one transaction-participating coordinator. It revalidates the frozen selectors, resolves at most 10,001 current active same-tenant recipients, rejects empty or over-limit expansion, then commits the published root, at most 10,000 immutable recipient rows, eligible typed EMAIL delivery rows, and occurrence settlement together. The scheduled instant is only the earliest eligible time; actual `publishedTime` is MySQL UTC from the successful transaction. Reschedule increases generation, cancel/delete and publish-now settle the old exact occurrence under the same lock order, and an expired or deterministically unauthorized occurrence returns the announcement to editable `DRAFT` with only a fixed management-safe reason.

OA notification delivery preserves `oa_announcement_recipient` and `oa_announcement_read_receipt` as the sole OA inbox/read truth; it does not create a duplicate Work `Notification`. The notification delivery ledger instead becomes a closed typed-source outbox. Existing rows are backfilled as `WORK_TASK_NOTIFICATION` without changing their digest, idempotency-key namespace, HMAC endpoint binding, guarantee or admission result. `OA_ANNOUNCEMENT_RECIPIENT` rows carry a composite foreign key to the exact recipient snapshot and use a source-specific unique key. An exhaustive application registry selects task-first or announcement-first admission; there is no generic source ID, table name, reflection hook, arbitrary payload map, or default tenant-wide branch.

OA EMAIL opt-in is a new default-off source preference, separate from the existing Work `emailEnabled` consent. Dispatch requires the immutable recipient snapshot, current `PUBLISHED` status, active membership, `notifications:read`, `oa-announcements:read`, the OA preference, a trusted current profile endpoint, and readiness for the exact fixed OA template. The template contains only announcement ID, bounded title and actual publication time; body, audience and the implemented OA announcement files attachment set never cross into the outbox or adapter. Withdrawal suppresses only rows that have not crossed the dispatch boundary. Any row with dispatch history or uncertain provider effect remains `AMBIGUOUS`, and `ACCEPTED` never writes an OA read receipt. The complete migration, lock, crash and compatibility oracle is frozen in the [OA scheduling and notifications](architecture.md#oa-announcement-scheduling-and-reliable-notification-integration).

## Activity and return-visit boundary

An `Activity` is a tenant-scoped timeline aggregate with one typed subject and at most 50 typed related records. It never owns business-record access: every command resolves the subject under that aggregate's current write range, while reads resolve it under its current read range. Related records are independently verified before storage, so an activity cannot be used to persist or reveal a hidden cross-domain relation. Only a caller's own active `FOLLOW_UP` entry is mutable; `SYSTEM` entries are append-only. Timeline paging is always anchored to one already-visible subject, which makes the repository total safe to expose.

`ReturnVisit` is a separately authorized, versioned aggregate. Its mandatory customer and optional contact/contract are tenant-scoped, and application logic confirms that every optional relation belongs to the same customer before saving. `RETURN_VISIT` built-in and custom fields use the shared field catalog and effective field policy; custom values and their database-enforced normalized unique reservations are replaced atomically with the root. The root also owns optional closed `visitForm` and `satisfaction` enums, stored with database checks and separately projected only through their current field access; form/satisfaction omission retains a historical value and explicit `null` clears it. An update retains an optional contact/contract relation when its request field is omitted and clears it only for an explicitly submitted `null`; its OpenAPI 3.1 contract declares every clearable field as nullable. Relationship IDs are removed at output time unless the caller can still read their owning aggregates, independently of return-visit visibility; each optional relation also carries `VISIBLE`, `HIDDEN`, or `EMPTY` so a hidden ID is never indistinguishable from no stored relation.

Return-visit list ordering follows the same closed static-or-custom model: `customSortFieldCode` may name only one active, non-built-in scalar RETURN_VISIT definition that the caller can currently read without masking. The application resolves it to a trusted definition ID and scalar type before persistence, and the repository uses that ID only in a parameterized correlated value expression with numeric casts where applicable.

Follow-up methods and templates are governed tenant configuration rather than caller-defined free text. Activity commands normalize and validate the selected method against the current catalog. The worklist is a read projection over nine independently authorized sources: customer activities, contacts, leads, opportunities, return visits, receivable-plan reminders, contract expiry, assigned pending approvals, and due Work tasks assigned to the current member. Its opaque `v3` cursor contains a position for every source; a stable global `(dueTime, kind, sourceId)` merge advances only records consumed by the current page. Bounded visibility scans may return an empty continuation page rather than advancing beyond an unknown earlier visible record. Decoder compatibility preserves all eight positions in legacy `v2` cursors and marks only the absent Work-task source exhausted, so an old pagination chain cannot gain an earlier new-source item mid-stream.

Worklist acknowledgement is a separate tenant/member-scoped write model keyed by kind, source ID, source version, and due time. Exact and category acknowledgement verify the caller's current projection before insert and never change a source aggregate. Category verification fails closed if the bounded scan cannot reach the end of the current worklist, rather than persisting a partial acknowledgement. A source version or due-time change therefore forms a new fingerprint and reappears. Worklist reads reapply record scope and required unmasked field access on every request; no cursor or stored acknowledgement carries authorization.

## Contact aggregate boundary

`Contact` follows the same tenant-scoped aggregate and field-policy boundary as `Customer`, but its root, children, stars, hierarchy guard, and pool relations are independent. The four contact capabilities resolve their own data scopes; collaborators can widen only contact read/write visibility according to their explicit access and never alter customer visibility. A customer link is a typed optional relation: contact create or update requires `customers:read` and a visible customer under that authority's data scope, while contact output resolves that link through the current customer predicate again. Thus a contact cannot be used to infer a cross-tenant or out-of-scope customer.

`ContactPool` repeats the customer-pool concurrency model with contact-specific membership and history tables. Pool operations use `contact-pools:*`, release additionally resolves `contacts:write`, and all entry, claim, assignment, deletion, transfer, daily-limit, cooldown, and automatic-release arbitration occurs under MySQL locks. It never shares pool membership rows with customers or grants ordinary contact/customer access outside the pool query boundary.

## Lead aggregate boundary

`Lead` is an independent tenant-scoped aggregate with its own field catalog, data scopes, children, stars, hierarchy, and saved views. Its visibility query includes both `ACTIVE` and `CONVERTED` records, while mutation behavior permits only `ACTIVE` records. Conversion acquires the lead/customization locks and runs the customer creation, contact creation, and lead finalization in one command transaction. Source values, including the owner that is copied to both projections, are copied only when the converter has unmasked read access to the corresponding lead field, while writes still require the target object field policy. The converted lead stores both typed associations; the relational constraint requires a customer and converted contact whenever `status=CONVERTED`, so the association remains recoverable after the conversion response is gone. The contact association is mapped only when the caller has `contacts:read` and the target is visible in that independent scope.

Public intake has a separate authentication boundary. The server generates a credential containing a canonical non-secret tenant locator, a case-sensitive opaque key ID, and a 256-bit secret for each tenant-local intake client, returns the complete credential only in the creation response, and persists only its hash. The locator selects a tenant-scoped lookup; only a matching active record and secret construct the verified caller, so public input never becomes a verified tenant or owner. Client creation requires its fixed owner to hold `leads:write`, a usable lead data scope, and write access to the mandatory `lead_name` and `owner_actor` fields; optional public fields remain subject to the owner's current field policy at submission time. The credential-format migration deactivates prior two-part credentials because their stored hashes cannot be transformed into a tenant locator; replacement clients must be provisioned. Each tenant has at most 100 active clients under the tenant serialization lock. A bounded, expiring source bucket atomically reserves an in-flight slot before lookup, releases it after a verified credential, commits it only after a failed credential, and cancels it when authentication infrastructure fails. An exhausted previously verified key is rejected before another lookup. Unknown credential fingerprints occupy a separate bounded pending cache and enter a tenant's verified-key cache only after secret verification, so forged formatted credentials cannot consume that tenant's verified-key slots. The parsed key ID is attached to the reservation before lookup, so client deactivation invalidates both settled and in-flight buckets. Verified-key buckets are partitioned per tenant and retain live quotas until expiry; when bounded tenant partition capacity is full, a new partition fails closed instead of evicting a live one. `X-Forwarded-For` is considered only when the direct peer is listed as a trusted proxy; otherwise the direct peer is the source and a gateway should handle proxy-aware rate limiting. Neither the secret nor a later copy of the raw key enters logs or responses. The in-process rate limiter is bounded admission control rather than a source of authorization truth.

After secret verification, intake authentication also requires the configured owner membership to remain active and grants only `leads:write` to the request security context. The application still resolves the owner's current data scope and field policy. A successful public submission returns only an acceptance receipt, never the internal lead, owner, or optimistic-lock identifiers.

## Opportunity aggregate boundary

`Opportunity` is a tenant-scoped versioned aggregate with a required customer, owner, pipeline/stage, expected close values, related contacts, one optional primary contact, collaborators, outcome, and typed OPPORTUNITY custom values. The primary contact must remain inside the aggregate's bounded contact set. `opportunities:read`, `:write`, `:delete`, and `:assign` each resolve an independent visibility predicate; collaboration widens only read/write according to its explicit level, while deletion and assignment stay owner scoped. Assignment validates the new active tenant member against the assigning grant's `SELF`, department, subtree, or tenant scope.

Opportunity list ordering is either a closed static field enum or one active, non-built-in scalar OPPORTUNITY field resolved by the application from `customSortFieldCode`. The two input modes are mutually exclusive. Before persistence, the application requires current readable, unmasked field access and converts custom metadata to only its definition ID and scalar type; the repository uses that trusted ID in a parameterized correlated value subquery, casting canonical INTEGER and DECIMAL values numerically. No request field code, column name, or expression can become SQL.

Customer and contact relationships never transfer record visibility. Every relationship write resolves the respective customer or contact read authority and checks the target through that domain's current data scope. Opportunity relation commands additionally require every selected Contact to retain the aggregate's customer ID; this runs for create, full customer replacement, contact replacement, and primary-contact change. Output intersects relation IDs with those predicates again, so later authorization changes fail closed. V96 stores that customer ID on every opportunity-contact relation and uses tenant/opportunity/customer and tenant/contact/customer composite foreign keys, making the invariant hold even if concurrent work changes a related root between application validation and persistence. The dedicated contact projection additionally applies the contact name field mask, while opportunity relation fields govern whether relationship values can be returned at all. Changing the primary contact first requires unmasked read access to the aggregate's contact collection, before either target visibility or set membership is evaluated. Typed saved-view customer and primary-contact predicates allow only exact bounded operators and validate every target before the query runs.

The aggregate remains readable after an outcome changes from `OPEN` to `WON`, `LOST`, or `INVALID`, but ordinary detail, owner, stage, contact, and collaborator mutations require it to be open. The outcome command is the explicit reopen path and clears outcome time and remark. Root updates use optimistic locking; relationship and custom-value children commit atomically with the root, and normalized custom uniqueness is finally arbitrated by a tenant-scoped MySQL key. Summary queries reuse the same record predicate and saved-view conditions, and require estimated amount to be unmasked readable.

## Opportunity pipeline catalog boundary

The Opportunity pipeline catalog contains tenant-owned, independently versioned `OpportunityPipeline` and `OpportunityPipelineStage` roots under non-data-scoped `opportunity-pipelines:read/manage` capabilities. Pipeline codes are permanently unique per tenant, stage codes per exact pipeline, and both retain Opportunity's bounded ASCII syntax with binary case-sensitive identity. Names, display order and stage probability are mutable current catalog facts; codes are immutable and never reused. New entries begin inactive, activation and last-active-stage rules execute under one tenant MySQL catalog guard, and deletion is a terminal soft state.

V85 backfills every existing exact `pipeline_code/stage_code` pair without rewriting it, aligns the Opportunity columns to `ascii_bin`, and adds a same-tenant pair foreign key. Fresh tenants receive the ordinary managed `direct` pipeline with `qualification` and `negotiation` stages. Existing valid history may exceed the new 100-pipeline/100-stage creation ceilings and remains paged and mutable, but cannot grow until its non-deleted count falls below the ceiling. Invalid legacy values that bypassed Opportunity fail the migration rather than being repaired heuristically.

Opportunity creation and any actual pair change acquire the OPPORTUNITY customization guard followed by the pipeline catalog guard and require both target rows to be active. A full update whose pair is binary-exactly unchanged may still edit other fields after that catalog entry is disabled or deleted, so deactivation prevents new assignment without freezing history. Ordinary Opportunity output remains code-only under customization field access; inactive/deleted codes stay available to saved views, reports and approval facts, and stage probability does not alter outcomes, summaries or forecasts.

Approval workflow stages remain a separate workflow-local namespace and state machine. Matching strings create no identity or foreign key, Opportunity stage changes do not advance workflows, and workflow actions do not mutate Opportunity pipeline or outcome. A future approval-gated sales-stage coordinator requires a separately frozen transaction, idempotency, lock-order and upgrade contract.

## Product catalog boundary

`ProductCategory` is a versioned tenant-owned tree node. Category mutation acquires one tenant catalog guard before reading or writing the tree, so opposing moves, normalized sibling-name uniqueness, the 16-level limit, and the 5,000-active-node bound are checked against a serialized catalog state. A category cannot be deleted while it has an active child or any non-deleted product dependency. All category keys and foreign keys include tenant identity, and deletion is a status transition rather than row removal.

`Product` is a versioned tenant-shared catalog aggregate with an active member owner, optional category, NFKC/lowercase code key, availability, price, and typed PRODUCT custom values. `products:read`, `:write`, `:delete`, and `:assign` require active membership but deliberately do not support record data scopes; the owner is responsibility metadata, not a visibility grant. Product writes acquire the PRODUCT customization guard before reading field definitions, then the catalog guard before saving. MySQL finally arbitrates active code and unique custom-field reservations, while reads apply current field access and masking after catalog visibility.

Product list ordering is either a closed static field enum or one active, non-built-in scalar PRODUCT field resolved by the application from `customSortFieldCode`. The two input modes are mutually exclusive. Before persistence, the application requires current readable, unmasked field access and converts custom metadata to only its definition ID and scalar type; the repository uses that trusted ID in a parameterized correlated value subquery, casting canonical INTEGER and DECIMAL values numerically. No request field code, column name, or expression can become SQL.

`OpportunityProductLine` is owned by the opportunity aggregate and contains a product snapshot, not a live product reference for display. Replacement locks the opportunity through its normal optimistic save path, requires unmasked write access to the OPPORTUNITY `products` relation, and requires unmasked PRODUCT reads for name, code, category, unit, and list price before exposing or freezing them. It acquires the product catalog guard before the transaction's first consistent read, then locks requested tenant products in numeric order, so product and category data cannot come from different repeatable-read snapshots. Every target must remain active and available. The request supplies a positive quantity and optional unit price; discount and line amount are calculated by the domain with fixed scales. At most 100 distinct product lines are stored, and later category/product edits, withdrawal, or soft deletion cannot rewrite their name, code, category, unit, list-price, sale-price, or amount history.

## Contract and invoice boundary

`Contract` is a versioned tenant-owned aggregate with independent read, write, delete, and assignment data scopes. Owner creation and replacement validate the target membership against the resolved assignment scope. Its customer is required; optional opportunity and contact relationships are independently visibility-checked and must belong to that customer, with tenant/relation/customer composite foreign keys preventing later relation moves from breaking the invariant. Every query and mutation response rechecks those relationship predicates and PRODUCT snapshot field access. The normal contract projection can hide collaborator information, so it is never a replacement baseline: the dedicated `GET /contracts/{id}/collaborators` requires `contracts:assign` with owner scope and returns the unmasked aggregate version, every persisted collaborator's actor ID, access level, nullable inclusive `effectiveUntil`, plus the caller's `OWNER`/`READ`/`WRITE`/`NONE` relationship state. A null expiry is unlimited; expired entries remain manageable in that baseline but are omitted from collaborator-derived query and mutation visibility. Product rows are aggregate-owned immutable snapshots built from locked available products after PRODUCT field-policy checks. The dedicated `GET`/`PUT /contracts/{id}/products` boundary is the complete product-relation baseline: both recheck readable unmasked contract/product snapshot fields, the replacement also requires `contracts:write`, locks the contract and catalog, recalculates totals from server-owned prices and quantities, and cannot lower the total beneath committed invoices, receipts, or active plans. Its narrow response includes only line identity/display snapshot, quantity, unit price, and version; it never exposes derived discounts or contract totals. Versioned `PATCH` requests, and the equivalent `PUT` requests, merge only submitted non-`null` fields; omitted and `null` values preserve stored data, so masked output cannot clear a relationship, sensitive attribute, or immutable-history field. Requests cannot provide catalog display values, discounts, subtotals, totals, tenant, or audit identity. Contract number uniqueness uses an NFKC/lowercase tenant key, both normalized length and every line/aggregate `DECIMAL(22,2)` amount are validated before persistence, and all dates are limited to MySQL's `1000-01-01` through `9999-12-31` range.

Contract batch owner transfer and batch delete are separate commands, not browser-side loops over single-record endpoints. Each accepts 1–100 unique `{contractId, version}` targets, resolves the caller's current assignment or deletion scope, locks the normalized ID order, and version-checks the complete target set before changing any row. Owner transfer also requires `owner_actor` write access and an active member within that scope. Batch delete preflights every invoice, receipt, and receivable-plan dependency before deleting a root or withdrawing attachments, so any stale target, scope denial, invalid owner, or dependency failure rolls the complete command back. Selected contract CSV export is a separate, non-mutating boundary: it intersects current `contracts:read` and `contracts:export` visibility, rejects unavailable or stale selected rows, derives a fixed field-policy-filtered column set server-side, formula-guards text cells, and returns one bounded, one-shot, `no-store` stream without relationships or custom fields.

`Invoice` is a versioned invoice-application aggregate with its own read, write, delete, assignment, and issue capabilities. Creation derives customer identity from a visible active contract while holding the contract row lock, but every response still suppresses that customer ID unless the caller independently retains `customers:read` visibility. Amount replacement locks that same contract before the invoice root and sums all other non-deleted invoice applications. Contract detail replacement also locks the root before checking the committed sum, rejects a customer change once any historical invoice exists, and rejects a total below that sum; deletion is rejected while a non-deleted invoice remains. The database repeats the customer invariant with a tenant/contract/customer composite foreign key. Requested and issued dates use the same MySQL-safe range as contracts. These rules serialize invoice creation, invoice amount changes, and contract reductions instead of relying on a preflight-only check.

Contract and invoice list ordering is either a closed static field enum or one active, non-built-in scalar CONTRACT or INVOICE field resolved by the application from `customSortFieldCode`; the two modes are mutually exclusive. The application requires current readable, unmasked access, then passes only the resolved definition ID, scalar type, and direction to the repository. Each repository owns its parameterized correlated custom-value expression and casts canonical INTEGER and DECIMAL values numerically, so request field code, column name, and expression cannot become SQL.

`InvoiceProfile` belongs to a customer but never grants customer visibility. Every list, create, update, and delete re-resolves `customers:read` for the target customer inside the actual read or write transaction; list and create do so before querying or inserting profiles, while update and delete do so after the tenant-scoped lookup and before mutation. Every repository operation requires an explicit tenant, and soft deletion is represented only by `InvoiceProfileStatus.DELETED`. A customer retains at most 100 active profiles; create holds the tenant INVOICE customization guard across visibility, count, and insert, and list queries use the same hard limit. Versioned profile and invoice edits obey the same non-`null` merge contract as contracts, so an omitted or masked sensitive field is retained rather than cleared. Personal profiles clear organization-only bank and tax fields. CONTRACT and INVOICE built-in fields are provisioned both by V38 for existing tenants and by organization bootstrap for every newly created tenant.

## Receivable boundary

`Receivable` and `ReceivablePlan` are separate tenant-scoped versioned aggregates with independent data-scoped capability families. Both derive customer identity from their contract, and persistence repeats this relation through tenant/contract/customer composite foreign keys. Their versioned `PATCH` and `PUT` updates merge only submitted non-`null` fields and retain omitted or `null` values, including a receipt's existing plan reference. Receipt create and amount replacement lock the visible active contract before the receipt root, then calculate the active receipt total and, when applicable, the active plan total; no receipt can exceed either its contract or plan. Plan create, batch create, and amount replacement take the same contract lock and prevent active planned totals above the contract. A plan becomes immutable after any receipt history, including soft-deleted receipts, so the historical allocation cannot be rewritten. Its received, remaining, and progress values are output projections computed from active receipts rather than stored counters. Contract total changes use the same lock and cannot fall below received amount; contracts with receipt or plan history cannot be deleted. RECEIVABLE approval facts are authoritative projections of the persisted receipt, and customer, contract, and plan IDs are omitted from approval results whenever their current relationship scope is absent. RECEIVABLE and RECEIVABLE_PLAN built-in fields are backfilled by V40 and provisioned for new tenants by organization bootstrap.

Receivable list ordering is either a closed static field enum or one active, non-built-in scalar RECEIVABLE field resolved by the application from `customSortFieldCode`; the two modes are mutually exclusive. The application requires current readable, unmasked access, then passes only the resolved definition ID, scalar type, and direction to the repository. The repository owns its parameterized correlated custom-value expression and casts canonical INTEGER and DECIMAL values numerically, so request field code, column name, and expression cannot become SQL.

After a receipt or return-visit query has admitted its final scoped records, output support may batch-project the latest tenant/object/subject approval state onto exactly those IDs. This read-only projection is separate from each aggregate lifecycle `status` and contains neither approval participants nor routing facts.

## Work-task boundary

Work introduces `WorkTask` as an independent tenant aggregate for manually created collaboration work. It does not reuse `ApprovalTask`, `StageTaskDefinition`, `Activity`, or `WorklistItemVO`, and it does not mirror their state. The root owns one current assignee, at most 50 followers, one optional CRM record reference, fixed priority and lifecycle, optional UTC due time, immutable first-start time, terminal times, an optimistic aggregate version, and a separate worklist-projection version. `DONE` and `CANCELLED` are terminal; `DELETED` is restricted soft deletion of a never-started task with no comment history.

`work-tasks:read`, `work-tasks:write`, and `work-tasks:manage` have no CRM data scope and do not imply one another. Read is only an entry permission: ordinary SQL visibility still requires the active caller to be creator, current assignee, or current follower, while tenant-wide visibility requires read plus manage. Participation, active membership, tenant, soft-delete, relationship, and fixed status/priority/due predicates are applied before both count and pagination. Cross-tenant and invisible IDs share not-found semantics. Structure, reassignment, follower replacement, cancellation, and deletion require the creator or a write-capable task manager; progress transitions require the current write-capable assignee. A visible write-capable participant may clear the task-owned CRM relationship, or set a non-null relationship only after the owning domain independently accepts the explicit new target's write scope and tenant.

V53 binds creator and assignee through tenant-composite membership foreign keys and supplies separate creator-list, assignee/due, and fixed-filter indexes. V56 adds the tenant/task/member follower relation, an independently versioned comment table, the paired checked polymorphic CRM reference, and relationship/comment indexes. Comments are never hydrated into the task aggregate; active rows page by tenant/task before output, while any historical comment row—including a soft-deleted one—blocks draft deletion. Every collaboration command locks the organization tenant guard before the task root and then the relevant follower/comment rows, rechecking active members after the guard. Relationship replacement validates only an explicit non-null replacement after locking the task; clearing or overwriting never resolves the previous target, preventing hidden-link existence probes and allowing stale or deleted links to be detached. A relationship-filter query performs its owning-domain read check inside the same `REPEATABLE_READ` snapshot as task count and page slicing. CRM relationship output batches references by owning type and reapplies read scope; access loss hides only the relationship fields. The relational state remains authoritative and no Redis state participates. Only title, priority, current assignee, due time, or lifecycle changes advance the worklist projection version; descriptions, followers, comments, and CRM links do not. The worklist projection consumes that dedicated version without changing the Work collaboration semantics.

The worklist projection exposes that version only through a lightweight repository projection owned by the Work-task boundary. The SQL requires the verified tenant, current actor as assignee, an active current membership, `TODO` or `IN_PROGRESS`, the requested due-time range, and the per-source `(dueTime, taskId)` cursor before its limit. The application additionally requires `worklist:read` and `work-tasks:read`. It does not call `BusinessRecordAccessGuard`, inspect the optional CRM link, hydrate followers/comments, or treat read+manage as an assignee. The resulting item points to `WORK_TASK` itself, and acknowledgement persists only the existing tenant/member/version/due fingerprint.

## Reporting boundary

Reports are application queries, not a tenant-wide read bypass or a materialized reporting store. Every read route first verifies `reports:read` and active membership. Commercial overview resolves all three source scopes for its combined overview; each trend or ranking resolves only the selected opportunity, contract, or receivable source. The three owning repositories expose fixed date-bucket and owner-ranking projections while reusing their existing tenant-scoped visibility predicates; there is no shared cross-object report repository or report-specific data scope.

The application requires unmasked access to every exposed value and every field that influences a bucket, predicate, date range, or ordering. It rejects the whole requested projection when the selected source or a required field cannot be read, preventing counts, monetary totals, dates, and rankings from becoming an oracle for hidden records. Trend queries accept only server-owned metric and granularity enums, caps trends at 120 buckets and ten years, and caps rankings at 100 rows and 366 days. Rankings use the fixed `amount DESC, count DESC, ownerActorId ASC` order. Field-policy reads and source aggregation run in the same read-only `REPEATABLE_READ` transaction; source-specific date indexes keep the bounded range predicates indexable.

Custom reporting uses a separate `ReportDefinition` aggregate and repository for tenant/member-owned metadata; it does not give that repository access to business tables. `reports:write` controls personal definition mutation but grants no record scope. Create/update take the same `(tenant, objectType)` database customization lock used by customization field lifecycle changes, so capacity, active-name uniqueness, dependency checks, and field deactivation cannot race into dangling configuration. The persisted JSON contains only bounded typed filters and COUNT/SUM descriptors and is decoded through `ReportDefinitionPOConverter` into a named aggregate snapshot; malformed stored JSON fails closed.

For catalog, detail, and every run, the application resolves the selected source capability, exact source visibility, and current active/searchable/readable/unmasked field intersection. A run passes a fully resolved `CustomReportQuery` to that source's repository. `MySqlCustomReportQuery` selects only hard-coded root columns or parameterized custom-value joins; request and stored strings never become SQL identifiers or expressions. It preserves the source's owner/department/collaborator visibility rules and expresses lifecycle as exact indexable sets (`ACTIVE` for opportunities and receivables; `ACTIVE`/`VOIDED` for contracts). Built-in ranges retain native DATE/DATETIME parameters, canonical custom DATE/DATETIME strings range directly over the field-value search index, and V51 adds missing `(tenant_id, status, time)` indexes for every supported root time field. Execution is bounded to 120 periods/ten years and a 501-row database probe, rejects results above 500 without truncation, and performs grouping and SUM/COUNT inside MySQL. Definition lookup, field-policy reads, and aggregation remain in one read-only `REPEATABLE_READ` snapshot.

Dashboard defaults are a separate current-member preference aggregate keyed by `(tenant, member)`. The aggregate stores a typed relative or bounded custom time range, a typed presentation data scope, and a bounded set from a server-defined display-module catalog, all under optimistic locking. A missing row is represented by the application defaults `CURRENT_MONTH`, `SELF`, and no hidden modules; reads do not create state. The current catalog contains only `CUSTOMER_CONTACT_REMINDER`, and hiding it is consumed solely by the presentation layer after the independently authorized overview response is assembled. The preference cannot carry source authorities, arbitrary predicates, member/department IDs, SQL, scripts, or arbitrary module names. In particular, its data-scope value is not the `RoleGrant` fact used by access resolvers.

Dashboard overview applies that preference in `DashboardOverviewServiceImpl` without introducing a cross-object repository. One injected UTC clock resolves the request window and automatic granularity once. `FixedReportQuerySupport` is shared with report trends and delegates each fixed metric to its owning repository; `DashboardVisibilityNarrower` intersects the independently resolved source visibility with the saved maximum and reloads the current active department/subtree when a tenant-wide source must be narrowed. Each card reads its required customization policy and aggregate in the same query-template snapshot. Its matching Top 10 ranking resolves the same narrowed source and date window but additionally requires the source owner field, so a hidden owner makes only that ranking opaque. Only known `ACCESS_DENIED` outcomes become opaque `UNAVAILABLE` cards or rankings; all other failures abort the overview. Totals are summed from the same zero-filled trend projection, preventing a separate summary query from drifting from card points.

The same response has a closed 16-value `dataSummary` layout for the reference workbench. It may only reuse facts already resolved in that same snapshot: the sales-brief sources provide new customers, new opportunities, opportunity amount, signed contracts, contract amount and receivable amount; a customer conversion aggregate independently resolves and narrows `customers:read`, requires unmasked deal-status and status fields, then counts visible active `WON` customers whose durable `deal_time` is in the window; the permission-filtered won-opportunity card supplies its count; a separately permission-checked opportunity outcome aggregate counts only visible active `LOST` records whose immutable `outcome_time` is in the dashboard window; the contract-expiration aggregate independently resolves and narrows `contracts:read`, requires unmasked end-date and status fields, then divides visible active contracts ending in the window at the request-fixed UTC as-of date; the customer follow-up aggregate independently requires active `activities:read`, resolves and narrows `customers:read`, requires unmasked customer created-time and status fields, then counts visible customers with a current-window direct active follow-up and new visible customers with no active direct follow-up; and the receivable-plan aggregate independently resolves and narrows `receivable-plans:read`, requires unmasked due-date, planned-amount and status fields, then sums visible active plans due in that window. Customer-pool entry now appends immutable release history in the same manual or automatic command transaction, while the existing claim history records both direct claims and assignments. The dashboard independently requires `customer-pools:read` and `customers:read`, limits both histories to the current accessible pool catalog, counts releases by former owner and only non-assigned claims by claimant, then narrows those actors with the dashboard customer scope. It never treats current customer-pool membership as release history and never widens a pool event through collaborator access or a UI preference. Historical events from before this durable source exists remain absent rather than guessed. `UNAVAILABLE` is therefore an intentional fail-closed state, not a zero or a client-computed omission.

The same snapshot also owns `customerContactReminder`, a fixed aggregate rather than a customer or activity list. It independently requires active `activities:read` membership, resolves and narrows `customers:read` visibility, and checks the unmasked customer created-time and status fields before `CustomerRepository` emits six counts. Five thresholds compare the maximum active direct `CUSTOMER/FOLLOW_UP` occurrence (or the customer creation time when none exists) against one request-fixed UTC timestamp. The overdue count evaluates only the newest active direct follow-up's past next-contact timestamp, so a subsequent customer follow-up clears an earlier overdue plan. Expected access denial yields no buckets; an inconsistent tenant or an unknown persistence failure remains a whole-overview failure. No activity content, customer ID, or mutable reminder state is exported.

`PerformanceTarget` is a separate versioned aggregate for one member, one calendar month, and the server-defined `ACTIVE_CONTRACT` measure. The migration enforces its tenant/member foreign keys and natural key, so target rows cannot be repurposed across tenants or double-created for a month. Target administration always rechecks the subject's active membership and uses an independent `dashboard-targets:read/write` authority; it neither accepts nor broadens data scope. `NavigationCatalog` exposes the `/administration/performance-targets` entry only when the same read authority resolves, while the browser's route guard remains a defense-in-depth check rather than a source of menu visibility. The dashboard may project the target only for the caller's effective `SELF` selection. It sums only the affected calendar-month rows and reuses the already authorized active-contract card for actual value, returning opaque `UNAVAILABLE` instead of attempting a department or tenant roll-up. No configured rows is an explicit `EMPTY` state, not a zero-valued target.

`DepartmentPerformanceTarget` is a distinct versioned aggregate rather than a member-target roll-up. It records one active department's explicit `ACTIVE_CONTRACT` amount for `YEAR/1`, `QUARTER/1..4`, or `MONTH/1..12`; the migration's `(tenant_id, department_id)` foreign key, unique period key, and service-layer active-department recheck prevent cross-tenant, duplicate, inactive, or deleted-subject changes. The `/batch` command accepts at most the complete 17-period calendar set, rejects duplicate period tuples, locks each existing natural key, and treats every supplied version as a mandatory optimistic baseline; inserts, replacements, and their output occur in the same command transaction, so a stale/deleted row or concurrent unique insert rolls the full batch back. `dashboard-targets:read/write` remains the management authority, but does not grant `organization:read`, report visibility, or a department dashboard projection. Annual, quarterly, and monthly values coexist as independently maintained management inputs; no client or server computes one from the others, and no actual/completion result is emitted until a future server-side department aggregate defines its own source visibility and field policy.

The member `POST /dashboard/performance-targets/import` and department `POST /dashboard/department-performance-targets/import` commands intentionally are not file-upload endpoints. A browser-owned CSV parser emits at most 200 generated typed rows and immediately discards the source; the server never accepts source bytes or attachment metadata. Each import command uses the write authority, normalizes and de-duplicates incoming natural tuples, sorts them to reduce lock inversion, rechecks every target subject in the tenant, locks each existing natural key, and creates or changes only its amount inside one `CommandServiceTemplate` transaction. Its concurrency model is explicit: unlike interactive edits there is no caller-supplied version baseline, so a complete valid import succeeds as one unit or any validation, subject, or unique-key failure rolls back all earlier rows. The safe completion projection carries only `importedCount` and cannot be mistaken for an authoritative dashboard aggregate.

## Marketing-form boundary

Marketing forms are tenant-managed versioned aggregates with ordered field children and an immutable `LEAD` or `CUSTOMER` target type. Their field codes reference the current target field catalog; field type and options are resolved from customization on each management or public read so stale metadata is not persisted. Configuration and target field lifecycle changes share the matching customization lock, and an active form is a database-checked dependency that blocks field deactivation. Activation builds the persisted owner's server-derived caller and invokes the matching Lead or Customer access resolver, so active membership, effective target write scope, and department-scope prerequisites are resolved rather than approximated from a non-null grant. It also requires current `WRITE` access to the target name, owner and every configured field. Every currently required public-safe scalar target field must be configured as required; unsafe relation, member, department and address fields remain unavailable in marketing forms. Public marketing file configuration provides FILE only for `LEAD` through a separate anonymous draft credential and structured candidate path without relaxing the scalar public-value whitelist; `CUSTOMER` forms reject FILE input.

Marketing-activity creation may coordinate the existing form aggregate through
`MarketingFormCreationCoordinator`: a nested `MarketingFormCreateRequest` is authenticated with
`marketing-forms:write`, validated under the matching LEAD or CUSTOMER customization lock, saved as INACTIVE, and linked
before the activity is persisted in the same outer command transaction. The create request accepts
either that nested form or an existing `marketingFormId`, never both. Updates reject nested form
creation instead of silently ignoring it. The form target must match the activity relation, so
`CONTACT` activities do not have a public form path and this is not a generic custom-object form
protocol.

`MarketingActivityType` is a server-owned closed catalog published through the activity
configuration-options query after current membership and `marketing-activities:read` validation.
New activity commands accept only its stable codes; the persistence column stays a string so a
pre-catalog type can remain unchanged during a later edit, but it cannot be introduced as a new
value. This makes the browser's dropdown an API-driven interaction rather than a client-side
copy of type labels, without forcing a lossy migration of historical activities.

`MarketingActivityBatchDeleteRequest` is a bounded command of 1–100 unique
`MarketingActivityVersionRequest` pairs. Its command template validates deletion authority and
all request-shape invariants, then locks the normalized ID order and version-checks the complete target set before
deleting any aggregate or withdrawing attachments. Root deletes and attachment withdrawals happen
only after that preflight in the same transaction, preserving all-or-nothing lifecycle semantics.

The anonymous identifier is a canonical tenant locator plus a random form key. It narrows a tenant-scoped repository lookup but grants no authenticated tenant context. Public submission deserialization is a strict whitelist: tenant, owner, status, unknown top-level properties, and unconfigured field codes are rejected, while public output omits internal owner, tenant, version, and success-message data. Rendering and submission revalidate current owner membership, capability, resolved target scope, and customization write policy, so later revocation fails closed without republishing. Submission locks the active form root in its outer command transaction, maps only the locked configuration, and invokes the matching reused Lead or Customer creation coordinator inside that transaction. It does not nest another `REQUIRES_NEW` command while retaining the form lock, preventing connection-pool starvation and making the created target record roll back with the coordinating command. Expected target-creation failures and wrapped internal failures therefore retain the sole client-facing `MARKETING_FORM_SUBMIT` error scene. Form update, status change, and deletion acquire the same root lock before the matching customization lock. This ordering makes a submission either finish before a concurrent change or observe the committed changed state; a completed deactivation cannot be followed by a target record created from its old snapshot. Deactivation remains available to form administrators even when the persisted owner has lost target write access, providing a fail-safe shutdown path.

The marketing submission ledger records the successful result as one immutable row in `crm_marketing_form_submission`, separate from the bounded `MarketingForm` aggregate. The public command appends the row only after the target coordinator returns the persisted Lead or Customer identity and while the same form-lock transaction is still active; either both the target record and ledger commit or neither does. Tenant-composite foreign keys bind the row to its form and the matching target record, separate target-scoped uniqueness prevents duplicate attribution, and `(tenant, form, idempotency key)` returns the same receipt only when its SHA-256 canonical request digest and form version match. A changed replay fails before it can consume a FILE capability or create another target record. No cascade removes historical success facts after a soft delete. The insert uses MySQL `UTC_TIMESTAMP(6)` and reloads that persisted value, so application-node clocks cannot change bucketing or ordering. The row contains only form identity/version, target type and record identity, idempotency key, request digest, and database UTC time—never submitted values, request metadata, IP addresses, or free-form attribution data.

Submission trends read only the tenant-scoped ledger after proving active membership, `marketing-forms:read`, and form ownership by tenant. They use fixed UTC DAY/WEEK/MONTH expressions, inclusive calendar inputs, zero-filled application buckets, a 120-bucket limit, and a ten-year limit; no target aggregate or target field is read. Visible-link pages additionally resolve the querying caller's current target-specific read visibility. Persistence applies current active target status plus SELF, department, subtree, tenant, and collaborator predicates inside a correlated SQL existence condition before both count and page slicing. Consequently historical accepted counts remain stable while soft-deleted, cross-tenant, or currently hidden target records neither occupy a page nor contribute to its total. INACTIVE and DELETED forms retain both management history queries.

Anonymous POST admission runs in the REST security chain before application or database work. The filter percent-decodes the application path once, validates its public-ID segment with `MarketingFormPublicId.parse`, regenerates the canonical identifier for the bucket key, and rejects malformed or non-canonical decoded paths. Direct submission, the `/submissions` alias, and equivalent percent-encoded path variants therefore share one quota. One atomic fixed-window decision consumes both a per-public-form and resolved-source quota. Both bucket maps are bounded, expire idle entries, and fail closed when full; defaults are 60 submissions per form per minute and 20 per source per minute. Source resolution shares the Lead trusted-proxy rules, so untrusted `X-Forwarded-For` values cannot create new buckets. This is per-replica local protection rather than a distributed global quota; multi-replica deployments use a gateway or shared limiter when global enforcement is required.

## OA form and request boundary

OA forms use `OA_REQUEST` as a stable customization and approval object type. New-tenant bootstrap and V52 existing-tenant backfill create the same five built-ins: writable `request_title`, plus server-derived `form_code`, `applicant_actor`, `applicant_department`, and `submitted_time`. A tenant may add governed custom fields through the existing customization APIs. `OaFormDefinition` persists only an NFKC/lowercase-normalized code, presentation metadata, one same-tenant OA approval reference, and ordered `(fieldCode, required, sortOrder)` children; field type, options, status, and role access are never copied.

Management reads require `oa-forms:read`, resolve current field metadata, omit HIDDEN fields, and never return deleted forms. The available catalog also requires `oa-requests:submit`, an active caller membership, an active matching approval whose initiator scope admits the member, and current `WRITE` access to every configured field. Missing, inactive, server-derived, or non-writable inputs fail closed; the file-field service handles FILE through its separate draft/value shape rather than scalar facts. `request_title` remains required; each form has at most 100 unique inputs and each tenant at most 200 non-deleted forms. The database repeats tenant identity through composite creator, approval, form, and field foreign keys and enforces live normalized-code uniqueness.

Create, update, status change, delete, customization field lifecycle mutation, and relevant approval-definition mutation share the `(tenant, OA_REQUEST)` customization guard. OA form commands acquire that guard before hydrating the root and its children, so a waiting transaction cannot retain a pre-guard `REPEATABLE_READ` snapshot. Approval-definition update and status change use the same guard-before-definition-row order; status preparation reads only the immutable object type outside its command transaction, then the transaction acquires the guard and reloads the definition with `FOR UPDATE`. Activation rechecks the active approval and requires every approval condition field to belong to the configured inputs or server facts. An active form blocks field deactivation, searchability removal, and approval deactivation or incompatible condition updates. Deactivation and later soft deletion deliberately avoid those dependency checks, preserving a fail-safe shutdown path even after referenced configuration becomes invalid.

OA requests use immutable `OaRequest` roots without drafts or post-submit field mutation. The submit command locks the tenant serialization row, rechecks active membership, acquires the OA customization guard, locks and reloads the active form, resolves current field metadata/access and the active approval, normalizes exact configured inputs, and derives applicant, department, form code, and submission time on the server. It inserts the request and unique-field reservations before invoking the internal `ApprovalSubmissionCoordinator`, whose fact supplier reads that persisted request; the resulting approval instance uses `oa:<requestId>` and is linked back before the single outer transaction commits. The path never calls the public `ApprovalService` command or opens a nested connection. A failure at any point rolls back both roots and all children. The `(tenant, applicant, idempotencyKey)` constraint is serialized before lookup, and a deterministic digest of form/version/normalized submission distinguishes equivalent retries from conflicting reuse.

OA visibility is a SQL union of applicant, historical task assignees, snapshotted managers, snapshotted watchers, or a current member with `oa-requests:manage`; `oa-requests:read` is only the entry capability. That predicate runs before count and page slicing. `BusinessRecordAccessGuard` uses the same adapter for approval details and mutations, so approval participation cannot bypass current active membership and OA entry authority. Both request and approval outputs apply current OA field hiding/masking, including top-level OA approval title/applicant/time projections; the request envelope does not duplicate raw server facts outside `values`. The request root stores no approval status mirror: approval remains the only status source. worklist sees the same approval task through its existing `APPROVAL_PENDING` source only when `request_title` remains readable without masking, while Work remains a separate object/API/capability boundary.

OA announcement keeps `OaAnnouncement` outside the customization/approval object model. Draft presentation and typed `TENANT`, `DEPARTMENT_SUBTREE`, or `MEMBER` selectors are versioned until publication; after publication content and selectors are immutable and only withdrawal followed by optional soft deletion is allowed. Publication acquires `organization_tenant` before the announcement root, rechecks the manager's active membership and every selector, expands active department descendants, intersects active same-tenant memberships, de-duplicates, and reads at most 10,001 candidate IDs. A result above 10,000 aborts the transaction. The root transition and chunked recipient inserts commit together, while concurrent publication is serialized by the root lock and optimistic version.

Inbox count, pagination, detail, and read writes require `oa-announcements:read` and apply published status, recipient snapshot, verified tenant, and current active membership in SQL. Organization changes never add recipient rows; suspension closes access even when a historical snapshot remains. A read command first takes a shared lock on the current membership and then on the visible announcement root, ordering it against concurrent suspension and withdrawal without exclusively serializing every recipient of a popular announcement. A unique-key insert-if-absent preserves and returns the first `(tenant, announcement, member)` UTC receipt under concurrent retries. Management pages map root-only `OaAnnouncementSummary` rows, and inbox page/detail/read-lock paths map root-only `OaAnnouncementInboxItem` rows; none queries department or member selector children. Full aggregate hydration remains isolated to managed detail and aggregate mutations. Management page/statistics and detail/statistics operations recheck active membership as the first read inside their `REPEATABLE_READ` query transaction, so authorization and all paged/count data share one snapshot. Static inbox/unread/receipt HTTP matchers require read authority before the broader write-only announcement matcher, while application guards independently repeat current membership and capability checks. Manager statistics batch only recipient and receipt counts. V55 repeats tenant identity through creator, selector, snapshot, and receipt foreign keys; V57 removes its redundant `deleted_time` mirror so `status=DELETED` is the only soft-deletion representation. Redis, worklist acknowledgements, Work tasks, outbox events, and external notification are not involved.

## Approval and stage workflow boundary

`ApprovalDefinition` is tenant-owned, versioned configuration over a stable `BusinessObjectType`. Its conditions reference only active searchable `FieldDefinition` codes and bounded typed values; no table, column, SQL, script, or arbitrary query expression enters the domain. Fixed members, active role assignments, manager fallback, and applicant-selected members resolve to at most 100 active tenant memberships, and normalized applicant-selected step keys cannot collide. Public routing facts are read from the persisted customer, contact, lead, opportunity, contract, invoice, or receivable inside the submission transaction. OA preview/submission instead enters through the form-bound OA request service and reads its just-persisted authoritative request; callers cannot use general approval submission to inject OA facts. A validated internal stage snapshot may override supported business values only after customization write authorization. A submission stores the definition version, normalized fact snapshot, submission-time manager set, step names and modes, and the final assignee route. Later definition status, managers, or metadata changes therefore cannot alter an existing `ApprovalInstance`.

`ApprovalInstance` owns at most 5,000 review tasks across the initial route and transfer history. `ALL` requires every assignee and rejects on the first rejection; `ANY` approves on the first approval and rejects only after all assignees reject; `SEQUENTIAL` activates one assignee at a time. `ONCE` skips an assignee who already approved an earlier step and rejects transfers back to such a member. Transfer checks total capacity before completing the original task, then appends a linked replacement to preserve the timeline. Every action locks the tenant-scoped root and uses root/task optimistic versions; persistence inserts replacements and updates only tasks whose state changed. A batch contains at most 50 unique instances, locks them in ID order, commits atomically, and returns typed all-or-none results. Approval lists and counts scan lightweight root references for business-record visibility; list pages then hydrate the final-page roots only to calculate caller-specific `allowedActions`. Receivable and return-visit projections first apply their own business visibility, then batch-read only the latest closed instance state for those already-admitted subject IDs; they never join tasks, people, routing facts, or action capabilities. Public instance and summary projections contain the display title, status, version, action capabilities and identity-free task timeline, never applicant/assignee identity, approval facts, business-object metadata, manager or watcher data. Detail and mutation behavior rechecks current business-record visibility; a client must use the returned capability rather than infer action eligibility from identity. Idempotency is unique per tenant and is accepted again only for the same definition, subject, object, and applicant.

`StageWorkflowDefinition` stores bounded stages, required field codes, tasks, applicability, and optional approval-definition references. For every gate, the union of stage-required and approval-condition fields is validated against the 100-field instance snapshot limit when the workflow is saved or activated and again when a referenced approval definition changes. Generated gate titles are bounded to the approval-instance title limit. Once any runtime record references a definition its stage configuration is immutable. A definition can soft-delete only when no `ACTIVE` or `AWAITING_APPROVAL` runtime record still uses it, preserving field and approval-definition dependencies until every run is terminal; it separately exposes only its domain-allowed next statuses when the caller has `CHANGE_STATUS`. `StageWorkflowRecord` binds only a stable business object type and numeric record ID. Every public read or write first reapplies that object's current customer, contact, lead, or opportunity data scope. Its canonical HTTP resource is `/api/v1/stage-workflow-records/{workflowRecordId}`; the projection includes the current stage, gate status, `allowedActions`, writable field codes, allowed task codes, structured ADDRESS current value and visible FILE metadata. A stage-origin `FileFieldDraft` additionally stores the exact tenant workflow-record scope; consuming it requires the same record, draft, field, complete non-expired staged file set and current customization write access. Snapshot assembly removes hidden fields and masks readable values for the current caller. An approval gate records its pending instance and resumes only after a terminal result; approval advances the stage, while rejection, cancellation, or withdrawal is consumed by one call that only restores `ACTIVE`. A later explicit advance captures fields and increments the attempt. Comments are tenant/record scoped, versioned, soft-deleted, exposed with caller-specific `canDelete`, and removable only by their author.

## Transactions and events

`CommandServiceTemplate` runs state changes through:

```text
validate -> prepare -> execute -> onSuccess
```

`CommandServiceTemplate` runs `validate` and `prepare` before opening an independent transaction for `execute` and `onSuccess`. Slow preparation such as password hashing therefore does not hold a database connection. A failure rolls that transaction back before it is converted to a `Result`, so an outer transaction is neither marked rollback-only nor surprised by `UnexpectedRollbackException`. Treat each command as its own atomic use case; do not use it when several commands must share one transaction. `QueryServiceTemplate` keeps the same validation/preparation boundary, then runs `execute` and `onSuccess` in an independent read-only `REPEATABLE_READ` transaction. Multi-query aggregate hydration therefore observes one database snapshot instead of mixing a root version with children from a later commit.

The relational database is the source of truth. `AfterCommitExecutor` delays cache writes, cache invalidation, and in-process event publication until commit. Events and cache actions use separate registrations so one callback failure cannot skip the other. Cache invalidation installs a short refill fence before eviction so a concurrent stale reader cannot repopulate a 30-minute entry after the write commits.

Events are already published from the post-commit phase. Use ordinary `@EventListener` consumers; an `@TransactionalEventListener(AFTER_COMMIT)` would be registered too late and will not receive this publication path.

Post-commit callbacks are not durable delivery. Use a transactional outbox when an event must survive process failure after commit.

Future call-start integration requires a typed command outbox and adapter command ledger with the [connector reliability contract](connector-integration.md#normalized-facts-and-durable-recovery). A core transport timeout retains the same command identity; it never creates a replacement command or infers whether the provider was called.

Redis is optional and implements an application output port. Cache keys include tenant identity. Selecting the no-op adapter must not change authorization or query correctness.

## Aggregate persistence

Aggregates own their state transitions. Persistence restores them through named snapshots and `reconstitute`, including identity, tenant, timestamps, and optimistic-lock version, without raising new domain events. Converters map persistence state explicitly; MapStruct is used only where mechanical mapping stays unambiguous. Customer, contact, and lead child collections are synchronized by natural key, so unchanged child rows retain their creation audit time and updates do not incur unconditional delete/reinsert cycles. Opportunity relationship, custom-value, and product-snapshot collections are replaced inside the same root transaction and never become visible independently of its optimistic-lock update.

Tenant-owned repository constraints (actor-global and control-plane exceptions remain explicit in their owning ports and tests):

- every tenant-owned business operation requires a non-null `TenantId`;
- update predicates include tenant and aggregate identity;
- MyBatis-Plus compares and increments the persisted `version`;
- zero updated rows produce a version conflict;
- save synchronizes and returns the same aggregate instance so pending events remain available;
- physical deletion is not part of the domain repository contract.

Soft-deletable aggregates use their own `status=DELETED`; for users this is `UserStatus.DELETED`. Deleted-user visibility is an explicit query policy, not a hidden SQL rewrite. For locally created users, the application command persists the user first, then uses that durable ID to create the global member profile, active current-tenant membership, and baseline member role in the same transaction. `ACTIVE` resumes the linked membership/profile; `INACTIVE`, `LOCKED`, and `DELETED` close them. Authorization cache invalidation is registered after the same successful commit, so an account lifecycle write cannot leave a usable member entry with stale tenant authority.

## Schema changes

Flyway is the only schema initializer. Migrations live in `infra/persistence/src/main/resources/db/migration` and use `V<version>__<description>.sql` names.

Do not add `schema.sql` or container initialization SQL, and do not edit an applied migration. Test migrations against an empty MySQL database and, when relevant, the previous schema. Keep migration columns, PO types, converter mappings, mapper XML, and aggregate reconstruction in the same change. Bounded JSON columns may persist validated metadata or preferences, but they are not an escape hatch for executable queries or unbounded domain state.

## Security boundaries

- Authenticated business APIs reject anonymous requests. Authentication, initial installation and public marketing forms use their dedicated, bounded admission paths described above; they do not grant general business access.
- Human HTTP routes and application use cases both check authorities; connector ingress uses an independent authenticated connector and has no CRM authorities.
- Authenticated tenant identity comes from verified human authentication or an exact active opaque connector registration, never ordinary request data. Public-form locators/capabilities and background claims resolve only their narrow operation context under the owning contract.
- A connector principal never represents an actor, member, owner, administrator, or external agent, and connection generation never participates in identity.
- Production cannot install the trusted-header development adapter.
- Request headers cannot grant authorities or administrator state.
- Passwords, reset tokens, authentication credentials, and full request objects must not be logged.
- Planned connector call paths also exclude complete or masked phone values from logs/metrics, and exclude phone HMACs, ciphertext metadata, recording references, provider URLs, raw callbacks, and provider exception messages from every ordinary observability path.
- Tenant-owned repository and cache calls without a tenant fail closed. Existing authentication, installation, actor-global, public-form, background-work and global reference/control-plane ports retain only their documented narrow exceptions; connector resolution remains limited to the two exact security projections above. All tenant-owned business access after resolution is tenant scoped.

See [configuration](configuration.md) for profile and security settings, and [development workflow](usage-guide.md) for adding behavior.

`ArchitectureBoundaryTest` uses ArchUnit bytecode analysis to enforce inward dependencies across application, domain, API, shared, and infrastructure classes. It also rejects controller-to-repository/VO coupling, public entity setters, missing core layers, and naming violations for Request, Response, VO, PO, and repository types.

## Controlled CRM CSV import boundary

`CrmImportDraft` is a tenant/member-owned, short-lived `LEAD|CONTACT|PRODUCT` state machine. It stores only lifecycle state, version, deadline and final imported-row count; the source is a single `IMPORT_DRAFT` controlled attachment relation, never a DTO blob or domain value. The target adapter requires fresh `files:write`, active membership, object-specific write authority and the original uploader on every attachment operation, so a generic attachment capability cannot be used to import CRM records or read another member's source. Only `text/csv` is admitted for this target; strict UTF-8 parsing, fixed server-defined columns, the 1 MiB/200-row limits and Jakarta field validation execute after clean publication. Product uses the fixed `name,code,categoryId,unit,listPrice,description,availability` columns. Preview projects only a count plus row number/stable code and no source value.

Confirmation locks tenant, import root and attachment relation in the shared attachment order, reparses the immutable available bytes, and invokes the existing Lead, Contact, or Product creation coordinator inside one `CommandServiceTemplate` transaction. Lead and Contact row validation, data-scope, field-policy, relation or unique-key failure rolls the entire import back. Product first normalizes each code and skips an existing active code or a repeated code in the same source; every remaining Product creation is transactional and any non-duplicate validation, scope, field-policy or relation failure rolls those creations back. A successful confirmation consumes the draft, records the actual created-row count, withdraws the source and schedules its ordinary controlled deletion; the same version may replay only the completion projection after a lost response. Withdrawal applies the same root lock and source cleanup. Unconfirmed source bytes and their derived error-report eligibility have a fixed seven-day retention: a bounded attachment-lane worker re-locks each due root, marks it `EXPIRED`, withdraws its private relation, and schedules exact byte reclamation. It retains only the non-sensitive lifecycle audit row; raw CSV bytes, file names, cells and failed raw requests are excluded from database payload columns, logs and public responses.

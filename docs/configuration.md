# Configuration reference

Runtime configuration lives in the repository-level `conf/` directory. The `start` module packages only `application.yml`, `application-dev.yml`, `application-prod.yml`, `banner.txt`, and `logback-spring.xml`. `application-test.yml` is available only on the test classpath; local overrides and credentials are excluded from release artifacts. Do not create a second configuration tree under `start/src/main/resources`.

## Profiles

| File | Purpose | Important behavior |
| --- | --- | --- |
| `conf/application.yml` | Defaults shared by every environment | Flyway enabled, Redis disabled, trusted headers disabled, health-only actuator exposure |
| `conf/application-dev.yml` | Local MySQL and optional Redis | Trusted headers remain disabled until explicitly enabled |
| `conf/application-test.yml` | MySQL Testcontainers integration tests | Trusted headers enabled for test requests, Redis disabled |
| `conf/application-prod.yml` | Production | Datasource variables required, trusted headers forced off, API documentation disabled by default |

No profile is selected implicitly. Start the application with one profile:

```bash
sh ./mvnw -f start/pom.xml spring-boot:run -Dspring-boot.run.profiles=dev
```

For a packaged application:

```bash
java -jar start/target/*-start.jar --spring.profiles.active=prod
```

Do not activate `dev` and `prod` together.

## Public lead intake

Public lead intake credentials are generated by the server as `tenantLocator.keyId.secret`. The locator is non-secret and only routes the lookup to a tenant-scoped query; the secret authenticates the request. The complete `apiKey` is returned only from client creation; retain it in a secret store because subsequent responses expose only the key ID and the database stores only a hash. The migration that introduces this form deactivates legacy two-part credentials: create replacement clients after deployment and distribute the returned credentials through a secret store.

| Property | Default | Purpose |
| --- | --- | --- |
| `atom.lead-intake.max-submissions-per-minute` | `60` | Per verified API-key submission limit |
| `atom.lead-intake.max-auth-attempts-per-minute` | `20` | Failed authentication attempt limit per resolved source |
| `atom.lead-intake.source-bucket-capacity` | `10000` | Maximum retained source buckets before new sources fail closed |
| `atom.lead-intake.source-bucket-ttl-seconds` | `120` | Idle source/key bucket retention, from 60 seconds through 60 minutes |
| `atom.lead-intake.pending-key-bucket-capacity` | `10000` | Maximum retained, pre-verification credential reservations; this cache never consumes verified-key capacity |
| `atom.lead-intake.verified-key-bucket-capacity-per-tenant` | `100` | Retained verified-key buckets for each tenant; it covers the 100 active-client tenant limit, and deactivation releases that client's bucket |
| `atom.lead-intake.verified-key-tenant-bucket-capacity` | `10000` | Retained tenant partitions; only expired partitions are removed, so a full cache rejects a new partition rather than resetting a live quota |
| `atom.lead-intake.behind-proxy` | `false` | Declares reverse-proxy deployment; startup warns when true without trusted proxy addresses |
| `atom.lead-intake.trusted-proxies` | empty | Comma-separated direct proxy IP literals allowed to supply `X-Forwarded-For` |

With the default empty trusted-proxy list, the direct peer address is the source and `X-Forwarded-For` is ignored. Set `atom.lead-intake.behind-proxy=true` in proxy deployments so a missing trusted-proxy list emits a startup warning. For a trusted direct peer, every `X-Forwarded-For` header line is combined in wire order and scanned from right to left; encountering a malformed hop immediately falls back to the direct peer instead of trusting any farther-left value. Authentication atomically reserves a source in-flight slot before any credential lookup; a verified credential releases that slot, a rejected credential converts it into a failed-attempt count, and an authentication-infrastructure exception cancels it without charging the source. An already exhausted, previously verified key is rejected before another lookup. A new credential fingerprint occupies only the independent pending cache until its secret verifies, and is promoted to the tenant's verified-key cache afterward; forged formatted credentials therefore cannot fill a tenant's verified-key capacity. Each tenant can retain at most 100 active intake clients; verified-key buckets are partitioned by tenant, and deactivating a client invalidates its local bucket so a replacement key can be admitted immediately. Partition capacity never evicts a tenant with a live window, preventing quota resets; a new partition fails closed until an existing one expires. Behind a reverse proxy, configure every direct trusted proxy IP (not an untrusted client-supplied header), or enforce source attempt limits at the gateway. The in-process limiter is local admission control, not a distributed quota service: with multiple application replicas, each replica has an independent quota. Use gateway or shared Redis-backed rate limiting when the deployment requires one global limit.

## Public marketing-form submission

Anonymous marketing-form POSTs consume both a per-public-form and per-source fixed-window quota before reaching controller, application, or persistence code. The public-ID segment is percent-decoded, parsed, and regenerated as a canonical bucket key, so the direct route, `/submissions` alias, and encoding variants cannot split one form's quota; malformed or non-canonical decoded paths are rejected. Both bucket maps are bounded, expired lazily, and reject new buckets when capacity is full instead of evicting a live quota. Source resolution reuses `atom.lead-intake.behind-proxy` and `atom.lead-intake.trusted-proxies`, so the direct peer remains authoritative unless it is explicitly trusted.

| Property | Default | Purpose |
| --- | --- | --- |
| `atom.marketing-form.max-submissions-per-minute` | `60` | Maximum anonymous POST attempts per public form in one minute |
| `atom.marketing-form.max-submissions-per-source-per-minute` | `20` | Maximum anonymous form POST attempts per resolved source in one minute |
| `atom.marketing-form.form-bucket-capacity` | `10000` | Maximum retained public-form buckets before new forms fail closed |
| `atom.marketing-form.source-bucket-capacity` | `10000` | Maximum retained source buckets before new sources fail closed |
| `atom.marketing-form.bucket-ttl-seconds` | `120` | Idle form/source bucket retention, from 60 seconds through 60 minutes |

The limiter is local to one application replica. Deployments requiring a global multi-replica quota must enforce it at a gateway or with a shared rate-limit service.

B19b successful-submission ledger, trend, and visible-link queries add no runtime property. Their date, bucket, page, and data-minimization bounds are fixed application contracts; the ledger uses the same MySQL datasource and Flyway lifecycle as the form and lead records, and its insert obtains time directly from MySQL `UTC_TIMESTAMP(6)`.

## Production settings

The `prod` profile requires datasource credentials, a stable authentication signing key, an HTTPS password-reset confirmation URL, and a production `UserNotificationPort`. Use [`.env.example`](../.env.example) as the complete runtime-variable inventory and follow the [deployment guide](deployment.md). Spring Boot does not read `.env` automatically; inject these values through the deployment platform or a container's `--env-file`.

After configuring these variables, run:

```bash
java -jar start/target/atom-crm-start.jar --spring.profiles.active=prod
```

Store production values in a secret manager or deployment platform. Do not commit passwords, tokens, private keys, or connection strings.

`LoggingUserNotificationAdapter` is for local development and tests. It is disabled in `prod` and never reports successful delivery. Production can use the bundled `SmtpUserNotificationAdapter`: set `ATOM_USER_NOTIFICATION_MAIL_ENABLED=true`, a valid `ATOM_USER_NOTIFICATION_MAIL_FROM`, and the standard `SPRING_MAIL_*` connection, TLS, authentication, and timeout settings. Missing sender configuration or a missing mail bean fails startup. Alternatively, leave that flag off and implement `application.port.out.UserNotificationPort` in `infra/external`; without either production adapter, startup still fails.

Welcome mail is an ordinary post-commit, asynchronous side effect. SMTP errors are logged by exception type without addresses, provider messages, or credentials; this is not an outbox-backed delivery guarantee. This adapter does not enable the separate work-notification EMAIL lane. Password-recovery mail has its own opt-in flag and sender in the authentication section below.

OpenAPI JSON and Swagger UI are disabled in `prod`. If they are required, set both SpringDoc variables to `true` and protect the routes at the gateway or in `SecurityConfig`.

## Redis

Redis is disabled by default:

```text
atom.redis.enabled=false
```

When disabled, `NoOpCacheService` satisfies the cache port and reads continue to use MySQL.

For local Redis:

```bash
docker compose up -d redis
```

Start the application with `ATOM_REDIS_ENABLED=true`, then use the standard Spring Data Redis variables for a remote server. Cache keys include tenant identity. Cache failure must not bypass authorization or database ownership checks.

## Enterprise-data adapter

Production has no bundled registry or commercial data source. With no deployment adapter and policy directory, `GET /api/v1/enterprise-data/capabilities` reports `ready=false`/`NOT_READY`, and query operations fail safely without affecting Customer APIs. A private adapter implements only the provider-neutral `EnterpriseDataSource` technical port. A deployment separately implements `EnterpriseDataReadPolicyResolver` to resolve the tenant-bound source kind, positive observation TTL and controlled `SEARCH_RESULT`/`DETAIL` attribution. Missing or disabled policy fails closed before any adapter capability or query call; ordinary requests cannot select credentials, accounts, connectors, endpoints, plans, usage permission or attribution text.

The planned Companies House/GLEIF production gate is frozen in [B23-O/2](B23-O-official-source-readiness.md): a private deployment must additionally prove organization qualification, versioned RA/type/schema and rights digests, shared-provider plus tenant quota admission, a positive readiness snapshot no longer than five minutes, and current-build three-layer conformance. Those are design requirements, not existing properties; do not add partial production flags that bypass the current disabled fallback. Until a real adapter and all evidence exist, production remains `NOT_READY`.

The deterministic synthetic adapter is restricted to `dev`/`test` and controlled by:

```text
atom.enterprise-data.synthetic.enabled=true
```

`application-dev.yml` and `application-test.yml` enable paired source and controlled-policy fixtures; `application-prod.yml` fixes them to `false`. The fixtures contain no real enterprise or person data. Even when the synthetic deployment policy permits broader fixture testing, the implemented B23a core publishes only `EPHEMERAL_ONLY`. Never use it to seed Customer records or as proof that a real source's license, attribution, retention, quota, organization-eligibility, or schema contract is ready.

## Planned file storage

B24-S defines the storage configuration evidence boundary, and B24a implements the `atom.files.*` properties plus disabled and secure-local composition beans. Production file capability must remain unavailable until a deployment supplies an opaque tenant binding policy plus a current adapter build that passes [B24-S](B24-S-storage-readiness.md). Ordinary requests may never select bucket, endpoint, region, root path, provider, account, credential, KMS key, encryption, retention or quota settings.

The first storage contract accepts only a single proxy stream of `1..67,108,864` bytes, uses full-object SHA-256, caps the adapter stream buffer at 64 KiB, and treats native single range as a separate operation. Multipart, resumable upload, presigned transfer, redirects and SDK auto-multipart are unsupported. A production policy must provide positive tenant/global ready and quarantine byte quotas, pending-intent and upload/download concurrency limits, free-capacity floors, process/global reserves, and an independent deletion control reserve; missing values leave the relevant operation `NOT_READY`.

An S3-like binding additionally proves a general-purpose bucket with steady enabled versioning, unique conditional PUT, non-null exact version IDs, checksum, exact-version read/range/delete and authoritative absence, public/ACL denial, encryption, expected owner, and governed Object Lock/replication/backup policy. A secure-local binding proves a dedicated non-webroot POSIX-like root, pre-provisioned shards, `SecureDirectoryStream`, `NOFOLLOW_LINKS`, `CREATE_NEW`, owner-only permissions, volume encryption, free reserve and current filesystem crash behavior. Node-local storage is dev/test-only unless multi-replica visibility, handle fencing and failover are separately proven. These are planned evidence fields, not permission to add partial production flags or secrets to YAML/logs.

## HTTP security

The default route policy is fail-closed:

- health is public;
- OpenAPI discovery is public only while its endpoints are enabled;
- user reads require `users:read`;
- user creation and updates require `users:write`;
- user deletion requires `users:delete`;
- organization bootstrap, membership requests, tenant lists, tenant-access checks, and region-reference reads use the non-delegable platform capabilities declared for those routes;
- tenant role administration separates `authorization:read`, `authorization:write`, and `authorization:assign`;
- navigation reads and preferences use `navigation:read` and `navigation:write`;
- field metadata, personal saved views, and embedded pages use their separate `fields:*`, `saved-views:*`, and `embedded-pages:*` capabilities;
- customer routes separate `customers:read`, `customers:write`, `customers:delete`, and `customers:assign`, each with its own tenant data scope;
- customer-pool routes separate `customer-pools:read`, `customer-pools:manage`, `customer-pools:release`, `customer-pools:claim`, `customer-pools:assign`, and `customer-pools:delete`; release additionally resolves the independent `customers:write` data scope in the application service;
- contact routes separately resolve `contacts:read`, `contacts:write`, `contacts:delete`, and `contacts:assign` data scopes; a customer link additionally requires `customers:read` in the application service;
- contact-pool routes use `contact-pools:read`, `contact-pools:manage`, `contact-pools:release`, `contact-pools:claim`, `contact-pools:assign`, and `contact-pools:delete`; release additionally resolves `contacts:write`;
- opportunity, product, approval, and workflow routes use their code-defined capability families and repeat record-scope checks in application services;
- contract routes separate `contracts:read`, `contracts:write`, `contracts:delete`, and `contracts:assign`; invoice routes separate `invoices:read`, `invoices:write`, `invoices:delete`, `invoices:assign`, and `invoices:issue`; both assignment capabilities constrain the target owner to their resolved data scope, while invoice profiles additionally recheck `customers:read`;
- unmatched API requests require authentication;
- all other unmatched routes are denied.

Human-facing application services repeat the authority check and derive `TenantId` from `AuthenticatedCaller`, so facade and non-HTTP human adapters follow the same policy. B22a connector ingress is a separate non-human boundary: it has no CRM authorities and follows the connector-registration resolution described below.

### Tenant identity and selection

For human APIs, tenant identity is established by the verified authentication principal and is passed explicitly through every use case. A request body, query parameter, or untrusted header cannot select a tenant. The dev/test trusted-header adapter described below is the sole human-authentication exception: it accepts both headers only when explicitly enabled and remains unavailable in `prod`.

### Browser password authentication

`/api/v1/authentication/password/login-options` accepts a tenant-scoped username and password, then returns a signed five-minute challenge plus only that user's active membership tenant choices. `/password/sessions` consumes the challenge and target membership to issue an eight-hour host-only `HttpOnly`, `SameSite=Strict` session cookie; it also issues a separate same-origin CSRF cookie. Every later cookie request rechecks the signature, user status, user aggregate version, and active target membership. Unsafe cookie-authenticated requests must echo the CSRF value in `X-Atom-CSRF`; a reset or user state/password mutation invalidates old sessions through the aggregate version. These public authentication routes are the narrow pre-tenant exception: they never make a request body or header a tenant identity for ordinary CRM use cases.

| Property / environment variable | Default | Purpose |
| --- | --- | --- |
| `atom.authentication.session-ttl` | `PT8H` | Signed browser session lifetime |
| `atom.authentication.login-challenge-ttl` | `PT5M` | Password-verified tenant-choice lifetime |
| `atom.authentication.password-reset-ttl` | `PT15M` | One-use reset-token lifetime |
| `ATOM_AUTHENTICATION_SIGNING_KEY` | empty outside `prod` | Canonical base64url HMAC key, at least 32 bytes; mandatory in `prod` |
| `atom.authentication.cookie-secure` | `false` | Must be `true` behind production HTTPS |
| `ATOM_AUTHENTICATION_PASSWORD_RESET_URL` | empty | Required absolute reset confirmation landing URL in `prod`; the server appends the encoded `token` query parameter |
| `ATOM_AUTHENTICATION_PASSWORD_RESET_MAIL_ENABLED` | `false` | Enables SMTP reset delivery when a `JavaMailSender` is configured |
| `ATOM_AUTHENTICATION_PASSWORD_RESET_MAIL_FROM` | empty | Required sending address when reset delivery is enabled |

Password reset stores only a SHA-256 digest of a one-use random token in Flyway table `authentication_password_reset_token`. The server returns a stable delivery-unavailable error when the delivery port is disabled or the reset URL is absent; it must not claim that a message was sent. Explicitly enabling SMTP recovery requires a configured `JavaMailSender`, otherwise startup fails. Never log or place passwords, browser-session values, login challenges, reset tokens, signing keys, SMTP credentials, or reset URLs containing tokens in diagnostic output.

### First-installation administrator

No initial administrator username, password, tenant identifier, or bootstrap secret is configured through YAML or environment variables. After Flyway has applied the schema and while no active login user has an active tenant-owner membership, an operator uses the public `/setup` page once to create the tenant 1 owner. The command uses the regular browser-session signing and cookie settings above, so production still requires `ATOM_AUTHENTICATION_SIGNING_KEY`, HTTPS with `atom.authentication.cookie-secure=true`, and the normal same-origin CSRF deployment. The installation marker is set atomically; migration repairs legacy marker rows that have tenant or role fixtures but no usable administrator, while an existing active owner keeps the bootstrap path closed.

B22a implements connector-specific bearer authentication for `/api/v1/connector-ingress/**`. The server-generated value is `connectorRef.keyId.secret`; the complete credential is returned only when a human administrator creates or rotates a connector, and only a SHA-256 verifier is stored. Its authenticated context contains only a globally unique opaque connector reference; the core resolves the current active registration to one immutable tenant binding before business access. A credential is authentication material, not an ordinary tenant header, and a request body cannot carry or override tenant, connector, actor, or authority. The current `/probe` route accepts no body and exists to verify this independent-process boundary; later normalized call-fact routes are not implemented.

| Property | Default | Purpose |
| --- | --- | --- |
| `atom.connector-ingress.max-requests-per-minute` | `600` | Accepted requests per verified connector in a fixed minute; rotation keys share the quota |
| `atom.connector-ingress.max-auth-failures-per-minute` | `20` | Invalid connector authentication attempts per resolved source in a fixed minute |
| `atom.connector-ingress.source-bucket-capacity` | `10000` | Maximum retained source buckets before new sources fail closed |
| `atom.connector-ingress.pending-credential-capacity` | `10000` | Maximum unverified credential fingerprints; they cannot create verified connector partitions |
| `atom.connector-ingress.verified-credential-capacity` | `10000` | Maximum locally retained verified connector partitions; the legacy property name is retained for compatibility |
| `atom.connector-ingress.bucket-ttl-seconds` | `120` | Idle bucket retention, constrained from 60 seconds through 60 minutes |

Connector source resolution reuses `atom.lead-intake.behind-proxy` and `atom.lead-intake.trusted-proxies`: an untrusted `X-Forwarded-For` never selects the source bucket. Source reservations happen before credential parsing, and pending credential fingerprints remain separate from verified connector partitions. A connector's active rotation keys enter one shared fixed-window counter only after secret verification. Credential or identity lookup failure returns `503`; a credential-lookup failure also cancels the source reservation rather than charging an invalid-secret attempt. Revoke removes only that key's verified membership without resetting the connector quota, while disable and retirement invalidate the connector partition after database commit. These limits are per application replica; deployments that need a global multi-replica quota must add a gateway or shared admission service. See [B22 section 12](../batch-B22.md#12-integration-principal-与-connector-tenant-解析设计闭合) and [B22a acceptance](acceptance/B22a.md).

B22-D additionally requires future production call deployments to configure a non-development envelope-key provider, deployment retention ceilings, and a versioned tenant call-data policy before a connector can become ready. The key provider must isolate tenant and purpose keys for address encryption, phone HMAC, recording-reference encryption, and recording-reference HMAC; key bytes and plaintext values never belong in YAML, environment-variable diagnostics, MySQL plaintext, or logs. A missing key provider/policy or a tenant duration above the deployment ceiling leaves calling unavailable; an adapter that cannot report controlled recording deletion specifically leaves recording unavailable while non-recorded calling may remain enabled. The deterministic dev/test key and retention fixtures must be rejected in `prod`. No such properties or adapters exist yet; [B22 section 14](../batch-B22.md#14-b22-d-敏感数据录音访问与保留设计闭合) is the implementation contract rather than a currently supported configuration surface.

B22-M further requires explicit production media-transfer limits before recording can become ready: normalized WAV/MP3 formats, maximum object and per-request bytes, open/idle/stream deadlines, active streams, private egress or PBX storage roots, redirect policy, and optional immutable single-range support. Human media access is a same-origin core proxy request that repeats authorization; no configuration may enable provider redirects, browser media tokens, arbitrary URL fetches, arbitrary filesystem reads, full-buffer adapters, shared caches, or a deterministic dev/test adapter in `prod`. Multi-replica global bandwidth/concurrency limits require a shared admission service or gateway but never replace application authorization. No such properties exist yet; [B22-M](spikes/B22-media-transfer.md) is the implementation contract and [B22-PM](B22-PM-pbx-media-contract.md) freezes the PBX stored-object/range/cancel/limit/delete-confirm conformance oracle.

Production retention values are deliberately not inferred from the test fixture. Deployments define the shortest necessary address, recording, interaction-metadata, audit, and adapter-journal periods, publish their backup retention, and run the retention sweep before a restored backup serves traffic. Shortening a tenant policy advances existing deadlines; lengthening applies only to new interactions. A recording becomes inaccessible at its deadline even while external deletion retries, and it cannot become `REMOVED` until the adapter confirms deletion.

B24 now exposes the frozen `atom.files.*` runtime surface, but no production adapter is enabled by default. `atom.files.enabled` and `atom.files.workers.enabled` default to `false`; the remaining prod policy has no readiness-producing default. It must explicitly provide `policy.max-file-bytes` (at most the first profile's 16 MiB), ready/quarantine/global reserve bytes, pending-intent and active upload/inspection/download limits, deletion control reserve, a positive `policy.local-free-floor-bytes`, upload/inspection/download deadlines, job lease/heartbeat/attempts, quarantine/tombstone retention, claim size `1..25`, storage profile/binding, detector/scanner profile, definition basis/freshness and allowlist revision. Secure-local samples its own current filesystem before construction, allocation and a never-used namespace write; the sample is only a fail-closed floor hint rather than a concurrent tenant-quota promise, so a later write failure still follows exact cleanup/reconciliation. Missing, non-positive, contradictory or expired values keep only the affected B24 operation/worker `NOT_READY`; they cannot prevent ordinary CRM startup or install a clean-by-default fallback.

B29a/c/d add no storage or scanner profile and inherit this gate. B29b implements `atom.files.public-marketing.enabled=false`, a 5-minute-to-2-hour `draft-ttl` (default `PT30M`), `max-files-per-draft=10`, `max-bytes-per-draft=33554432`, `max-active-drafts-per-form=100`, `max-requests-per-form-per-minute=120`, and `max-requests-per-source-per-minute=30`, all with the code ceilings frozen in [B29](../batch-B29.md). This gate controls only new anonymous FILE drafts/candidates. Invalid or disabled public configuration cannot stop scalar marketing submissions or internal files: scalar and public-FILE buckets are isolated, invalid FILE request limits reject only new draft/candidate admission, and existing credentialed content upload/status/withdraw routes use a fixed bounded fallback. Existing public drafts still expire, delete and release capacity. An upload intent and its first retention sweep are capped at the exact draft deadline. A B24-ready adapter never enables anonymous intake automatically; public intake also cannot make B24 ready. `/actuator/health/publicMarketingFile` reports only `DISABLED`, `CONFIG_INVALID`, `FILES_NOT_READY`, `RUNTIME_FAILURE`, or `READY`; `atom.public_marketing_file.lane_state{lane="public_marketing_file",state="..."}` exposes the same fixed five-state set. Neither surface includes tenant, form, draft, file, source, or exception values. Multi-replica global source quotas remain a gateway/shared-admission responsibility, while MySQL form/tenant/global capacity is authoritative.

## Scheduled automation

`atom.scheduling.enabled` defaults to `false`. `atom.scheduling.pulses-enabled` defaults to `true` and is the explicit deployment/test stop switch for every local scheduled wake-up; an enabled notification lane reports `DOWN/SCHEDULER_DISABLED` while it is off. B26a accepts only deployment-owned fixed cadence and limits: `pulse-delay` (1 s–5 min), each lane concurrency (1–16), monotonic `cadence-revision` (`B26A_V1` onward), `pool-cadence` (1 min–7 d), `pool-record-limit` (at most 1,000), recurrence cadence/record-limit (the same bounds), lease (1 s–30 min), deadline (1 min–7 d), attempts (1–20), retry backoff (1 s–6 h) and terminal retention (1–90 d). A deadline must exceed its lease and still contain one lease plus one retry backoff. Invalid B26 core values fail the scheduled-automation lane closed while ordinary CRM requests continue; invalid recurrence cadence/record-limit instead close only `WORK_TASK_RECURRENCE`, leaving Customer/Contact kinds eligible. Values outside the legal concurrency range never get silently truncated into a different active topology.

B27a adds `atom.work.recurrence.enabled` (default `true`), `policy-revision` (`B27A_Vn`, default `B27A_V1`), `tzdb-fingerprint` (default `AUTO`) and `reconciliation-delay` (default `PT5S`, bounded to 1 s–5 min). An invalid delay is never passed to Spring's scheduler: reconciliation uses the safe 5-second fallback and reports the recurrence lane `CONFIG_INVALID`. `AUTO` writes the current JDK tzdb evidence into the keyed control row and every replica must subsequently match it. A declared fingerprint must exactly match local runtime evidence. A newer policy revision first enters durable `RECONCILING`: V68 checkpoints bounded active-series cursor batches and publishes `READY` only after all cursors have been recomputed. A still newer revision safely replaces an interrupted target and restarts its bounded scan; unparseable persisted rules roll the batch back instead of terminating user series. During reconciliation no recurrence run is materialized or claimed, while DRAFT/PAUSED templates remain editable. An older revision or same-revision tzdb mismatch leaves only the recurrence lane not ready, so activation and materialization fail closed while ordinary Work task requests remain available. `automationScheduling` health exposes this fixed-cardinality recurrence readiness and is not `READY` during recurrence drift. Scheduling must also be enabled and B26's cadence control must be reconciled before a series can become `ACTIVE`.

B27b adds `atom.notifications.reminders.enabled` (default `true`), `pump-concurrency` (1–16, default `1`), `lease-duration` (1 second–30 minutes, default `PT2M`), `max-attempts` (1–20, default `5`), `retry-backoff` (1 second–6 hours, default `PT1M`), `retry-deadline` (1 minute–7 days, default `P1D`), `terminal-retention` (1–90 days, default `P14D`) and `notification-retention` (1–365 days, default `P90D`). The dedicated bounded pump never enables an external channel and is independent of B26 schedules. Notification retention, terminal-occurrence retention, and claim each run in their own short committed transaction, retaining the task → occurrence → notification mutation lock order. Claim/effect admission uses database UTC; a lease is capped at its hard deadline, and final emission repeats database-UTC lease/deadline predicates before it can commit a notification. Expired leases are recovered one locked row at a time, and failed effects enter `RETRY_WAIT` before becoming durable `DEAD/RETRY_EXHAUSTED` at the first exhausted attempt or deadline. Invalid values disable only the notification-reminder lane; `notificationReminders` reports `DOWN/CONFIG_INVALID`, `DOWN/SCHEDULER_DISABLED`, or `DOWN/RUNTIME_FAILURE` after a purge, claim, or unrecoverable recovery infrastructure failure, and returns to `READY` only after a successful reminder pump. Ordinary Work CRUD and inbox reads remain available. Every sweep deletes at most a fixed batch: notifications have an absolute configured retention ceiling; occurrence evidence is subsequently removed only when no notification references it and the task is terminal or its projection is stale, preserving exact current-projection idempotency. Provider-delivery, endpoint, preference, email, webhook, token, and credential properties do not exist in B27b.

B27c adds `atom.notifications.channels.email.enabled` (default `false`), `pump-concurrency` (1–16, default `1`), `lease-duration` (1 second–30 minutes, default `PT2M`), `dispatch-deadline` (1 second–30 minutes, default `PT30S`, and never longer than the lease), `settlement-reserve` (100 milliseconds–30 seconds, default `PT1S`, strictly shorter than the lease), `max-attempts` (1–20, default `5`), `retry-deadline` (1 minute–7 days, default `P1D`), `retry-backoff` (1 second–6 hours, default `PT1M`) and `terminal-retention` (1–365 days, default `P30D`). An enabled deployment must additionally pin nonblank `adapter-contract`, `adapter-build`, `binding-revision`, `active-endpoint-binding-key-version`, and a corresponding secret `endpoint-binding-keys` entry; contract/build/binding must exactly match the adapter's readiness evidence. Readiness has a strictly positive remaining TTL of at most five minutes. Dispatch receives only the remaining `min(leaseUntil, deadlineAt) - DB now - settlement-reserve` budget; insufficient budget skips provider I/O, and a provider call whose settlement is lost fails the lane. Terminal retention is bounded by `atom.work.task.reminders.notification-retention`, so a delivery tombstone cannot extend notification-content lifetime. Invalid EMAIL values close provider dispatch only: no new EMAIL row is created, but deadline/terminal-retention maintenance still runs so legacy rows cannot pin notification retention. `notificationDelivery` reports `DISABLED`, `CONFIG_INVALID`, `SCHEDULER_DISABLED`, or `RUNTIME_FAILURE`; `READY` means the local pump is healthy, never that an adapter is provider-ready or an email arrived. A production adapter must still supply a current operation readiness snapshot. No setting accepts endpoint, account, credential, provider URL, message body, arbitrary template, or public retry policy.

B28a implements `atom.oa.announcements.publication.enabled` (default `false`), `pump-concurrency` (1–16, default `1`), `lease-duration` (1 second–30 minutes, default `PT2M`), `max-attempts` (1–20, default `5`), `retry-backoff` (1 second–6 hours, default `PT1M`), `max-lateness` (1 minute–7 days, default `P1D`) and `terminal-retention` (1–90 days, default `P14D`). A schedule command is accepted only while this lane is enabled, valid, and the common pulse is available; disabling it later preserves existing durable occurrences without pretending they executed. Claim, lease, deadline and actual publication use database UTC. Invalid values close only scheduled publication; OA draft CRUD, immediate publication, inbox and read receipts remain available. `oaAnnouncementPublication` health reports only `DISABLED`, `CONFIG_INVALID`, `SCHEDULER_DISABLED`, `RUNTIME_FAILURE` or local `READY`.

B28b reuses the B27c EMAIL configuration and keyring, but evolves readiness into a closed per-template catalog. A Work row still requires the unchanged Work template revision; an OA row independently requires the fixed `B28B_OA_ANNOUNCEMENT_EMAIL_V1` revision. Supporting one never implies support for the other, so a Work-ready deployment can keep OA delivery not ready without regressing Work. Wildcard templates and tenant-provided content are invalid. `emailEnabled` remains the Work preference, while `oaAnnouncementEmailEnabled` is an independent default-off consent. Neither field carries an endpoint, provider or tenant. Enabling OA publication never enables EMAIL, and enabling EMAIL never makes an announcement schedule ready.

At startup an enabled valid replica reconciles its revision through the global MySQL control row. A larger revision increments every drifted schedule generation, cancels its old active runs and resets active schedules to an immediately coalescible due time. An older mixed-version replica cannot reverse that control row and reports `DOWN` with `state=NOT_READY`, `reason=REVISION_DRIFT`; a missing or unreconciled control plane is also `NOT_READY`. The `automationScheduling` contributor reports `DOWN` for this state or invalid configuration, while disabled scheduling remains explicit `UP/DISABLED`.

`atom.scheduling.pulses`, `atom.scheduling.pulse.duration`, `atom.scheduling.lane.active`, `atom.scheduling.lane.queued`, `atom.scheduling.lane.last.success.utc`, `atom.scheduling.automation.materialized`, `atom.scheduling.automation.runs`, `atom.scheduling.automation.due.lag`, `atom.scheduling.automation.affected`, `atom.scheduling.automation.last.success.utc`, `atom.scheduling.automation.run.state`, `atom.scheduling.automation.schedule.state`, `atom.work.recurrence.outcomes`, `atom.work.task.reminders` (`claimed`/`emitted`/`cancelled`/`dead`), `atom.oa.announcements.publication` (fixed `scheduled`/`claimed`/`published`/`cancelled`/`retry`/`dead`/`misfire` outcomes), `atom.notifications` (`unread`/`read`/`withdrawn`), and `atom.notifications.delivery` (fixed source/channel/lifecycle outcome) use only fixed lane/kind/source/outcome/status labels—never tenant, run, pool, series, record, actor, endpoint, provider, or exception values. Reminder, publication, inbox and delivery counters are recorded only after their owning transaction commits. These properties do not enable file storage or file workers; `atom.files.enabled` and `atom.files.workers.enabled` retain their independent readiness gates. There is no tenant-configurable cron, timezone, payload, script, callback URL or public automation endpoint.

Pinned-definition scanners must fence attempts to one engine/catalog generation. Managed-definition scanners must expose their distinct service/schema/update-channel evidence and require an explicit deployment policy accepting that weaker audit level; configuration may not populate a fake `latest` signature version. Scanner endpoints, paths, bucket/prefix, account/region, IAM/KMS, event bus, parser plugins and threat details stay private. Dev/test synthetic adapters must be impossible to enable in `prod`, accept no arbitrary URL/path, and contain no real customer or malicious files. Full readiness and conformance requirements are frozen in [B24-I](B24-I-content-inspection.md), while names, first profile, public media/size ceiling, worker policy and absence of production defaults are frozen in [B24-SPLIT](B24-SPLIT-implementation-boundaries.md).

The organization module can list the caller's active memberships and validate one `targetTenantId`. Those operations are data-only: they never replace `AuthenticatedCaller.tenantId`, mutate a security context, or issue a new credential. A target tenant in a membership request is likewise a destination to be reviewed, not a caller-selected execution tenant.

Region reference data is exposed separately at `/api/v1/reference/regions`. The bundled `RegionReferenceCatalog` returns no data by design; deployments that need regions provide a curated `@Primary RegionReferenceCatalog` adapter. It is not tenant-owned organization data and must not be populated from request headers, request bodies, or unreviewed imports.

### Trusted development headers

The development adapter accepts `X-Dev-User-Id` and `X-Dev-Tenant-Id`. Both values must be positive integers; authorities come from server configuration, not request headers.

Enable it locally:

```bash
ATOM_SECURITY_TRUSTED_HEADER_ENABLED=true \
  sh ./mvnw -f start/pom.xml spring-boot:run -Dspring-boot.run.profiles=dev
```

The adapter is disabled by default, requires `dev` or `test`, and refuses `prod`. The `dev` profile binds to `127.0.0.1` unless `SERVER_ADDRESS` is deliberately overridden. Never forward these headers from an internet-facing proxy.

### Production authentication

The built-in password/session authentication described above supports production with its required signing key, HTTPS, and current-user/membership checks. An alternative identity-provider adapter must verify real credentials, including signatures, issuer, audience, expiry, and required claims. Map the verified subject and tenant claim to the infrastructure principal, retain only code-defined non-tenant platform capabilities from the credential, and merge tenant-assignable capabilities from `TenantAuthorityResolver`. The effective catalog includes `users:*`, `organization:*`, `authorization:*`, `navigation:*`, `fields:*`, `saved-views:*`, `embedded-pages:*`, `customers:*`, `customer-pools:*`, `contacts:*`, and `contact-pools:*`; do not treat unknown strings as authorities. Let `AuthenticatedCallerMapper` create the API context, and never construct it from request JSON or arbitrary client headers.

Customer/Contact pool automatic release is implemented only through the fixed B26a schedule/run ledger described above. Its human diagnostic entry point still requires a verified caller; its background handler receives only the tenant/fence context from the claimed durable row, uses its own persisted cursor, queries at most 25 pools per page and locks at most 50 distinct pools. Do not fabricate a system caller, derive tenant from a job payload, or treat an arbitrary `@Scheduled` method as distributed ownership. Production remains disabled until an explicit valid deployment policy is supplied, and B24 file-worker enablement remains a separate gate.

### Password hashing

`infra/security` supplies a replaceable BCrypt adapter. The `atom.security.password.bcrypt-strength` property defaults to `12`. The domain receives only a `PasswordHash`; plaintext is not stored in the aggregate or persistence object.

## MyBatis-Plus

Mapper XML is loaded from `classpath*:mapper/**/*.xml`. Underscore-to-camel-case mapping is enabled and second-level cache is disabled. Queries and updates include `tenant_id`; `version` is checked by the optimistic-lock interceptor; pagination is the last MyBatis-Plus inner interceptor. Validated field options, member layouts, saved-view conditions, and customer custom values use bounded JSON columns, but no raw SQL or executable query representation is persisted. Customer saved-view predicates are generated only from a fixed built-in catalog or parameterized field-value predicates. The project does not use MyBatis logical delete.

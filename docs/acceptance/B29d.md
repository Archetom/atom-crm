# B29d 验收记录：OA 申请协作附件与审批终态冻结

## 实现范围

- `OA_REQUEST` 是 B24 封闭附件目标，复用 `/api/v1/attachment-targets/oa-request/{requestId}/attachments`；普通协作关系不带 `fieldCode`，不会写入 OA 提交 facts、submission digest、审批路由或 FILE snapshot。
- 上传、状态、撤回与下载先锁定 tenant root，再以 `FOR SHARE` 当前读复核 active membership，避免 MySQL `REPEATABLE_READ` 在锁前一致性读保留旧会员快照。写入还要求 `files:write`、`oa-requests:read`、`oa-requests:collaborate`、当前申请可见性与 `PENDING`。可协作人仅限申请人、当前 `PENDING` 审批任务 assignee 和提交时持久化的实例 manager；历史 assignee、watcher 和仅有 `oa-requests:manage` 的成员仍可按原申请可见性读取，却不能写。
- 读取和下载继续叠加 `files:read` 与原 OA 申请参与者/tenant-manager 可见性。终态后只保留 `AVAILABLE` 附件的读取，所有 intent、上传、状态和撤回均失败关闭。
- OA target 的关系锁顺序是 `approval_instance -> oa_request -> attachment relation/file`。锁定审批根后的任务水合也使用 `FOR UPDATE` 当前读，因此在锁前 OA 可见性建立的 MySQL `REPEATABLE_READ` ReadView 不会保留历史 assignee。审批 action、排序后的 batch action、withdraw 与 cancel 在内存终态变更后、实例持久化前锁定申请，撤回全部 non-`AVAILABLE` relation 并登记已有 B24 deletion/retention work；其余 `AVAILABLE` relation 由不可变终态冻结。worker 用相同顺序重检终态，不能由旧 job 发布 cutoff 候选。
- `V84__add_oa_request_collaboration_attachment.sql` 为 `crm_attachment_relation` 增加 `oa_request_id`、same-tenant 复合 FK、root/state 索引及 exact-one target CHECK；`crm_oa_request_file_value` 和 approval FILE snapshot 表未改动。

- `OaRequestAttachmentTerminalCoordinatorTest`：仅 OA 终态进入 cutoff，`PENDING` 不触碰关系。
- `AttachmentParentLifecycleImplTest`：cutoff 只关闭未就绪 candidate，已 `AVAILABLE` relation 保持冻结集合。
- `FlywayMigrationManifestTest`：迁移连续至 V84。

# B27c 验收记录：外部通知可靠投递内核

## 范围

B27c 为 B27b 已提交的 Work 站内通知增加可选、仅 EMAIL 的 transactional delivery outbox。它不引入 public send/retry API、任意收件人或地址、provider credential、HTML/template payload、webhook/SMS/IM/push，且不改变任务、工作台确认、站内已读或 reminder occurrence 终态。

## 已实现边界

- `V71__create_notification_delivery_outbox.sql` 增加 tenant/member typed EMAIL preference（缺失即 OFF）及 `crm_notification_delivery`，`V72` 增加首次 dispatch 冻结的 digest 列，`V73` 将其升级为 tenant/purpose-domain-separated keyed-HMAC binding digest/version 并新增持久化 effect certainty。每个 `(tenant, notification, EMAIL)` 只有一行；行只保存固定 template revision、canonical payload/endpoint digest/version、certainty、状态、attempt、deadline、lease/fence 和 safe reason，绝不保存 plaintext endpoint、provider request/response、credential 或异常正文。
- reminder effect 在同一 MySQL 事务中先保存唯一 `Notification`；仅在 EMAIL deployment 可 dispatch 且成员当时 opt-in 时才创建其唯一 `READY` delivery。事务失败不会留下单独 inbox 或 outbox 半事实；通道关闭或配置非法时仍保留站内通知，且 delivery maintenance 独立执行。
- delivery worker 独立于 B26 run 和 reminder occurrence，先预检 adapter readiness 后才使用 MySQL UTC 短事务 claim；`UNSUPPORTED` 或短暂 not-ready 不会 claim 或终态化行。effect transaction 固定按 `task -> notification -> delivery` 加锁，并重新验证开放任务、当前 notification projection、当前参与关系、active membership、`notifications:read`、`work-tasks:read`、opt-in、服务端 member-profile EMAIL endpoint 与 adapter readiness。尚未跨 dispatch boundary 的缺失交集提交 `SUPPRESSED`、零 provider call；已有 guarantee/history 的行转为 `AMBIGUOUS`，不会抹掉未知 effect。抑制指标仅在该事务成功提交后记录。
- `NotificationChannelAdapter` registry 只允许 `EMAIL`，readiness 绑定 channel、deployment-pinned contract/build/binding、guarantee、fixed template revision 和最长五分钟的短正 TTL。默认 `DisabledEmailNotificationChannelAdapter` 为 `UNSUPPORTED`；现有 `LoggingUserNotificationAdapter` 不在 registry 内，也不会声明 ready 或消费 delivery。
- 第一次 `DISPATCHING` 冻结 guarantee、idempotency window 和 HMAC endpoint digest/version。`IDEMPOTENT_SEND(window)` 只以同一 delivery ID、payload/endpoint digest 和稳定 key 在原 window 内恢复，包括 ambiguous effect；effect certainty 一旦为 ambiguous，窗口、deadline、尝试耗尽、任务变更或 admission recovery 都保守结算 `AMBIGUOUS`，不能写为 `DEAD`。明确无 provider effect 才可 `DEAD`。`AT_MOST_ONCE_SEND` 的 retryable 或 ambiguous effect 都直接结算 `AMBIGUOUS`，绝不自动重投。adapter 的实际预算是扣除 settlement reserve 后的 `min(leaseUntil, deadlineAt) - DB now`，预算不足不调用；provider 调用后的 settlement 缺失令 lane 失败。超时取消后按 guarantee 结算。`ACCEPTED` 仅代表 adapter/provider 明确受理，从不映射为到达、阅读、打开或点击。
- task mutation 在持有 task root 后只 suppress 尚未进入 dispatch boundary 的过时/撤回 delivery；admission 已提交后不会伪称能够撤回已开始的 provider effect。终态 rows 以有界批量物理清理，deadline 回收与清理即使 provider dispatch 关闭或配置非法也会运行；terminal delivery retention 被限制为不长于 notification content retention，避免父 notification 被运行账本延长。deadline 和任务变更返回按 `SUPPRESSED`/`AMBIGUOUS`/`DEAD` 拆分的 outcome，指标仅在事务成功提交后以固定 `channel=email` 与 outcome 标签记录。

## API 与运行配置

- `GET /api/v1/notifications/preferences`
- `PUT /api/v1/notifications/preferences`，唯一字段为 `emailEnabled`；调用者只能修改自己，不能提交 endpoint、provider、account、tenant 或其它 recipient。
- `atom.notifications.channels.email.enabled` 默认 `false`；另有 bounded `pump-concurrency`、`lease-duration`、`dispatch-deadline`、`settlement-reserve`、`max-attempts`、`retry-deadline`、`retry-backoff`、`terminal-retention`、部署固定的 `adapter-contract`/`adapter-build`/`binding-revision`，以及 secret `active-endpoint-binding-key-version`/`endpoint-binding-keys` keyring。`dispatch-deadline` 为 1 秒至 30 分钟且不超过 lease，实际调用还会扣除 settlement reserve；terminal retention 不得大于 notification retention。`notificationDelivery` health 只报告 `DISABLED`、`CONFIG_INVALID`、`SCHEDULER_DISABLED`、`RUNTIME_FAILURE` 或 lane `READY`，不将其解释成 provider ready 或邮箱送达。

## 验证

- `NotificationDeliveryPumpTest` 使用 synthetic adapter seam，证明 readiness `UNSUPPORTED` 不 claim、task-first admission 后才产生 provider call、稳定 idempotency key/HMAC binding version 被传递、endpoint 漂移与 dispatch timeout 均不会重投不再精确的 command、实际 dispatch budget 为 lease/deadline 的余额且 settlement 丢失会失败，opt-out 在 adapter 前按 dispatch history 正确结算。
- `NotificationDeliveryStoreRepositoryImplTest` 覆盖 frozen guarantee/window/HMAC endpoint digest、ambiguous idempotent retry、at-most-once terminal、tenant-scoped settlement、deadline lease recovery 与分类 deadline outcome。`WorkTaskReminderIntegrationTest` 在真实 MySQL/Testcontainers 中覆盖 deadline crash/backoff 不会违反 `deadline_at > available_at`、已歧义记录不会因 deadline 或 admission recovery 降级为 `DEAD`、真正的 preference `SecurityFilterChain` 授权、禁用 channel 不创建新 delivery 且仍回收历史 deadline 行，以及 outstanding delivery 不会阻塞 B27b retention pump。
- `CI=true sh ./mvnw test` 仍是 schema、SQL lock/fence 与 Flyway 的完整 MySQL gate；没有真实 provider adapter、endpoint、credential 或 production readiness 被该内核测试启用。

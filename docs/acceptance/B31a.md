# B31a acceptance: permission-aware bounded Contact CSV export

## Implemented scope

- `POST /api/v1/contacts/export/csv` requires `contacts:export` at the security route and independently resolves owner-derived `contacts:export` scope plus ordinary `contacts:read` visibility inside the application query transaction.
- `ContactExportQuery` preserves both predicates. The Contact repository applies their SQL intersection while retaining active/non-pool lifecycle, keyword/name/owner/customer/starred/current-member saved-view filters, relationship-target checks, and `contact_id ASC` order.
- The export accepts 1–50 ordered unique field codes and rejects unknown, inactive, hidden, masked, duplicate, relation, collection, FILE, or other unsupported fields. It projects only fixed scalar Contact columns and parameterized custom scalar values.
- Customer filters and saved-view Customer targets require unmasked Contact `customer`, current `customers:read`, and exact Customer visibility; saved-view parent targets require current Contact read visibility. Relation IDs never become CSV cells.
- The service probes at most 5,001 IDs, reads output in 200-ID batches, builds one UTF-8 BOM CSV inside a read-only `REPEATABLE_READ` transaction, and rejects a document over 16 MiB before HTTP output begins.
- `ContactCsvDocument` owns the Customer/Contact/Lead shared non-queueing admission lease (one per member, four per replica) until write completion, failure, or cancellation. REST writes only the completed document with `no-store`, `nosniff`, and the fixed `contacts.csv` disposition.
- RFC 4180 encoding uses CRLF, stable field-code headers, typed scalar normalization, and formula hardening before quoting. The feature creates no B24 file, storage object, job, receipt, history, or download token.

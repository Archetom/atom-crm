# B24a Work Task 附件内核验收记录

## 交付范围

B24a 实现了 `AttachmentFile` 聚合和 bytes、inspection、publication 三轴状态；文件身份、预期/实存长度与 SHA-256 内容证据，以及不可改绑的 Work Task 当前 owner 关系。所有公开入口都位于 `/api/v1/attachment-targets/{targetType}/{targetId}/attachments`，并以 `files:read` 或 `files:write` 与 Work Task 当前可见/协作权限交集授权。Work Task adapter 只使用任务 creator、assignee、follower 或 manager 可见性，不读取其可选 CRM relation；任何附件历史都使任务软删除失败。

`V59__create_attachment_foundation.sql` 是 B24a 唯一的 Flyway migration，创建 tenant-scoped file、relation、content、job、read lease 和 usage 六类事实表，带 typed Work Task/FK/tenant、state/CHECK、lease/fence 和必要索引。terminal retention 使用 V59 既有 `(tenant,file,content,kind,generation)` 唯一键：generation 由 source kind 与全局唯一 source job ID 无碰撞地派生，因此不同阶段不会吞掉彼此的 recovery，也不占用冻结给 B24b relation 扩展的 V60。另有不可归属 tenant 的 `crm_attachment_global_usage` 单例仲裁行。它先于 tenant usage row 锁定，因此 `globalReserveBytes` 是真实跨租户容量而不是每 tenant 上限。所有 usage 路径统一按 global→read-lease→tenant 锁序执行；即使新的 reservation 因上限被拒绝，也会在同一提交中结算已过期的 download lease，释放的 lease 以独立事务幂等重试。storage、readiness、inspection 和 runtime policy 以 application port 表达；secure-local、bounded magic、streamed inspection 是显式 adapter，默认 composition 全部 `NOT_READY`，生产配置保持 `atom.files.enabled: false` 与 worker disabled。

上传 intent 先锁 exact Work Task root，再创建 upload plan 与 durable work；withdraw/expiry 后的 upload admission 必须仍是 `UPLOADING + PRIVATE` 且在 plan deadline 前，reconciliation 也不能把 withdrawn aggregate 重新 finalize。HTTP raw PUT 校验唯一 Content-Length、`application/octet-stream`、无 content encoding/transfer encoding，并只流式使用 64 KiB buffer；store/open 的 absolute total deadline 与 policy 的 open/idle watchdog 会关闭卡住的 source/read handle。GET 支持完整读取或单一 bytes range，失败范围在 storage open 前归一为 416，并在授权/root lock 后取得 durable same-call-stack read lease，直到 handle close/cancel 或 hard expiry 才允许删除确认。六类 worker 通过 MySQL `SELECT … FOR UPDATE SKIP LOCKED` lease/fence claim；每个串行 worker invocation 只 lease 一个 job，避免排队工作在未执行前耗尽 attempt。claim/heartbeat/commit 只触及 job row，领域提交按 target→relation→file→job 的顺序重验 fence。达到 deadline 或 max attempts 的 job 转 `DEAD`，再由 retention 进入 state-aware cleanup：stored object 只能经 exact delete 和 absence confirmation 标记 `REMOVED`。reconciliation、inspection、publication 和 cleanup 都使用新的子阶段 deadline；terminal `STORED+CLEAN+PRIVATE` 会以新 deadline 重排 publication。

secure-local 的 physical namespace 与 stored identity 都绑定 `StorageBindingRef` 的 fingerprint；allocation 产生的 32-byte `storageGeneration` 同时写入 durable plan、store descriptor 与 probe command，receipt-loss recovery 因而不能接受同 locator 的其他 attempt。不同 binding 不能 probe/open/delete，descriptor 缺失但 content 尚在只能报告 `MISMATCH`；`MISMATCH` 永不作为 incomplete abort 的清理成功证据。`abortIncomplete` 只在删除后复验两项 entry 均不存在、并完成 root directory force 后才返回 `ABSENT`；foreign attempt 返回 `MISMATCH`，worker 只能重试，不能释放 quota 或标记 `REMOVED`。每个 node-local store 以共享 commit fence 覆盖 winner/duplicate 的整个 content、descriptor、directory-force/rollback 临界区；duplicate 不能在 winner 的 durable commit 前读取 descriptor 或打开其 one-shot source。`CREATE_NEW` 冲突会在同一个 one-shot input 上比较证据并收敛相同 PUT；content 已创建而 descriptor 尚未完成时，会在同一 upload deadline 内等待 descriptor，而不是把并发 winner 错报为 503。finalize 按最终锁定的 file/plan 状态收敛，两个同时 admission 的相同 PUT 都可得到 accepted。`STORED` 的 replay 还必须精确使用 durable plan 中不可变的 intent version，并以同一 one-shot stream 再次证明 length/SHA-256；它使用独立 I/O deadline，不受已过 intent TTL 阻断；任意旧/新 version 或等长不同 bytes 都是 conflict。withdraw 与 finalize 交错时，观察到的 receipt 被持久化为 exact identity 后只走 `DELETE_EXACT → CONFIRM_ABSENCE`，不会降级到 `INCOMPLETE_ABORT`。content 与 descriptor force 后，store descriptor publish、delete 及 confirm-absence 都强制执行经 attestation 证明可用的 root directory durability procedure；force 使用构造时打开并持续持有、且与每个 `SecureDirectoryStream` file-key 相等的目录 handle，而非按 pathname 重开。无法 directory force 的 platform/profile 保持 `NOT_READY`。secure root 必须严格为 owner-only `0700`，entry 必须为同一 file store 的普通、同 owner、`0600` 文件。`open` 在向调用方公开前以同一 relative-open content handle 核对全对象 SHA-256，并在 full/range 读完时重新核对 descriptor、字节数和 SHA-256；任一漂移均不会标记 completed。精确 delete 对 content/descriptor 的任一 crash cut 都可安全重试。DEAD job 与 replacement retention work 在同一 MySQL `REQUIRES_NEW` transaction 提交，recovery generation 由 source kind/job ID 派生；terminal UPLOADING recovery 必须先进入 generation-fenced exact probe，绝不直接 abort 已成功 store 而未 finalize 的 locator。worker 对每段外部 I/O 按 `jobHeartbeat` 持续续租，结果提交仍依 target→relation→file→job fence。

首个可启用 profile 是 `LOCAL_SECURE_NIO_V1+BOUNDED_MAGIC_V1+STREAMING_ENGINE_V1`，但 `atom.files.*` properties 不能自证：部署必须注入私有 `SecureLocalAttachmentConformanceReportSource`，其独立 report 要精确匹配 binding、policy、secure-local root 的 canonical path/owner/mode/file-key/device digest、allowlist/catalog revision、完整 `S-01..S-14`、`I-01..I-14` 与 `X-01..X-08` scenario set、engine build、definition generation/basis 与 freshness。build digest 覆盖 external、application、domain、persistence/schema、API DTO/facade、REST controller/security、start scheduler/composition 与 shared error semantics 的完整运行 code source；缺失任一 artifact 会直接 `NOT_READY`，不存在 `MISSING_*` 的自洽值。每个 storage operation 在同一 `SecureDirectoryStream` 中相对打开 descriptor/content，并在打开后复验 root 的 owner/mode/file-key/device 证据；entry 必须是同一 file store 中的普通、同 owner、0600 文件，open 失败会关闭 directory/channel。scan 先验证 result 的 generation/basis 与实际 scan-start evidence；只有这个 fence 成立的 threat 才是最强事实，即使 scan 后 generation 漂移也继续拒绝。bounded magic 会填满其固定前缀，允许合法的 short read。inspection readiness 的 report/engine/definition 故障会停止新 intent admission；report source 撤销、过期或异常时，启动期未过期 storage evidence 只保留 `PROBE_EXACT`/`ABORT_INCOMPLETE`/`DELETE_EXACT`/`CONFIRM_ABSENCE` cleanup lane，绝不继续开放 store/read/replay。storage snapshot 取 report 与五分钟上限的最早值；inspection snapshot 还取 definitions 与 definition max-age 的最早值。B23 已发布的 `ENTERPRISE_DATA_*` scene code 保持 `7300..7302`，B24a 使用无冲突的 `7330..7336`。

## 覆盖的验证点

- Domain tests 覆盖三轴状态、只在 clean/stored/private 时发布以及 reject 不可重新 clean。
- Application tests 覆盖 NFC filename、allowlist/checksum 与 single-range 严格解析。
- `B24aWorkTaskAttachmentIntegrationTest` 运行完整 HTTP intent/upload/status/list/full/range/withdraw，并以两个 admission 后的 storage barrier 证明并发相同 PUT 都收敛为 202；同时验证 `STORED` replay 仅接受原始 intent version 和完全相同 bytes，以及 Work attachment history 阻止软删除。
- `AttachmentPersistenceIntegrationTest` 同时确认 empty-schema 与真实 V58→V59 MySQL Flyway 升级路径；它验证 V60 不存在、job 未被 B24a 扩列、global arbiter、跨 tenant reserve、lease takeover、拒绝 reservation 下的 expired-download 结算，以及 source kind/job ID 派生 generation 隔离的 DEAD→replacement retention durable row 对。
- `AttachmentStorageConformanceTest` 覆盖 one-shot duplicate PUT、winner/duplicate durable commit fence、allocation generation fenced store/probe、root drift、entry 0600/file-type/file-store fail-closed、partial descriptor `MISMATCH`、same-length content tamper 的 pre-open/post-read SHA-256 failure、native single range 和可取消 open timeout；`B24aAttachmentCrashIntegrationTest` 覆盖 descriptor/content delete crash cuts 的收敛。
- `AttachmentInspectionConformanceTest` 验证 bounded magic（包括合法 short read）、pinned streamed definition evidence、basis/generation mismatch、scan 中 generation reload 对 clean 失败关闭，以及已确定且 scan-start fenced 的 threat 在 generation reload 后仍被拒绝；`AttachmentIncompleteAbortWorkerTest` 验证 foreign-generation `MISMATCH` 只会 retry 而不结算 removed。start runtime 中的 `AttachmentComposedConformanceTest` 验证外部 report + binding + root + policy + 完整 B24 runtime digest 可启用 secure-local profile，report fault 仅保留 cleanup lane，且 properties-alone、bootstrap/runtime report fault 均不能使普通 CRM 启动失败。
- `DisabledAttachmentConfigurationTest` 确认未安装 runtime adapter 时 policy、storage 和 inspection 都不会声称 ready；`ArchitectureBoundaryTest` 额外禁止 attachment core 引入 servlet、filesystem、URL/URI、multipart 或 provider SDK。

# B32a acceptance: tenant Opportunity pipeline and stage catalog

## Implemented scope

- Tenant-owned `OpportunityPipeline` and `OpportunityPipelineStage` roots expose immutable, binary-exact ASCII codes, mutable display facts, explicit `ACTIVE` / `INACTIVE` / `DELETED` lifecycle, optimistic versions, and terminal no-reuse deletion.
- `GET`/query routes require `opportunity-pipelines:read`; create, update, lifecycle, and deletion routes require `opportunity-pipelines:manage`. Both are non-data-scoped tenant-catalog capabilities guarded by active membership.
- A tenant catalog guard serializes cross-root lifecycle and capacity checks. Pipelines start inactive, must have an active stage to activate, cannot lose the final active stage while active, and can be deleted only when inactive with all stages deleted. A stage must be inactive before deletion; the maximum non-deleted catalog size is 100 pipelines per tenant and 100 stages per pipeline.
- V85 preflights every historical Opportunity pair before any DDL, then makes pipeline/stage columns `ascii_bin`, backfills every existing exact pair without rewriting values, creates per-tenant catalog guards and pipeline/stage tables, gives fresh tenants active `direct/qualification` and `direct/negotiation` defaults, and adds a same-tenant exact-pair foreign key. Direct SQL fixtures explicitly provision their required catalog pair.
- Opportunity creation, full-update pair moves, and `/stage` pair moves acquire the OPPORTUNITY customization guard before the catalog guard and require the target pair to be active. A binary-exact unchanged pair makes no `/stage` save/version change and lets full ordinary updates continue after catalog deactivation or deletion.
- B05 continues to own code-field visibility and B11 workflow stages remain wholly independent. Catalog probability has no effect on Opportunity outcomes, reporting, forecasts, saved views, or workflow state.

## Verification

`OpportunityPipelineModelTest` covers inactive creation, exact-code normalization, terminal deletion, lifecycle preconditions, and supplementary-character name boundaries at 200/201 code points. `OpportunityIntegrationTest` covers dedicated catalog authority and cross-tenant closure, default provisioning, pipeline/stage activation order, last-active-stage protection, active-pair creation, blocked new assignment after deactivation, unchanged-pair compatibility, 100/100 capacity, unhinted status/no-status repository query plans with tenant-prefix ordered indexes, concurrent deactivate/create serialization, concurrent two-stage deactivation, duplicate-code creation, delete/create-stage serialization, and the B05 field-write check occurring before catalog lookup. `PersistenceIntegrationTest` upgrades a V84 database through an invalid-history preflight failure, verifies no V85 DDL leaked, repairs the history, then verifies retry, binary collation, uppercase/lowercase exact-pair backfill, Opportunity version and saved-view/report/approval/workflow JSON preservation, and rejection of unknown, cross-pipeline, and cross-tenant composite pairs. `TrimmedCodePointSizeWebValidationTest` verifies trimmed 64-code-point code and ASCII/supplementary-character 200-code-point name boundaries for pipeline/stage creation and name updates.

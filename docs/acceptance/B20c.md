# B20c 内部公告验收记录

## 交付结论

B20c 已交付 `/api/v1/oa/announcements` 的草稿分页与详情、创建、更新、发布、撤回、软删除、我的公告分页与详情、未读数量和幂等已读。公告只保存有界纯文本，不进入 B15 工作台，不创建 B21 Work 任务，也不发送邮件、短信、推送、Webhook 或其他外部通知。

管理边界使用 `oa-announcements:write`，接收与回执边界使用独立的 `oa-announcements:read`；两者都要求已验证 caller 的当前活动 tenant 成员关系。公共请求没有 tenant、creator、publisher、recipient、read time 或生命周期写入口，未知属性会被拒绝。

## 生命周期与发布快照

`OaAnnouncement` 是 tenant-scoped、版本化聚合，状态为 `DRAFT`、`SCHEDULED`、`PUBLISHED`、`WITHDRAWN`、`DELETED`。只有草稿可修改标题、正文和受众；发布后只能撤回，活动发布必须先撤回才能软删除。B28a 的排期 generation、到期授权复核和 occurrence 语义见 [B28a](B28a.md)。所有转换校验请求版本，发布、撤回和其他写入都锁定同一公告根。

受众严格区分 `TENANT`、`DEPARTMENT_SUBTREE` 和 `MEMBER`。草稿写入及发布都会在组织 tenant 锁内重新校验活动同 tenant 部门和成员；发布通过递归部门投影解析当前活动成员，合并三类选择器后按 actor 去重。查询读取上限为 10,001，超过 10,000 整体失败，不会截断；空受众同样不发布。根状态和分块接收人插入在一个事务内完成。

接收人表是发布时的不可变事实。后续加入或调入部门不会新增历史接收人，调出部门也不会删除既有快照；当前成员一旦失活，即使快照仍在，也无法进入普通 API。并发使用同一版本发布时只有一个事务成功，另一个稳定返回版本冲突，接收人不会重复。

## 已读与统计

我的列表、详情和未读数量在 SQL 中同时应用 verified tenant、`PUBLISHED`、接收人快照和当前活动成员关系，再统计和分页。撤回或删除会立即从普通查询和未读数量消失。

管理列表使用不含受众的根级 `OaAnnouncementSummary`，收件箱分页、详情和标记已读的加锁可见性检查使用根级 `OaAnnouncementInboxItem`；这些路径不会访问部门或成员选择器表。只有管理详情和需要完整聚合的写操作加载受众，避免合法的 `200 × 10,000` 选择器数据进入 JVM。

标记已读先共享锁定当前成员关系，再共享锁定仍可见的公告根，使它分别与成员失活、公告撤回形成确定顺序，同时不把同一热门公告的不同接收人串行化。回执按 `(tenant, announcement, member)` 唯一键原子插入，冲突时保留并返回首次服务端 UTC 时间。管理员详情和分页只批量返回 `recipientTotal` 与 `readTotal`，不返回接收人画像、设备、位置或阅读时长；两条管理读路径都在同一个 `REPEATABLE_READ` 查询事务内先复核活动成员，再读取根、计数和分页统计。

## 持久化与边界

`V55__create_oa_announcement.sql` 创建公告根、部门选择器、成员选择器、不可变接收人和已读回执；`V57__remove_oa_announcement_deleted_time.sql` 在不修改已应用迁移的前提下移除冗余 `deleted_time`，最终模式只用 `status=DELETED` 表示软删除。根、选择器、接收人及回执全部显式携带 tenant；creator、部门、成员、公告和接收人关系使用复合外键，回执不能写给未投递成员。状态与时间组合、Unicode 字符长度、版本和布尔选择器都由数据库约束再次保护。

正文最多 20,000 Unicode 码点，标题最多 200 码点；API 把内容作为普通 JSON 字符串原样返回，不执行 HTML 或 Markdown 渲染，也不接受附件、模板、脚本或外部图片配置。

HTTP 层先匹配 `/mine`、`/unread-count` 和 `/mine/{id}/read` 并要求 `oa-announcements:read`，随后用公告通配规则要求其余路由具有 `oa-announcements:write`。应用层继续独立执行相同能力和当前活动成员校验。

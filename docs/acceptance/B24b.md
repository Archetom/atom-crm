# B24b 八类 CRM 业务附件目标验收记录

## 交付范围

B24b 沿用 B24a 的单一 `AttachmentFile`、target-first HTTP 路由和六类 durable worker，不增加通用文件库、文件状态、worker kind 或新的公共 target 路由。Customer、Contact、Lead、Opportunity、Contract、Invoice、Receivable 与 ReceivablePlan 分别注册一个显式 `*AttachmentTargetAccess`；注册表必须同时拥有九个闭集 target（含 Work Task），缺少、重复或未知 target 都失败关闭，不能退化为 tenant-level 授权。

每个 CRM adapter 复用其 owning domain 的 read/write resolver 与 visibility projection，并在命令、upload/status/withdraw 和 worker 提交时取得 exact parent root。Customer/Contact 的 `IN_POOL` 使全部附件操作安全不可见但不建立删除工作；Lead `CONVERTED`、Contract `VOIDED` 和 Invoice `ISSUED` 保持附件可用，其他删除状态关闭访问。所有八个父软删除路径（含 Customer/Contact 的 pool-delete 批处理）在已有 command transaction 中先取得对应 typed root 的 `FOR UPDATE` 锁，再调用 `AttachmentParentLifecycle`，因而父删除与附件 mutation 都遵循 `parent → relation → file`，不会出现先锁 relation/file、后锁父记录的反向锁序。lifecycle 仅关闭 active relation、撤回 aggregate，并写入 `DELETION` 或 `INCOMPLETE_ABORT` 与 retention durable work，不在事务中进行 storage I/O。

inspection 与 publication worker 会保留删除清理通道，但会消费 worker lock 返回的 lifecycle projection：Customer/Contact 处于 `IN_POOL` 时，已领取的 inspection/publication job 在持有 parent → relation → file → job 锁序的当前事务中转为 `PAUSED`。该转换归还 claim 所加的 attempt、清除 lease、不建立 terminal recovery；恢复 owner 后 parent lifecycle 才将对应 job 重排为 `PENDING` 并刷新 deadline。这样暂停不会在长期公海期间耗尽重试或删除附件，publication 也不会把 late clean 文件推进为 `AVAILABLE`；删除后的 withdrawn/removing 文件仍可由删除和 retention worker 清理。

可用附件列表使用 closed typed SQL provider 选择 parent 列，在 MySQL 侧执行 `COUNT(*)` 和 `ORDER BY available_time DESC, id DESC LIMIT` 的 join 查询。它不再先加载最多 100 个 relation、逐文件查询再在 JVM 排序分页。

`V60__add_crm_attachment_targets.sql` 只扩展 `crm_attachment_relation`：Work Task parent 变为 nullable，增加八个 nullable typed parent ID、八组 `(tenant_id,parent_id)` 外键与八个覆盖索引。relation CHECK 改为九种 target/type 的 exact-one parent 组合，因此既有 Work 行仍合法，跨 tenant、悬空或 type/parent 不匹配的 relation 均由 MySQL 拒绝。`V61__add_attachment_paused_job_state.sql` 仅扩展既有 job CHECK 以保存 `PAUSED` durable defer 状态；它不增加 worker kind 或 public API。B24b 交付时 B24c 的 FILE field、OA draft，以及 Product、ReturnVisit、Announcement、Activity、connector 和 B22 recording 均未接入；B29a 后续已接入 Product/ReturnVisit。

## 验证

- `AttachmentTargetAccessRegistryTest` 覆盖九 target 的完整显式注册、缺项与重复注册失败关闭。
- `CrmAttachmentTargetAuthorizationTest` 覆盖八个 CRM target 的 read/collaborate typed adapter 矩阵；`CrmAttachmentTargetAccessSupportTest` 覆盖 eight-root worker lock，以及 Lead conversion、Contract void、Invoice issue 和 Customer/Contact pool pause 的 lifecycle projection。
- `AttachmentParentLifecycleImplTest` 覆盖 stored 与 uploading relation 的父删除撤回、typed relation 关闭、分别建立 deletion/incomplete-abort 与 retention work，以及 pool restore 时只重排 paused inspection/publication job。
- `AttachmentPausedTargetWorkerTest` 覆盖 pool pause 后 inspection 不触碰 storage、不写 CLEAN，publication 不写 AVAILABLE，并调用 defer 而非 retry 的 late-worker no-resurrection。
- `AttachmentFileRepositoryImplTest` 覆盖 size=1 时列表只调用一次 typed count 和一次 typed page join，不访问 relation mapper。
- `B24bCrmAttachmentTargetIntegrationTest` 参数化运行八个实际 CRM root 的 typed lock、same-tenant relation 与 target/file mismatch；直接插入九类错误 parent/type，验证跨 tenant typed FK，并让 Work Task 与 Customer 两个 target 并发竞争同一 file；恰有一个 relation 成功。它还在真实事务中锁住 leased job 后 defer，验证 attempt 回退、过期 PAUSED job 不会 terminal-recover、Customer/Contact restore 重排；publication 与 Customer soft-delete 的交错验证 withdrawn 文件不能复活。
- `AttachmentPersistenceIntegrationTest` 覆盖 empty-schema V60/V61、V58 到 V61 的真实 Flyway upgrade，以及 relation 的八个 typed parent 列、FK 与覆盖索引。

# B23a 企业数据查询内核验收记录

## 交付边界

B23a 最初交付 `/api/v1/enterprise-data` 下的 capability 探测、按登记名称的有界单页查询和 USCC/LEI 精确查询；B23-CH 后续在不改变该读边界的前提下补入 `UK_COMPANIES_HOUSE/GB_CH_NUMBER` 请求、capability/observation 投影和 scheme 校验。所有入口均要求活动 tenant 成员和独立的 `enterprise-data:read` 能力；公共请求不能选择 provider、connector、账号、endpoint、套餐或凭据。B23-CH 没有启用真实 source，因此本记录的零持久化、tenant 隔离和生产失败关闭结论不变。

规范输出保持 B23-XP 的固定 allowlist，来源技术 capability、tenant 部署政策、受控 attribution、核心 TTL 和核心 usage 上限取最严交集。B23a 对外最高只能是 `EPHEMERAL_ONLY`；生产默认 source/policy 均为 `NOT_READY`，测试只使用显眼虚构数据。

本批次不实现 Customer 写入、身份占用、择取/采用、刷新、缓存、持久化 observation、durable provenance、Activity/事件/报表/工作台投影或真实 provider adapter。B23-XI 的 tenant 内身份唯一仲裁和 B23-XP 的采用事务仍属于后续 command 边界。

## 零持久化

外部 capability 和 source I/O 全部在 `ServiceOperation.prepare` 中完成，位于 `QueryServiceTemplate` 的独立只读 `REPEATABLE_READ` 数据库快照之前。执行阶段只把已经完成核心复核的 observation 投影为 VO；查询服务没有 repository、cache、event、`AfterCommitExecutor` 或 command 依赖。

`EnterpriseDataIntegrationTest.tenantBoundQueriesCannotCrossMembershipAndNeverPersistDatabaseRows` 在两个真实 MySQL tenant bootstrap 完成后，对当前 schema 的每张基础表记录精确行数快照，再执行 capability、名称查询、精确查询及两次跨 tenant 拒绝。所有请求结束后整库行数快照必须完全相等，并额外确认 schema 中不存在 enterprise-data、registered-identity 或 adoption-provenance 持久化表。

该断言证明 B23a 的成功、授权失败和跨 tenant 失败路径都不新增或删除数据库行；结合只读事务和应用端口结构，验收结论为候选与详情仅存在于当次响应生命周期，不会进入 Customer、Activity、报表、工作台或其他持久化路径。

## Tenant 隔离与调用顺序

- `OrganizationAccessGuard.requireActiveMembership` 先从已验证 `AuthenticatedCaller` 导出 `TenantId`，再允许 policy、adapter capability 或 source 查询；失活、缺能力或错误 tenant 在任何 source I/O 前拒绝。
- 部署 policy 按派生 tenant 先于 adapter capability 解析；缺失或禁用 policy 不触达 adapter。
- outbound port 只接收派生 `TenantId` 和 typed query/identifier，不接收 caller-controlled tenant 或 provider selector。
- MySQL/HTTP fixture 使用两个 owner/tenant 交叉请求，A owner 不能借 tenant B header 查询，B owner 也不能进入 tenant A。
- `EnterpriseDataComposedFixtureTest` 在同一 adapter 进程内进一步证明两 tenant 的 source binding、policy、TTL、attribution、候选上限、quota、failure state 和调用计数互不影响；跨 binding identity 在 lookup 前拒绝。

因此，一个 tenant 的 policy disable、quota exhaustion、source failure 或 selector 集合不会改变另一个 tenant 的 readiness、结果或额度。

## 错误归一化

adapter 只能向核心暴露四种无原始 body/message 的错误类型。应用码和 HTTP 契约固定如下：

| Source error | Application error | HTTP | Public message |
| --- | --- | --- | --- |
| `NO_RESULT` | `304` | `404` | `No enterprise data was found` |
| `LIMITED` | `305` | `429` | `Enterprise data source is temporarily limited` |
| `UNAVAILABLE` | `306` | `503` | `Enterprise data source is unavailable` |
| `UNSUPPORTED` | `307` | `422` | `Enterprise data query is not supported` |

任意 adapter runtime、null/超量结果、重复 primary identity、错误 jurisdiction/source kind、未声明 identity type 或 selector 不匹配均失败关闭为 `306`。请求 DTO、identifier 和 observation 的字符串表示固定脱敏；raw provider error canary 不进入 `Result`、HTTP message 或公开 observation。格式、checksum、枚举和未知属性错误仍在边界归一为 `101/400`，不会伪装成来源故障。

`EnterpriseDataQueryServiceImplTest` 穷举四种 source error，并把携带敏感 canary 的任意 runtime 收敛到安全 `306`；`ResponseEntityUtilTest` 参数化复核 `304..307` 的完整公开码、状态和固定消息；`EnterpriseDataIntegrationTest` 再通过真实 HTTP 验证有效但无结果的 LEI 为 `304/404`，未支持 jurisdiction 为 `307/422`。

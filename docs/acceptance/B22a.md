# B22a Connector 安全与控制平面验收记录

## 交付边界

B22a 交付 connector 注册、凭据生命周期、独立非人工认证主体、当前 tenant 解析和未来 ingress 写事务所需的 registration 锁。人工控制平面位于 `/api/v1/connectors`，使用 tenant 可分配的 `connectors:read` 与 `connectors:manage`；非人工边界当前只提供不带 body 的 `POST /api/v1/connector-ingress/probe`。

本子批次不接收呼叫事实，不创建 call interaction、leg、inbox、outbox 或 adapter journal，不处理号码、录音、媒体、agent/device 映射、provider readiness，也不包含云通信或 PBX adapter。B22-R/D/S/M/A/CW/CP/PC/PD/PM 的后续契约保持独立。

## 主体与 tenant 来源

`AuthenticatedConnector` 唯一有身份语义的值是已经由核心认证的规范 `connectorRef`，并携带同一认证服务实例签发的进程内 opaque evidence；直接构造、其他认证服务实例或普通 bean 不能伪造该 evidence。HTTP 层只有基础设施 `ConnectorPrincipal` 可以携带认证服务产生的 context；`ActorPrincipal`、`AuthenticatedCaller`、trusted headers、普通 JSON 和 connector bearer 不能互相替代。connector principal 没有 CRM authority，无法进入人工控制平面。

传输认证和应用解析使用两个独立的 pre-tenant 输出端口：

- `ConnectorCredentialLookup` 只按完整 `(connectorRef, keyId)` 精确查询 verifier、registration 状态和 key 状态；
- `ConnectorIdentityLookup` 只按完整 `connectorRef` 精确查询 verifier-free 的内部 connector、tenant、状态和版本；
- 两者都返回有界单行投影，歧义、未知、停用、退役和撤销全部失败关闭，不提供列表、前缀、provider account 或跨 tenant 搜索；
- `ConnectorGuard` 先验证认证 evidence，再解析活动 registration 并产生单用例 `ConnectorContext`。后续 ingress command 必须在首个业务写之前调用 `lockActive`，以 tenant、内部 connector ID 和 ref 锁定同一根记录；无活动事务的调用立即失败，不会把自动提交的 `FOR UPDATE` 误当成并发保护。

## 凭据与生命周期

connector ref、18-byte key ID 和 32-byte secret 均由服务端安全随机生成。完整凭据固定为 `43-char connectorRef + '.' + 24-char keyId + '.' + 43-char secret`，只在创建或轮换响应中出现一次。数据库保存 64 位小写十六进制 SHA-256 verifier，不保存 secret 或完整 bearer；比较使用恒定时间字节比较。

一个 registration 最多有两个活动 key，以支持有界重叠轮换。撤销立即使指定 key 失效。状态固定为：

- `ACTIVE`：活动 key 可以认证；
- `DISABLED`：可恢复停用，全部 key 暂时拒绝；至少保留一个活动 key 才能重新启用；
- `RETIRED`：不可逆退役并撤销全部 key，不能重新启用、轮换或修改。

所有人工写入锁定 tenant-scoped registration 并校验乐观版本。key 撤销、停用和退役只在数据库事务提交后清除本机认证桶，回滚不会提前暴露认证状态变化。

## 持久化与限流

`V58__create_connector_control_plane.sql` 创建 registration 与 credential 表。`connector_ref` 使用 binary-exact 全局唯一约束；根表提供 tenant/ID/ref 复合候选键，credential 永久携带并外键引用同一 `(tenant, connector, ref)`，因此有 credential 的 registration 不能把 tenant 或 ref 更新到另一个身份。人工仓储的查询、分页、加锁和保存全部显式 tenant scoped。

connector 认证入口在 lookup 前消耗来源 reservation。来源失败、未验证 credential 和已验证 connector 使用三个独立有界 map；伪造的规范 credential 只能进入 pending 容量，不能创建 verified connector 分区。同一 connector 的两个活动轮换 key 共享一个 fixed-window 计数，撤销单 key 不会重置该 connector 的已消费配额。桶满或分钟配额耗尽返回 `429` 且不驱逐 live window；credential lookup 异常取消 reservation 并返回 `503`，identity lookup 异常也稳定返回 `503`，两者都不会降级为未知主体。来源解析复用既有可信代理规则，所有桶均为单实例 admission control，不声明多副本全局配额。

## 验证范围

单元与架构测试覆盖 credential 规范解析、随机长度、hash-only verifier、恒定时间匹配、聚合重建与两 key 上限、不可逆退役、guard 在业务访问前解析、认证投影状态组合、主体 mapper 隔离、HTTP filter 的 `401/429/503` 分类、PO hash-only 往返和架构包命名。

`ConnectorIntegrationTest` 使用 MySQL/Testcontainers 覆盖两 tenant 隔离、一次性 secret、数据库只存 verifier、人工/connector 路由不可互换、未知 server-owned 属性拒绝、两 key 重叠与第三 key 拒绝、撤销/停用/恢复/退役、不可逆退役、tenant/ref 复合外键不可迁移，以及 ingress registration 锁与并发停用的确定顺序。

验证命令：

```bash
sh ./mvnw -q test -DskipITs

CI=true sh ./mvnw -q -pl start -am \
  -Dtest=ConnectorIntegrationTest \
  -Dsurefire.failIfNoSpecifiedTests=false test

CI=true sh ./mvnw -q test
```

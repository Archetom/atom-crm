# B29c 验收记录：OA 公告附件冻结与接收人下载

## 实现范围

- `OA_ANNOUNCEMENT` 是 B24 封闭附件目标之一，公开复用
  `/api/v1/attachment-targets/oa-announcement/{announcementId}/attachments`；附件只关联公告根，绝不复制到接收人、EMAIL outbox、URL 或公告正文。
- 只有 active member 且同时具有 `files:write` 和 `oa-announcements:write` 的管理者能在 `DRAFT` 创建、上传、查询状态或撤回。`SCHEDULED`、`PUBLISHED`、`WITHDRAWN` 与 `DELETED` 全部拒绝附件变更；取消排期回到 `DRAFT` 后才重新开放。
- 草稿查询/下载要求 `files:read` 与 `oa-announcements:write`；已发布下载要求 `files:read`、`oa-announcements:read`、当前 active membership、根仍为 `PUBLISHED`，以及 immutable recipient snapshot 的 exact admission。两种权限不互相推导，未获附件读权限的接收人不会从公告收件箱推断附件存在。
- 排期、立即发布和 due-publication 都在 `organization_tenant -> oa_announcement` 锁内读取最多 101 条 active relation，并按 `relation/file` 顺序锁定；重新排期先锁定并取消旧 `occurrence`，再锁附件，即完整顺序为 `tenant -> announcement -> occurrence -> relation/file`。集合必须不超过 100 条且每条均为 `AVAILABLE`。失败不会发布根、写 recipient snapshot 或创建 EMAIL delivery；due failure 将公告回退到 `DRAFT` 并记录安全原因 `ATTACHMENT_UNAVAILABLE`。
- 撤回和删除在同一公告根锁/事务内关闭所有 active 附件关系并注册原有 durable cleanup，不要求 `files:write`。附件 worker 在非草稿根上不再把待处理文件发布出去。
- `V83__add_oa_announcement_attachment_target.sql` 为 `crm_attachment_relation` 添加 typed `oa_announcement_id`、same-tenant composite FK、根/status 查询索引及 exact-one target check，并扩展 OA publication/occurrence 的安全原因约束。`V79`–`V82` 已由其他已合并能力占用，因此没有改写已存在迁移。
- B28 EMAIL 保持 attachment-free、URL-free；template 仍仅含公告 ID、标题和实际发布时间。

# B20b OA 申请运行时与审批联动验收记录

## 交付结论

B20b 已交付 `/api/v1/oa/requests` 的预览、原子提交、参与申请分页和详情。申请提交后不可编辑，B11 审批实例仍是唯一运行状态来源；审批、驳回、转审、批量、撤回和取消继续使用既有 B11 API。B15 仅复用原有 `APPROVAL_PENDING` 来源，没有新增 OA 待办投影。

实现使用 V54，未创建或引用 B21a 的 Work 聚合、表、API、能力或迁移。B20b 与 B21a 只共享既有 caller、组织授权和工作台扩展基础，两个业务边界可独立合入。

## 原子提交与幂等

提交在一个 `CommandServiceTemplate` 事务内按稳定顺序锁定 tenant、OA customization guard 和活动表单，重新读取活动成员、当前字段、字段 `WRITE` 策略和活动审批定义。客户端只能提供表单输入、申请人选择的审批成员与抄送人；tenant、申请人、部门、表单 code 和 UTC 提交时间都由服务端派生。

`OaRequest` 及其字段/唯一值先持久化，随后内部 `ApprovalSubmissionCoordinator` 通过 `BusinessRecordFactResolver` 从该申请重新读取权威事实并创建 `oa:<requestId>` B11 实例，最后写回一次性审批关联。该路径不调用会开启独立事务的公共 `ApprovalService`。单连接 Hikari 用例把池上限设为 1，申请和审批仍能完成；路由失败时申请、字段、唯一值和审批全部为零。

公开幂等边界是 `(tenant, applicant, key)`。tenant 行锁把同一申请人的并发重试串行到首次结果可见之后；数据库唯一键提供最终仲裁。服务端只保存表单 ID、版本、规范字段值及选择/抄送的确定性 SHA-256 摘要，不保存未治理原始请求。相同提交的串行与并发重试返回同一申请和审批 ID，改变表单、版本、规范值、选择或抄送返回稳定冲突。公共 B11 同时保留 `stage:` 和 `oa:` 命名空间。

## 可见性与字段安全

申请仓储在 SQL 计数和分页前应用申请人、历史审批任务成员、提交时管理人、抄送人和 `oa-requests:manage` 活动成员的并集。`oa-requests:read` 只允许进入接口，不授予同部门或全 tenant 数据；跨 tenant 和普通非参与成员使用 not-found/空页语义。

OA 申请响应的结构层只保留申请、表单、审批和版本标识以及 `approvalStatus`；表单 code、申请人、部门、标题和提交时间只从经过当前 B05 策略的 `values` 输出，避免原始顶层副本绕过隐藏或脱敏。B11 OA 详情和摘要同样对 facts、title、applicant 与 submitted time 应用当前策略；依赖原始 title 列的通用 B11 keyword 查询明确排除 OA，不能用命中结果形成隐藏字段 oracle。B15 只有在 `request_title` 当前可读且未脱敏时才输出 OA 审批摘要；隐藏或脱敏标题不会进入工作台。

验收用不同成员分别覆盖申请人、审批人、管理人、抄送人、普通 reader、OA tenant manager 和跨 tenant caller。审批人先以未脱敏标题看到一个既有 `APPROVAL_PENDING` 项，再把字段策略改为 `PARTIAL`；OA 详情和 B11 详情都返回同一掩码，工作台项同步消失。

## 持久化与兼容性

`V54__create_oa_request.sql` 创建不可变申请根、字段值和唯一值预留，所有主外键、唯一键与索引都显式携带 tenant。申请到审批使用 `(tenant, approvalInstanceId, OA_REQUEST, requestId)` 复合外键，审批实例也增加对应 subject 候选键，防止跨 tenant 或错误对象关联。表单产生申请历史后，其规范 code 不再允许修改。

B11 原有 100 个路由/CRM 快照字段上限保持不变；只有 `OA_REQUEST` 实例可容纳 100 个表单输入加四个服务端事实。阶段门、普通审批定义和公共 CRM 提交仍使用 `MAX_ROUTING_FACTS=100`。

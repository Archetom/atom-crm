# Object layering and naming

Names identify both meaning and architectural ownership. Prefer a domain or boundary term over generic names such as `Model`, `Data`, `Manager`, `Helper`, or `Util`.

API Request/Response types and persistence objects do not belong in `domain`. Infrastructure never exposes `UserPO` through a public contract.

## Mapping path

```text
HTTP JSON -> Request -> application use case -> aggregate -> PO -> MySQL
MySQL -> PO -> reconstituted aggregate -> VO -> Response -> HTTP JSON
provider/PBX -> private transport adapter -> typed normalized call fact -> application ingress -> CallInteraction
authenticated human GET -> media authorization transaction -> typed private-adapter byte stream -> uncached same-origin HTTP body
authenticated human query -> tenant guard -> adapter capability + deployment read policy -> allowlisted observation -> VO -> Response
authenticated human upload/download -> target authorization transaction -> exact-generation storage port -> bounded proxy stream outside transaction
anonymous marketing FILE -> canonical public form + exact draft credential -> quarantined B24 stream -> atomic Lead FILE binding
composition-root pulse -> bounded work pump -> claimed durable tenant/kind/fence -> owning application handler -> tenant-scoped business transaction
composition-root pulse -> claimed OA publication occurrence -> tenant/announcement/current-authority transaction -> recipient snapshot + optional typed delivery
```

- `infra/rest` binds JSON and maps verified human authentication to `AuthenticatedCaller`; the B22 normalized ingress maps only a connector-authenticated infrastructure principal to `AuthenticatedConnector`.
- `infra/facade` owns the public Request/Response boundary and maps VO to Response without exposing domain objects.
- `application` validates Request input, creates domain value objects, and uses an Assembler only for aggregate -> VO -> Response output mapping.
- `infra/persistence` maps aggregate to PO and calls `reconstitute` on reads.
- Persistence converters are written explicitly; only `UserPOConverter` uses MapStruct. Where it is used it handles mechanical field mapping only, and validation, defaults, identity, version restoration, and event registration stay explicit either way.

Reporting keeps definition state and executable projections distinct. `ReportDefinition` is the versioned personal aggregate; `ReportDefinitionPO` plus named `filtersJson`/`measuresJson` properties are its storage representation; `ReportDefinitionVO` and `ReportDefinitionResponse` are application and public projections. `CustomReportQuery` is an immutable, fully resolved domain query passed to exactly one owning business repository, not a persistence model and not a public request. It contains typed field references rather than SQL identifiers or expressions.

`ProductQueryRequest.customSortFieldCode` is an API input only. `ProductQueryServiceImpl` resolves it under current PRODUCT field policy into the domain `ProductSort` value containing a definition ID, scalar type and direction; it never carries a caller-supplied SQL identifier. `ProductRepositoryImpl` owns the correlated `crm_product_field_value` order expression and accepts only that resolved domain value. POs and raw scalar storage stay in `infra/persistence`, while `ProductVO` remains the field-filtered application output.

`ReceivableQueryRequest.customSortFieldCode` and `ReturnVisitQueryRequest.customSortFieldCode` follow that same boundary. Their application services resolve a current active, non-built-in, readable and unmasked field to `ReceivableSort` or `ReturnVisitSort`; those domain values contain only definition ID, scalar type and direction. Their repositories own the corresponding correlated custom-value ordering expressions, including numeric casts, and never receive a request-controlled identifier or SQL fragment.

`ContractQueryRequest.customSortFieldCode` and `InvoiceQueryRequest.customSortFieldCode` follow the same boundary. Their application services resolve a current active, non-built-in, readable and unmasked CONTRACT or INVOICE scalar field to `ContractSort` or `InvoiceSort`; those domain values contain only definition ID, scalar type and direction. Their repositories own the corresponding correlated custom-value ordering expressions, including numeric casts, and never receive a request-controlled identifier or SQL fragment.

## Creation and reconstruction

- A `create...` method or domain factory creates new state and may raise a creation event.
- `reconstitute(NamedSnapshot)` restores persisted state by named fields and does not raise events.
- Methods such as `changeStatus`, `changeEmail`, and `delete` enforce state transitions.
- `onPersisted(...)` synchronizes generated identity, audit timestamps, and version after a successful write.

Aggregates do not expose public setters or use Lombok `@Data`. Define equality from aggregate identity or value-object value, not every mutable field.

`AuthenticatedCaller` stays at the API/application boundary. The application validates its tenant and passes a `TenantId` explicitly to domain, repository, and cache operations. Ordinary request bodies do not carry tenant identity, and repositories do not recover it from a `ThreadLocal`.

`AuthenticatedConnector` is the implemented B22a API/application context containing only a core-authenticated opaque `connectorRef`. A dedicated application guard resolves its current active registration to a tenant before business access. It must not grow nullable actor, tenant, role, authority, external-agent, or connection-generation fields, and it must never be constructed from a normalized fact body. The narrowly scoped credential and identity projections are separate application security output ports rather than a general unscoped domain repository. B22a's probe deliberately has no fact body; later call-ingress commands must call the guard's tenant-scoped registration lock before their first business write.

B22 sensitive values use dedicated purpose-named types and capabilities, not ordinary strings hidden in a generic request, VO, event, map, or JSON column. A human request selects a CRM record and field; the application creates an encrypted call-address snapshot. Connector ingress carries a dedicated one-shot sensitive address or opaque recording reference beside, never inside, the normalized lifecycle fact map. Plaintext holders must disable default JSON serialization and use a fixed redacted `toString`; persistence POs contain only bounded envelope/fingerprint fields and key versions. Crypto and media implementations belong to `infra/security` or a private external adapter behind narrow application ports, while domain/application retain normalization, policy, expiry, and access semantics. See [B22 section 14](../batch-B22.md#14-b22-d-敏感数据录音访问与保留设计闭合).

For B22-S, `CallInteraction` owns lifecycle milestones and at most two normalized `CallLeg` children. A `CallLeg` uses an immutable `AGENT` or `REMOTE_PARTY` role and an opaque connector-scoped external reference; it is not a PO-shaped copy of a Twilio Call, Asterisk channel, FreeSWITCH channel, bridge, endpoint, or device. Dispatch status, observation/reconciliation status, and recording availability remain named concepts beside lifecycle instead of nullable fields folded into one generic status. Adapter capabilities and member endpoint projections belong to typed application output ports. Device identifiers, extensions, SIP URIs, registrations, tokens, native errors, headers, variables, and arbitrary topology maps do not enter domain or public Request/Response types.

For B22-M, a human media request still maps to `AuthenticatedCaller`; it never uses `AuthenticatedConnector` or a media bearer grant. Application authorization creates a same-call-stack, non-serializable open value after writing the minimal access attempt in a short transaction. The external adapter receives tenant/connector scope, a purpose-specific decrypted opaque recording reference, normalized WAV/MP3 kind, optional single byte range, deadlines and cancellation. It returns only typed metadata plus a closeable/backpressured byte source. `URL`, `URI`, `Path`, `File`, `byte[]`, HTTP response/header maps and provider SDK objects remain infrastructure-private and cannot appear in domain, VO, Response, event, outbox, audit or persistence objects. See [B22-M](spikes/B22-media-transfer.md).

For B22-A, lifecycle, readiness and member endpoint capability remain separate types. The planned core snapshot exposes only fixed operation results, freshness, safe reason classifications and opaque build/binding evidence. Provider account, app, node, callback route, credentials, native resource identifiers, raw errors and isolation implementation details remain private; they do not become domain enums, public requests, generic maps or persistence-shaped provider models. Private adapter artifacts depend only on published application/API contracts and cannot access core repositories, mappers, POs or datasource. See [B22-A](B22-A-adapter-readiness.md).

B22-CP is a test-only composed contract, not a new runtime layer or a generic provider event model. Its driver controls stream ownership, durable crash points, native-frame delivery and read-only reconciliation; its independent oracle reads bounded test projections of the adapter stores and core state. Native frames, channels, bridges, connection generations and fencing tokens remain private adapter fixture inputs. Only the already planned typed facts cross into the core. A provider implementation cannot place its expected-state calculator behind the oracle interface or expose test-only snapshots through production ports. See [B22-CP](B22-CP-pbx-composed-contract.md).

B22-PC is likewise a test-only composition, not a production command API or a provider command abstraction. Its driver can claim a core outbox, deliver one typed start, inject durable crash points, advance a virtual clock, emit a governed PBX event and run read-only reconciliation. The independent oracle distinguishes the core outbox, adapter ledger/result delivery and provider invocation/logical-object stores. Provider keys, dial strings, native command maps, SDK responses, query cursors and test effect projections remain private infrastructure inputs; none become domain, Request/Response, VO, event or ordinary outbox fields. See [B22-PC](B22-PC-pbx-command-contract.md).

For the implemented B23a read kernel, `RegisteredIdentifier` keeps `identityScope`, `registryScheme`, `canonicalValue`, and identifier standing distinct. Optional `LegalJurisdiction` and coarse entity status are sibling profile facts, not nullable fields folded into the identity key. Scheme-specific catalog rules own characters, length, segment structure, governed department/category pairs, leading zeros, checksum, explicit Companies House number classes, and allowed scope/scheme pairs; the existing generic identifier normalizer is not a registry-identity validator. `GB_CH_NUMBER` retains its full eight-character value and rejects an unknown prefix rather than repairing it through a generic alphanumeric regex. Provider IDs, source locators, accounts, connector references, names, addresses, raw statuses and arbitrary maps remain outside domain identity. Adapter facts also do not own permission or attribution: the application intersects them with `EnterpriseDataReadPolicy`, and B23a caps the public result at `EPHEMERAL_ONLY`.

The Customer-owned semantic relation remains a B23-XI design: one Customer to many registered identities, with a dedicated persistence reservation making each exact identity key belong to at most one non-deleted Customer per tenant. B23a does not implement that relation, reservation, adoption provenance, or Customer write. It is not a configurable B05 unique field and not an independently addressable provider profile aggregate. See [B23-XI](B23-XI-registered-identity.md).

For B24-S, storage binding, locator and generation are application/persistence concepts rather than file-domain or public identities. A planned locator is persisted before byte I/O and a stored identity remains opaque; application can compare it for exact equality but cannot parse a bucket, version, path or filesystem name. Domain content evidence contains only exact actual bytes and canonical SHA-256, never provider metadata. The typed storage port separately exposes allocate, single-stream store, exact probe, full/single-range open, exact delete, absence confirmation and incomplete cleanup. Read handles are non-serializable, closeable, cancelable and bounded; `URL`, `URI`, `Path`, `File`, `byte[]`, HTTP headers, SDK streams/responses and provider exceptions stay in `infra/external`. Multipart is not hidden inside the first contract. See [B24-S](B24-S-storage-readiness.md).

B24-I treats an inspection subject, type evidence, scanner evidence, readiness snapshot and core conclusion as distinct concepts. ClamAV commands/replies, Tika detectors/parsers, AWS events/tags/findings, sockets, paths, bucket/key/version fields, threat names, parser metadata and provider errors remain in `infra/external`; none becomes a public Request/Response, domain enum, PO-shaped provider model, generic map, event or audit payload. Container-aware detection is an isolated infrastructure process, not a library call that turns the core JVM into the parser sandbox. See [B24-I](B24-I-content-inspection.md).

B32a assigns public pipeline/stage requests and responses to `api`, the independently versioned `OpportunityPipeline` and `OpportunityPipelineStage` roots plus exact code/lifecycle policy to `domain`, and permission, tenant-catalog guard, bootstrap, cross-root activation rules and Opportunity-pair validation to `application`. Persistence owns V85, binary code columns, POs/converters/mappers, the MySQL guard and same-tenant pair foreign key. The catalog is not a B05 option list or a B11 workflow child: B05 continues to govern the Opportunity code fields, while workflow-local stages retain their own aggregate and runtime. There is no generic business catalog, arbitrary object/code map or reflective router. See [B32](../batch-B32.md) and [B32a acceptance](acceptance/B32a.md).

## Naming conventions

| Concern | Convention |
| --- | --- |
| Application write policy | `CommandServiceTemplate` |
| Application read policy | `QueryServiceTemplate` |
| Use-case lifecycle | `ServiceOperation<T>` |
| Public interface | Business name without an `I` prefix, such as `UserService` |
| Implementation | `*Impl` only for a meaningful interface |
| Output port | Business capability, such as `CacheStore` or `PasswordHasher` |
| Adapter | Technology plus capability when useful, such as `RedisCacheService` |
| API mapping | `*Assembler` or explicit static mapper methods |
| Persistence mapping | `*POConverter` |
| Repository port | `*Repository` in `domain` |
| Repository adapter | `*RepositoryImpl` in `infra/persistence` |
| Configuration | `*Config` or `*Configuration`, consistently within a package |
| Exception | Specific cause, not a catch-all name |
| Test | Class under test plus `Test`; integration intent visible in the name |

Avoid `Abstract*` on concrete Spring beans. Use `Request`, `Response`, `VO`, or a domain term instead of a generic `DTO` when the role is known.

## Error names

| Type | Meaning |
| --- | --- |
| `DomainException` | Stable domain failure with a domain error classification |
| `ApplicationException` | Application workflow failure that may be retried according to policy |
| `NonRetryableApplicationException` | Stable application rejection |
| Infrastructure exception | Translated at the adapter boundary or by a dedicated mapper |

Public errors expose a stable code and safe message, never an arbitrary internal exception message. Specific names include `UserNotFoundException`, `UserAlreadyExistsException`, and `AggregateVersionConflictException`.

## Persistence and collections

Java fields use camelCase and SQL columns use snake_case:

| Java | SQL |
| --- | --- |
| `tenantId` | `tenant_id` |
| `phoneNumber` | `phone_number` |
| `externalUser` | `is_external_user` |
| `passwordHash` | `password` (explicit legacy mapping) |
| `createdTime` | `created_time` |
| `updatedTime` | `updated_time` |
| `optionsJson` | `options_json` |

Persistence converters map every PO field in both directions, including `version` and audit timestamps. The optimistic-lock field is `version` in every layer. A JSON column is represented by a named `*Json` PO property and is decoded into validated domain types by the converter; domain objects do not expose raw JSON. Avoid Java property names that force SQL reserved words as generated aliases. Soft deletion uses `status=DELETED`; there is no `deleted_time` field.

Aggregate-owned collections may use separate child POs and tables while remaining one domain aggregate. For example, `CustomerAddressPO`, `CustomerTagPO`, `CustomerCollaboratorPO`, and `CustomerFieldValuePO` are hydrated in batches and reconstructed into one `Customer`; `CustomerPoolAdministratorPO`, `CustomerPoolEligibleMemberPO`, `CustomerPoolEligibleDepartmentPO`, and `CustomerPoolRulePO` reconstruct one `CustomerPool`. Public APIs never expose those persistence types, and child writes share the root command transaction and version check. Current pool membership and append-only claim history are persistence relations with named domain records, not mutable fields smuggled into the pool aggregate as JSON.

Repository single-result queries return `Optional<T>`, collections return an empty list rather than null, and domain pagination uses `PageResult<T>`. Convert it to public `Pager<T>` outside the domain boundary. Validate required input at the nearest trusted boundary and enforce domain invariants again in value objects.

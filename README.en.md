# atom-crm

[简体中文](README.md)

[Quick start](#quick-start) · [Deployment](docs/deployment.md) · [Contributing](CONTRIBUTING.md) · [Security](SECURITY.md) · [Changelog](CHANGELOG.md)

Repositories: [backend atom-crm](https://github.com/Archetom/atom-crm) · [frontend atom-crm-web](https://github.com/Archetom/atom-crm-web).

`atom-crm` is a Java 25 and Spring Boot 4.1 multi-module Maven project generated by Atom Archetype. It includes user and organization management, tenant authorization and customization, customer/contact/lead/opportunity/product aggregates, record pools, and public lead intake. User queries return the named `UserPageResponse` page and typed `UserResponse` items so generated clients retain complete pagination types.

R1 coordinates: `io.github.archetom:atom-crm:1.0.0`. See the [R1 release scope](release-R1.md) for the frozen 1.0 boundary, deployment gates, and explicit deferrals. This repository provides the backend API. The browser application lives in the separate `atom-crm-web` repository; run both for the complete CRM.

## Requirements

- JDK 25
- Bundled Maven Wrapper 3.9.16
- Docker with Docker Compose for local MySQL and integration tests
- Make (optional)

Redis is disabled by default and is not required to build or start the project.

## Quick start

From this repository root, start MySQL and build all modules:

```bash
docker compose up -d mysql
sh ./mvnw clean install
```

Run the application with the `dev` profile:

```bash
sh ./mvnw -f start/pom.xml spring-boot:run -Dspring-boot.run.profiles=dev
```

Check the health endpoint:

```bash
curl http://localhost:8080/actuator/health
```

Configuration files are stored in `conf/`. Development API documentation is available at `http://localhost:8080/swagger-ui/index.html`.

### Start the frontend

Use the frontend repository link above to obtain the matching `atom-crm-web` version and check it out into a separate directory. From that directory, use the Node.js and pnpm versions specified by its `.node-version` and `package.json`:

```bash
pnpm install --frozen-lockfile
pnpm dev
```

Open the local URL printed by the frontend server. Its same-origin `/api` proxy defaults to `http://localhost:8080`; set `VITE_API_PROXY_TARGET` using the frontend `.env.example` when the backend uses a different address. The committed OpenAPI snapshot and generated types are sufficient for a first run. Refresh them after API changes following the frontend `openapi/README.md`. Release the two repositories as a tested pair and record both commit IDs in release notes.

### First installation

Ordinary use does not require development identity headers. On a fresh database, open the frontend `/setup` page. It checks `GET /api/v1/installation` and submits `POST /api/v1/installation/tenant-admin` to create the workspace 1 owner and a browser session atomically. There is no default administrator username or password. Restrict a new deployment to its operator until initialization is complete. Later sessions use `/login` with the credentials you chose. Installation closes once an active owner exists; it is not a password recovery mechanism.

### Production deployment

The commands above are for local development. See the [deployment guide](docs/deployment.md) for build, container, and release checks, and [.env.example](.env.example) for production variable names without real credentials. Spring Boot does not automatically load `.env`; inject it through your deployment platform or container. For `prod`, provide database credentials, a stable session-signing key, an HTTPS same-origin proxy, and the password-reset landing URL following [production configuration](docs/configuration.md#production-settings). Welcome notifications require SMTP (`ATOM_USER_NOTIFICATION_MAIL_ENABLED=true`, `ATOM_USER_NOTIFICATION_MAIL_FROM`, and `spring.mail.*`) or your own `UserNotificationPort` adapter. Password-reset mail has a separate switch. Do not use development identity headers or the local Compose database passwords in production.

Files, enterprise data, calling, and background automation have separate deployment prerequisites. Their source or test fixtures do not imply production readiness. Verify the [R1 scope and release gate](release-R1.md) and the paired frontend/backend revisions before distributing a release.

## Project structure

| Module | Responsibility |
|---|---|
| `api` | Public requests, responses, facade contracts, and `AuthenticatedCaller` |
| `domain` | Aggregates, value objects, domain events, repository and domain-service ports |
| `application` | Use-case orchestration, command/query templates, output ports, and transaction callbacks |
| `shared` | Framework-neutral result and error types |
| `infra/rest` | Spring MVC, Spring Security, and HTTP error mapping |
| `infra/persistence` | MyBatis-Plus, Flyway, and cache adapters |
| `infra/external` | Third-party system adapters |
| `infra/security` | Password hashing and other security adapters |
| `infra/facade` | Facade contract implementations |
| `start` | Spring Boot composition root and integration tests |

Dependencies flow from `infra` to `application` to `domain`. The `domain` module does not depend on `application`, `api`, or any `infra` module. See [Architecture](docs/architecture.md) for the complete rules.

## Configuration

- `conf/application-dev.yml`: local development settings.
- `conf/application-test.yml`: automated test settings.
- `conf/application-prod.yml`: production settings, with no default datasource credentials.

The `X-Dev-User-Id` and `X-Dev-Tenant-Id` headers are limited to explicitly enabled `dev` and `test` environments. Normal browser access uses the implemented password login, HttpOnly session cookie, and same-origin CSRF protection. Production requires a signing key, HTTPS, and a same-origin proxy; see [browser authentication configuration](docs/configuration.md#browser-password-authentication).

Organization APIs live under `/api/v1/organization`; membership relationships are explicit records between a verified actor and tenant. Department structure writes and target-tenant membership submission serialize on the target tenant, while `GET /membership-requests/mine` pages only the verified applicant's own requests under `organization:request`; it never enumerates target tenants, departments, or other applicants and does not change credentials. Authorization and navigation live under `/api/v1/authorization` and `/api/v1/navigation`. Customization APIs under `/api/v1/fields`, `/api/v1/saved-views`, and `/api/v1/embedded-pages` keep field metadata and role field policy tenant scoped, while layouts and saved views belong to the current member. Field lifecycle changes and layout or saved-view writes are serialized per `(tenant, objectType)`; lifecycle changes reject remaining dependencies, and reads fail closed against the current field catalog. Saved filters are bounded typed structures rather than executable queries. Field metadata also publishes server-determined `filterOperators` for each field, including each operator's accepted minimum and maximum value counts. Saved-view list, create, update, and default operations return the named `SavedViewResponse`, while deletion has an explicit empty response. Embedded pages only render validated HTTPS URL templates, and the server never fetches their targets.

Customer APIs live under `/api/v1/customers`. Core details, tags, addresses, collaborators, hierarchy, and custom values are persisted atomically under one optimistic-lock version. Tags retain their display names, while add/remove operations, deduplication, and the catalog share a separately persisted NFKC/lowercase key. Reads apply the caller's `SELF`, `DEPARTMENT`, `DEPARTMENT_SUBTREE`, or `TENANT` data scope and then narrow output through field access and masking; masked time fields never expose exact values. Non-blank name, owner, duplicate, nearby, and tag predicates additionally require unmasked readable fields. Hierarchy bounds are applied after record visibility, while writes guarantee that a complete hierarchy tree stays within 64 levels and 2,000 nodes. Every customer aggregate save is serialized with field lifecycle changes per `(tenant, CUSTOMER)`, and custom-field uniqueness is immutable after creation. Deletion is `status=DELETED`, never a physical row removal.

`GET /api/v1/customers/{customerId}/business-overview` is a customer-first, permission-aware fixed overview. After proving the exact customer is currently visible, it returns seven stable source cards; each independently applies its own read authority, data scope, lifecycle predicate, and unmasked required fields. A denied source is represented by an opaque `UNAVAILABLE` card without count or amount, and customer visibility never widens a source domain.

Customer-pool APIs live under `/api/v1/customer-pools`. Pool configuration, administrators, eligible members/departments, and automatic-release rules form a versioned tenant aggregate; a tenant can retain at most 500 non-deleted pools, and one customer can belong to at most one pool. Releasing a customer requires the independent `customer-pools:release` capability and remains constrained by the caller's `customers:write` data scope; claim, assignment, and pool deletion use separate capabilities. Entry changes the customer to `IN_POOL` and removes ownership and collaborators, while claim or assignment restores `ACTIVE`. MySQL row locks and claim history arbitrate daily limits, previous-owner cooldowns, and concurrent claims; manual and automatic entry also append a durable release history event in the same transaction. Pool reads still apply B05 field access and masking, and return a parent relationship only when the parent remains in the same accessible pool. The member catalog applies all eligibility predicates in the database through a lightweight root projection, tenant owners can see every active pool, the current member's administrator flag is projected without loading configuration relations, and customer counts are aggregated in one batch. Automatic release persists a per-tenant pool-ID rotation cursor, scans at most 50 pools per invocation in pages of 25, and resumes from the last position so later pools are not starved; B26a now supplies its durable production scheduling and distributed execution boundary.

B26a implements the unified scheduling and automation-kernel boundary for Customer/Contact pool automatic release: durable fixed-kind schedules and runs, shared MySQL UTC, cross-replica leases/fences, stable evaluation time, bounded retries, monotonic revision reconciliation, and safe operations evidence. Background execution never fabricates an `AuthenticatedCaller`. B24 attachment workers only moved to the common composition-root wake-up surface and retain their own job ledger, readiness, external-I/O, and recovery semantics. Scheduling remains disabled by default. See the [B26 plan](batch-B26.md) and [B26a acceptance record](docs/acceptance/B26a.md).

B27a/B27b implement Work recurrence, durable reminder occurrences, and the current-member in-app inbox. B27c adds an optional EMAIL transactional outbox: the self-only `/api/v1/notifications/preferences` endpoint accepts only `emailEnabled` and defaults to off. Readiness is preflighted before a row is claimed and rechecked under task → notification → delivery locks with current membership, authority, task visibility, preference, and a server-resolved profile endpoint before provider I/O. First dispatch freezes the guarantee, original idempotency window, and a tenant/purpose-scoped HMAC endpoint binding with its key version. `IDEMPOTENT_SEND` reuses only that exact command inside the original window; once effect certainty is ambiguous, deadline, retry exhaustion, stale-task handling, or admission recovery preserves `AMBIGUOUS` rather than claiming no provider effect. Provider dispatch is bounded by the remaining lease/deadline budget after settlement reserve; a lost settlement fails the lane. Ledger deadline/retention maintenance remains active while the channel is disabled, and terminal delivery retention cannot extend notification-content retention. `ACCEPTED` means provider acceptance only. EMAIL remains disabled by default and the sample welcome logging path is excluded. See the [B27 plan](batch-B27.md) and [B27c acceptance](docs/acceptance/B27c.md).

B28a/B28b implement one-shot scheduled OA-announcement publication and reliable EMAIL integration. The publication coordinator atomically commits the announcement root, immutable recipient snapshot, and outbox rows for currently opted-in members who still hold `notifications:read` and `oa-announcements:read`. `crm_notification_delivery` is a closed typed source over `WORK_TASK_NOTIFICATION` and `OA_ANNOUNCEMENT_RECIPIENT`; existing Work commands retain their digest, `b27c:` idempotency key, HMAC binding, guarantee, and admission semantics. The independent `oaAnnouncementEmailEnabled` preference defaults off, and the OA template includes only announcement ID, title, and actual publication time—never body or audience. Withdrawal/deletion suppresses rows that have not crossed dispatch, while any uncertain provider effect remains `AMBIGUOUS`. Publication, in-app read, and provider acceptance remain distinct facts. See the [B28 plan](batch-B28.md), [B28a acceptance](docs/acceptance/B28a.md), and [B28b acceptance](docs/acceptance/B28b.md).

B29a/B29b/B29c/B29d implement the bounded file boundary. B29b lets active MarketingForms configure custom LEAD `FILE` fields and create candidates through a one-time anonymous draft credential whose purpose-separated digest is the only persisted credential evidence. A public candidate names its exact draft as upload origin and never impersonates the form owner as a member. Submission atomically locks the form/LEAD guard/draft/candidates, creates the Lead, publishes and binds the exact READY set, consumes the draft, and appends attribution. Public routes expose neither downloads, scanner details, nor internal identities; `atom.files.public-marketing.enabled` remains false by default. B29c adds draft-only OA announcement attachments with an immutable publication set. B29d adds ordinary post-submit OA Request collaboration attachments at `/api/v1/attachment-targets/oa-request/{requestId}/attachments`: writing requires `files:write`, `oa-requests:read`, `oa-requests:collaborate`, active membership, and applicant/current-pending-assignee/instance-manager participation. Approval terminal transitions withdraw every non-`AVAILABLE` candidate and freeze the remaining available set; immutable OA submission FILE facts, route snapshots, and digests are unaffected. See the [B29 plan](batch-B29.md), [B29c acceptance](docs/acceptance/B29c.md), and [B29d acceptance](docs/acceptance/B29d.md).

B30a implements a permission-aware, bounded Customer CSV export at `POST /api/v1/customers/export/csv`. It intersects owner-derived `customers:export` scope with existing `customers:read` visibility, exports only explicitly selected current readable/unmasked scalar fields, and completes one UTF-8 BOM document before the HTTP body starts. Output is fixed to `customer_id ASC`, RFC 4180 quoting, stable field-code headers, formula hardening, and 5,000-row/50-field/16-MiB limits. It neither reuses B24 nor pre-allocates import, Excel, cross-object, asynchronous-artifact, or bulk-migration contracts. See the [B30 plan](batch-B30.md) and [B30a acceptance](docs/acceptance/B30a.md).

B31a implements the equivalent permission-aware, bounded Contact CSV export at `POST /api/v1/contacts/export/csv`. It intersects owner-derived `contacts:export` scope with ordinary `contacts:read` visibility, retains Contact collaborator, pool, Customer and parent-contact relation safeguards, and accepts only the frozen selected scalar-field request contract. Output is fixed to `contact_id ASC`, UTF-8 BOM, RFC 4180 quoting, formula hardening, and the same 5,000-row/50-field/16-MiB limits. See the [B31 plan](batch-B31.md) and [B31a acceptance](docs/acceptance/B31a.md).

B33a implements the equivalent permission-aware, bounded Lead CSV export at `POST /api/v1/leads/export/csv`. It intersects owner-derived `leads:export` scope with ordinary `leads:read` visibility; preserves Lead keyword, name, owner, subordinate-owner, star, converted and saved-view/temporary-filter semantics; and rechecks Customer and parent-Lead filter targets under current visibility. Output is limited to selected readable/unmasked scalar fields in fixed `lead_id ASC` order with UTF-8 BOM, RFC 4180 quoting, formula hardening, and 5,000-row/50-field/16-MiB limits. See the [B33 plan](batch-B33.md) and [B33a acceptance](docs/acceptance/B33a.md).

B32a implements the tenant Opportunity sales-pipeline and stage catalog. The catalog uses immutable, case-sensitive exact codes, independently versioned pipelines and stages, dedicated non-data-scoped `opportunity-pipelines:read/manage` capabilities, a database catalog guard, optimistic locking, and same-tenant composite foreign keys. V85 backfills existing pairs without rewriting them, while new tenants receive active `direct/qualification` and `direct/negotiation` defaults. Deactivation blocks only new assignment or an actual move, while an existing Opportunity remains readable, filterable, and editable when its pair is unchanged. B05 continues to own access policy for the two `TEXT` fields, and B11 workflow stages remain a separate namespace with no implicit synchronization. See the [B32 plan](batch-B32.md) and [B32a acceptance record](docs/acceptance/B32a.md).

Contact and contact-pool APIs live under `/api/v1/contacts` and `/api/v1/contact-pools`. Contacts are independent versioned aggregates with their own scopes, tags, collaborators, hierarchy, job title, next-contact time, field policy, and pool membership. Their optional customer link is accepted only after the caller can see that tenant-local customer, is suppressed again unless the current customer visibility allows it, and can be explicitly cleared with `customerId: null`; `nextContactTime: null` explicitly clears the optional time. Saved-view customer and parent-contact conditions permit only visible `EQ`/`IN` targets, preventing relationship visibility inference. Contact pools use separate `contacts:*` and `contact-pools:*` capabilities and persistence relations while retaining the bounded claim, cooldown, transfer, and fair automatic-release rules.

Lead APIs live under `/api/v1/leads`. Leads have independent field policy, data scopes, tags, collaborators, addresses, hierarchy, saved views, and optimistic locking. `POST /api/v1/leads/{leadId}/convert` creates a customer and contact in one transaction, then persistently associates both through the immutable converted lead's `customerId` and `convertedContactId`. Converted leads remain queryable and readable, but cannot be changed or converted again. Public submission is restricted to `POST /api/v1/open/leads` with `X-API-Key: <tenantLocator>.<keyId>.<secret>`; the locator must use canonical unpadded Base64URL encoding to scope the tenant lookup, and the case-sensitive key ID identifies the client within that tenant, while tenant and owner derive solely from an active intake client verified by its secret. Client creation also requires that owner to currently hold `leads:write`, a usable lead data scope, and write access to `lead_name` and `owner_actor`. Every public submission remains subject to that owner's current business and field policy, so revoking a baseline permission or supplying an optional field without current write access rejects the request. The server generates each credential, returns the complete `apiKey` only in that creation response, then stores only its hash and never logs it; the migration that introduces this form deactivates legacy two-part keys, so replacement clients must be created. Each tenant has at most 100 active clients. Authentication atomically reserves a source in-flight slot before lookup, releases it after verification, counts it only on credential failure, and cancels it after authentication-infrastructure failures; exhausted verified keys are rejected before another lookup. Unknown credential fingerprints stay in a separate bounded pending cache until their secret verifies, so forged credentials cannot occupy per-tenant verified-key capacity. The key ID is attached to the reservation before lookup, so deactivating a client immediately invalidates settled or in-flight local buckets to admit a replacement. Verified keys default to 60 submissions per minute; source buckets and tenant-partitioned verified-key buckets are bounded and expiring, and live tenant windows are never evicted to admit a new tenant. Deployments behind a reverse proxy must configure trusted proxy addresses or enforce source limits at the gateway.

Opportunity APIs live under `/api/v1/opportunities`. An opportunity is a tenant-scoped versioned aggregate that atomically owns its required customer, owner, pipeline/stage, expected close values, related and primary contacts, collaborators, and OPPORTUNITY custom values. `opportunities:read/write/delete/assign` resolve independent record scopes; relationship writes and output also fail closed through the caller's current customer and contact visibility, owner assignment is bounded by the assignment grant's scope, and an ordinary collaborator can remove only themselves through a dedicated endpoint. Direct queries, typed saved views, and amount summaries require the governing field to be unmasked readable; saved values are type-validated and normalized before SQL, while MySQL arbitrates custom uniqueness. Outcomes are `OPEN`, `WON`, `LOST`, and `INVALID`, and replacing or clearing an outcome remark always requires field write access; closed records remain readable but must be explicitly reopened before ordinary mutation. B24 now provides governed attachments and FILE fields; B25a now supplies the customer-context seven-source overview without widening any source domain's visibility.

Approval and stage-workflow APIs live under `/api/v1/approval-definitions`, `/api/v1/approvals`, and `/api/v1/stage-workflows`. Definitions use bounded typed B05 field conditions and active tenant members or roles; inactive roles never resolve retained assignments. Public preview and submission read authoritative condition values from the owning business aggregate, so request `facts` cannot rewrite the route. Stage gates start from the authoritative record snapshot and permit only B05-`WRITE`-validated pending values to override it. Submission snapshots the definition version, normalized facts, managers, and resolved route, so later configuration changes cannot rewrite runtime access or cancellation rights. Approval and stage snapshots omit hidden fields and apply the caller's current masks. Every runtime read, action, batch, withdrawal, cancellation, page, and pending count reapplies the owning customer, contact, lead, opportunity, contract, or invoice scope; hidden records neither consume page slots nor contribute to totals. Customer, contact, opportunity, and contract IDs captured in contract/invoice facts are also rechecked against each relationship domain's current read scope and are consistently omitted from details, summaries, and pages when hidden. Pages scan lightweight references and fetch root-only summaries for the final response page, while batch actions also return summaries without task history; the single-instance detail endpoint provides the full task, manager, and watcher timeline. Public idempotency keys are trimmed consistently for lookup and persistence and cannot claim the reserved `stage:` namespace. Every dynamic assignee source is capped at 100 unique active members, and normalized applicant-selected step keys must remain unique. The initial route and transfer history share a 5,000-task cap, `ONCE` rejects transfers to earlier approvers, and persistence inserts replacements or updates only tasks whose state changed. Sequential, all, any, repeat, withdrawal, cancellation, and sorted atomic batch actions remain versioned and database-arbitrated. Stage start reloads current configuration under the object lock, active workflows only reference active approval definitions, generated gate titles are capped at 200 characters, and the required/condition field union is validated against the 100-fact limit from both workflow and approval-definition mutations. Required values must normalize non-empty, and referenced fields cannot be deactivated or made non-searchable. Null collection elements fail closed at transport and application boundaries, comments remain author/version guarded, and every repository operation stays explicitly tenant scoped.

After a stage gate is rejected, cancelled, or withdrawn, the first `advance` only consumes that terminal result and restores `ACTIVE`; a later explicit call recaptures fields and increments the approval attempt. A workflow cannot be soft-deleted while any `ACTIVE` or `AWAITING_APPROVAL` runtime record remains, so its field and approval-definition dependencies stay protected.

Product and category APIs live under `/api/v1/products` and `/api/v1/product-categories`; opportunity product snapshots use `/api/v1/opportunities/{opportunityId}/products`. The tenant-shared catalog uses the non-data-scoped `products:read/write/delete/assign` capabilities. Category writes share a database guard, with a 16-level and 5,000-active-node bound; cycles, normalized sibling-name collisions, dependency deletion, and optimistic conflicts fail closed. Product codes are tenant-unique by an NFKC/lowercase key, PRODUCT custom fields use the common field policy, and MySQL arbitrates custom uniqueness; deletion only writes `status=DELETED`. An opportunity stores at most 100 server-validated snapshot lines after checking opportunity write access, `products` field write access, product read capability, and current availability. Product name, code, category, unit, and list price must also be readable without a PRODUCT mask. The catalog guard is acquired before the transaction's first consistent read so the product and category snapshot comes from one catalog state; product roots/custom values and opportunity roots/snapshot lines are also hydrated in read-only `REPEATABLE_READ` transactions. Discount and line amount are server-calculated, and later catalog edits, withdrawal, or deletion cannot rewrite historical opportunity values.

Contract, invoice-application, and invoice-profile APIs live under `/api/v1/contracts`, `/api/v1/invoices`, and `/api/v1/invoice-profiles`. Contracts and invoices use independent `contracts:*` and `invoices:*` data-scoped capabilities plus CONTRACT/INVOICE field policy, with explicit HTTP authorization per route; an assigned owner must also fall within that operation's `assign` scope. Before replacing contract collaborators, `GET /api/v1/contracts/{contractId}/collaborators` returns an authoritative baseline within the `contracts:assign` owner scope: the contract `version`, the complete `actorId/access` collaborator list, and the caller's `callerState` (`OWNER`, `READ`, `WRITE`, or `NONE`). An empty list therefore means that no collaborators exist, never that the caller lacks viewing scope. Contracts, invoice profiles, invoices, receivables, and receivable plans expose versioned `PATCH` updates; their corresponding `PUT` requests have the same safe partial-update semantics: only submitted non-`null` fields change, omitted or `null` fields retain their current values, and `version` is required. A masked detail field or historical relation therefore cannot be overwritten accidentally. Contract lines accept only a product ID, quantity, and optional sale price; catalog display values are snapshotted and all discounts and amounts are calculated by the server, while an empty product collection requires no product-read capability. Contract number keys are tenant-unique after NFKC/lowercase normalization, with both post-normalization length and aggregate `DECIMAL(22,2)` precision checks. Invoice customer identity is derived from the locked contract and backed by a tenant/contract/customer composite foreign key. Composite customer foreign keys also keep a contract's optional opportunity and contact on the same customer after later relationship changes, with save-side constraint races mapped to stable domain errors. Invoice creation or amount changes and contract amount changes serialize on the contract row, so committed non-deleted invoice totals cannot exceed the contract and a contract with invoices cannot change customer. Issue, reset, and owner-change responses independently reapply customer and contract visibility. Invoice profiles soft-delete through `status=DELETED`, reapply customer visibility inside the actual read or write transaction, and are limited to 100 active rows per customer under serialized creation and bounded queries. Blank keywords are treated as no search. New tenant bootstrap provisions both built-in field catalogs. CONTRACT and INVOICE are also available to the B11 authoritative-fact approval runtime.

Receivable and receivable-plan APIs live under `/api/v1/receivables` and `/api/v1/receivable-plans`. They use separate `receivables:*` and `receivable-plans:*` data-scoped capabilities and RECEIVABLE/RECEIVABLE_PLAN field policies. Both records derive their customer from the contract, and tenant/contract/customer composite foreign keys preserve that relationship. Their edits follow the B13 versioned partial-update contract: `PATCH` and `PUT` change only submitted non-`null` fields, while omitted or `null` values retain the current value. Receipt creation and amount replacement lock the contract before arbitrating active totals; receipts cannot exceed the contract or their selected plan. Planned totals likewise cannot exceed the contract, and a plan with receipt history cannot change or be deleted. Received, remaining, and progress values are computed from active receipts; fully settled plans are absent from the available-plan endpoint. A contract cannot be reduced below received amount or deleted once it has receivable or plan history. RECEIVABLE is available to the B11 authoritative-fact approval runtime, with current record and relationship visibility reapplied. V40 provisions the built-in fields for existing tenants.

Activity, return-visit, and worklist APIs live under `/api/v1/activities`, `/api/v1/return-visits`, and `/api/v1/worklist`. Activities are versioned subject-anchored timelines: every subject and related record is checked through its owning domain, follow-up methods/templates are governed tenant options, and only caller-authored follow-ups are mutable. Return visits use independent data scopes and RETURN_VISIT field policy, require a customer, and enforce that optional contact/contract relations belong to that customer; a field-safe simple option route is available. Omitted `contactId` and `contractId` values retain their relations on a return-visit update, while an explicit `null` clears one; their OpenAPI 3.1 schemas permit `integer` or `null`. Details label each optional relation as `VISIBLE`, `HIDDEN`, or `EMPTY` so a client cannot mistake a hidden link for an empty one. The worklist uses an opaque nine-source cursor to stably merge customer activities, contacts, leads, opportunities, return visits, receivable-plan reminders, contract expiry, assigned pending approvals, and due Work tasks assigned to the caller. Every request reapplies each source's capabilities, data scope, field policy, or dedicated participation predicate. Exact or category acknowledgements are stored separately per tenant/member and include source version and due time, so changed items reappear without mutating business records; category verification fails closed without writing partial results when its bounded scan cannot reach the final page. The `v3` cursor accepts old `v2` continuations while treating Work tasks as exhausted for that legacy pagination chain, preventing mid-stream insertion.

B16b gives the customer, contact, lead, opportunity, product, and return-visit lists one `keyword` contract. The trimmed keyword is bounded to 200 Unicode code points and blank input means no search. Server-owned candidates are intersected with current active, searchable, readable, and completely unmasked field policy; hidden or masked fields never participate, and no surviving candidate returns an empty page. Text uses escaped literal-prefix matching, while product code uses its NFKC/lowercase key. Verified tenant, per-object data scope, active/soft-delete state, and ordinary customer/contact pool exclusion remain outside and restrictive around the keyword predicate.

B16c extends the same field-aware `keyword` contract to contract, invoice-application, receivable, and receivable-plan lists. Contract names, invoice application numbers/titles/invoice numbers, and receipt numbers use literal prefixes; contract numbers use their NFKC/lowercase key; plan keywords match an exact positive installment and unparsable input returns an empty page. Payment methods are no longer keyword candidates. Each query remains restricted by its verified tenant, data scope, status, and current field policy.

The B17a core report is `GET /api/v1/reports/core`. It returns the caller-visible OPEN/WON/LOST opportunity funnel, active-contract count and amount, and active-receipt count and amount. `reports:read` only authorizes entry: the application independently resolves the current `opportunities:read`, `contracts:read`, and `receivables:read` scopes, never creates a shared reporting scope, and rejects the entire response if any source is unavailable. The report also requires unmasked read access to exposed amounts and to the `outcome` and `status` fields that define its buckets and active-contract predicate. Field-policy reads and all aggregates share one read-only snapshot, so a report cannot expose fields or records outside the underlying business routes.

The B17b fixed trend and owner-ranking endpoints are `POST /api/v1/reports/trends` and `POST /api/v1/reports/rankings`. A request selects exactly one of `WON_OPPORTUNITY`, `ACTIVE_CONTRACT`, or `ACTIVE_RECEIVABLE` and supplies an inclusive date range. Trends support DAY/WEEK/MONTH with ISO-Monday weeks, zero-filled periods, at most 120 buckets, and at most ten years. Rankings default to 10 rows, allow at most 100 rows and 366 days, and sort by amount, count, then actor ID. Each request resolves only the selected source's read capability, current data scope, and required unmasked fields; it does not require access to the other two sources. Aggregation remains inside the owning opportunity, contract, or receivable repository.

B17c personal custom reports live under `/api/v1/reports/catalog` and `/api/v1/reports/definitions`. The first release permits one OPPORTUNITY, CONTRACT, or RECEIVABLE source, one date field and DAY/WEEK/MONTH granularity, one optional select/boolean/member/department dimension, 1..8 COUNT/SUM measures, and at most 20 typed filters. RELATION fields are omitted from the filter catalog and rejected during persistence and execution so a report cannot bypass the related object's independent record scope. Definitions are private to `(tenant, creator member)` even for owners and administrators. Create, replace, and soft-delete require the new `reports:write`; reads and runs require `reports:read`. Every access re-resolves the selected source capability, current record scope, and unmasked read access for every referenced field. Execution uses server-owned field descriptors and parameterized MySQL aggregation in the owning repository; SELECT option keys use binary-exact comparison, grouping, and ordering. Root rows use each source's exact lifecycle set, built-in time fields retain native DATE/DATETIME parameters, and custom time values use canonical ISO strings so bounded ranges can use tenant/status/time or field-value search indexes. Runs have hard limits of 120 time buckets, ten years, and 500 result rows; overflow fails instead of truncating. Active definitions also block deactivation or disabling searchability of their referenced fields.

The B18a current-member dashboard defaults are `GET/PUT /api/v1/dashboard/preferences`. They are stored per `(tenant, member)` and default to `CURRENT_MONTH` plus `SELF` until first saved. Relative time choices cover today, current week, month, quarter, and year; `CUSTOM` requires a complete range of at most 366 days. The data-scope choice is one of `SELF`, `DEPARTMENT`, `DEPARTMENT_SUBTREE`, or `TENANT` and is only a presentation restriction: it cannot grant or widen any source authority, record scope, or field access. Updates use optimistic versions, and both routes require `reports:read`.

The B18b fixed sales dashboard is `GET /api/v1/dashboard/overview`. It applies the current member's B18a defaults to three fixed KPI/trend cards: won opportunities, active contracts, and active receivables. One UTC date is captured per request; ranges of at most 31 days use daily buckets, 32–120 days use ISO-week buckets, and 121–366 days use monthly buckets, with empty periods filled with zeroes. `reports:read` only permits entry: each card independently resolves its source read capability, effective record scope, and required unmasked fields, then intersects that visibility with the saved presentation maximum. An unavailable source or field produces an opaque `UNAVAILABLE` card without count, amount, or points while other cards remain usable; unexpected infrastructure failures still fail the request. Its closed 16-position data summary includes public-pool release and direct-claim counts only when both `customer-pools:read` and `customers:read` are available: immutable events are filtered to the member's current accessible pool catalog and narrowed by the former owner or claiming actor, never inferred from current membership. Aggregation reuses the B17b source repositories and date indexes in the same read-only `REPEATABLE_READ` snapshot as field-policy reads.

Member monthly `ACTIVE_CONTRACT` targets are managed at `/api/v1/dashboard/performance-targets`; `(tenant, member, metric, year, month)` is unique and every target subject remains active. The dashboard's target projection remains self-only and never derives a department or tenant target by summing member rows. Department targets use the independent `/api/v1/dashboard/department-performance-targets` contract. It stores explicit `YEAR/1`, `QUARTER/1..4`, and `MONTH/1..12` values for an active department under `(tenant, department, metric, year, period, periodNumber)`, with the same separated `dashboard-targets:read/write` authority and optimistic versions. Its `/batch` command atomically creates or version-replaces one through seventeen explicit period values; a duplicate period, stale baseline, or concurrent unique conflict rolls back the whole command. These settings are not business facts and are not presented as dashboard actuals or completion rates until a separately authorized server-side aggregate exists.

Member and department targets each expose a separate atomic import command: `POST /api/v1/dashboard/performance-targets/import` and `POST /api/v1/dashboard/department-performance-targets/import`. The browser must first decode a bounded CSV locally into 1–200 generated typed target rows; the service receives, parses, and persists neither source bytes, filename, nor any attachment. Imports only accept `ACTIVE_CONTRACT`, recheck current write authority, tenant, active member/department, year, period, and amount for every row, and create or replace natural keys in a deterministic lock order. Imports deliberately have no client version baseline: an invalid row or concurrent unique conflict rolls back the complete command. The completion response exposes only the imported-row count; callers refresh facts through the ordinary target queries.

B19a marketing-form management is exposed under `/api/v1/marketing-forms` with separate `marketing-forms:read` and `marketing-forms:write` capabilities. Forms move through `INACTIVE`, `ACTIVE`, and `DELETED`; field configuration references the current B05 LEAD catalog instead of copying stale types or options. Activation requires an active owner whose `leads:write` scope is fully resolved by B09 `LeadAccessResolver`, write access to every configured field, and every currently required lead field exposed as required. An active form also prevents its referenced field from being deactivated. Anonymous rendering and submission use `/api/v1/open/marketing-forms/{publicId}`. The public identifier locates the persisted tenant and form but is not an authentication credential; the submission body is a strict whitelist that rejects tenant, owner, status, unknown top-level properties, and unconfigured fields. Every render and submission rechecks current owner and B05 policy. Submission locks the form root and runs the reused B09 lead-creation operation in the same outer transaction, so a completed update or deactivation cannot be followed by a write from an older form snapshot and no nested `REQUIRES_NEW` transaction consumes a second database connection; B09 failures use the `MARKETING_FORM_SUBMIT` (6907) error scene. Before application handling, anonymous POSTs decode, parse, and regenerate the canonical public ID so the direct route, `/submissions` alias, and equivalent encoding variants share one bucket, then consume bounded per-form and per-source minute quotas, defaulting to 60 and 20; success exposes only an acceptance flag and the configured success message. This limiter is local to one application replica, so global multi-replica quotas remain a gateway or shared-service responsibility.

B19b appends one minimal attribution ledger row in the same transaction as every successful public lead creation. It stores only tenant, form and actual form version, lead, and the submission time generated by MySQL `UTC_TIMESTAMP(6)` and reloaded after insert; a ledger failure rolls the lead back, while failed requests, submitted values, IP addresses, headers, and UTM data are never persisted. `POST /api/v1/marketing-forms/{formId}/submissions/trends` requires `marketing-forms:read` and returns zero-filled DAY/WEEK/MONTH accepted counts, bounded to 120 buckets and ten years. `POST .../submissions/query` additionally requires `leads:read` and applies the caller's current SELF, DEPARTMENT, DEPARTMENT_SUBTREE, TENANT, and collaborator visibility in SQL before count and pagination. Trends retain historical success facts; soft-deleted or currently hidden leads disappear only from the link page. Historical queries remain available for INACTIVE and DELETED forms, and the anonymous success response still exposes no internal IDs.

B20a OA form management is exposed under `/api/v1/oa/forms`. `oa-forms:read/write` govern tenant-scoped, versioned `INACTIVE`, `ACTIVE`, and `DELETED` definitions; the submitter catalog additionally requires `oa-requests:submit`. A form stores at most 100 field codes, order values, and required flags, then resolves current B05 metadata and role field access on every read. Hidden fields are omitted, and an ordinary member sees an active form only when the bound approval initiator scope allows that member and every input field remains writable. `request_title` is always required, while `form_code`, `applicant_actor`, `applicant_department`, and `submitted_time` are server-derived. B24c supports FILE through separate OA drafts and ordered file facts: files never enter scalar `values/facts`, and only CLEAN candidates are frozen in the OA submission transaction. Activation requires an active same-tenant B11 definition for `OA_REQUEST`, whose conditions may use only configured input fields and server facts. Active forms block referenced-field deactivation/searchability removal and incompatible approval-definition changes. All related mutations share the `(tenant, OA_REQUEST)` database guard; MySQL also arbitrates normalized code uniqueness and the 200-live-form tenant cap under concurrency. V52 backfills the five built-ins for existing tenants, while tenant bootstrap provisions them idempotently for new tenants.

B20b OA request runtime is exposed under `/api/v1/oa/requests`. `oa-requests:submit` previews and atomically submits an immutable request, while `oa-requests:read` admits callers to participating-request pages and details; `oa-requests:manage` widens only tenant request reads and does not replace B11 review, withdrawal, or cancellation authority. Submission locks current tenant/form/approval configuration, re-resolves B05 `WRITE` access and server-owned applicant, department, and time facts, persists the authoritative request, then creates the `oa:<requestId>` B11 instance on the same database connection. Any failure rolls back the request, unique reservations, and approval together. `(tenant, applicant, key)` supports concurrent equivalent retries, while changing the form, version, or normalized values yields a stable conflict. SQL applies the union of applicant, historical assignees, snapshotted managers/watchers, and OA managers before counting and paging. Request output and B11 OA snapshots reapply current hidden/masked field policy, and the approval remains the sole runtime-status source. V54 adds tenant-composite request integrity; B15 keeps its existing `APPROVAL_PENDING` source, with no B21 Work table, API, or capability dependency.

B20c internal announcements are exposed under `/api/v1/oa/announcements`. `oa-announcements:write` manages versioned `DRAFT`, `PUBLISHED`, `WITHDRAWN`, and `DELETED` records, while `oa-announcements:read` only reads publications actually delivered to the current active member and writes that member's own receipt. Strict selectors support the whole tenant, department subtrees, and explicit members. Publication locks the organization tenant before the announcement root, resolves and de-duplicates active same-tenant memberships, and persists an immutable snapshot of at most 10,000 recipients; overflow aborts instead of truncating. Later joins and department moves cannot widen history, while inactive members and withdrawn/deleted publications disappear from inbox and unread queries. Titles of at most 200 and bodies of at most 20,000 Unicode code points remain plain text with no HTML/Markdown rendering, attachments, or external notification. Read writes use shared membership and announcement locks to order suspension and withdrawal, then atomically preserve the first server-UTC receipt without serializing all recipients of the same announcement. V55 connects roots, selectors, snapshots, and receipts with tenant-composite foreign keys; V57 removes the redundant deletion timestamp and keeps `status=DELETED` as the sole soft-delete representation.

B21 work tasks are exposed under `/api/v1/work/tasks` with non-data-scoped `work-tasks:read`, `work-tasks:write`, and `work-tasks:manage` capabilities. Each versioned task has exactly one current assignee, at most 50 followers, one optional CRM record, an optional UTC due time, fixed priority, and a `TODO`/`IN_PROGRESS`/`DONE`/`CANCELLED`/`DELETED` lifecycle. The creator or a member with both write and manage can edit, reassign, replace followers, cancel, and perform restricted soft deletion; the current assignee with write can progress it. Followers gain task read and plain-text comment eligibility only, never execution or structure-management rights. Plain read sees tasks where the active caller is creator, assignee, or follower, while read plus manage enables tenant-wide reads. SQL applies active membership, participation, tenant, relationship, lifecycle, and fixed filters before count and pagination.

Comments are independently versioned and paged, Unicode-whitespace stripped, limited to 5,000 Unicode code points, and soft-deletable only by the current active author; even deleted comment history prevents draft-task deletion. CRM links are limited to CUSTOMER, CONTACT, LEAD, OPPORTUNITY, CONTRACT, INVOICE, RECEIVABLE, and RECEIVABLE_PLAN. Creating or setting a non-null link reapplies the owning write scope, data scope, and tenant check to the explicit new target. Clearing or replacing a link does not probe an unreadable previous target, so a hidden link and no link do not produce different authorization outcomes. Relationship-filter authorization, count, and page slicing share one read snapshot. Output reapplies the owning read scope and omits the ID after access loss, and neither side grants access to the other. V53 stores the task root and worklist query index; V56 adds followers, comments, paired relationship checks, composite foreign keys, and indexes. The `WORK_TASK` worklist source requires both `worklist:read` and `work-tasks:read` and projects only the active current assignee's open tasks due that day. Its acknowledgement fingerprint uses the dedicated projection version and due time. Followers, comments, links, and description-only changes do not advance that version; title, priority, assignee, due-time, or status changes create a new reminder fingerprint. Collaboration changes do not create Activities, and acknowledgement does not mutate task state.

B22a connector security and control-plane routes live under `/api/v1/connectors`, with `connectors:read` and `connectors:manage` separating human reads from mutations. Lists, details, revocations, and status changes return a credential-free `ConnectorResponse`; lists use the named `ConnectorPageResponse`; only creation and rotation return `{ connector, credential }` through `ConnectorCredentialCreatedResponse`. The server generates the connector, key ID, and 256-bit secret; the full `connectorRef.keyId.secret` credential is returned only once on creation or rotation, while MySQL stores only its SHA-256 verifier. A connector can have at most two active keys. Optimistic updates govern `ACTIVE`, recoverable `DISABLED`, and irreversible `RETIRED`; revocation, disable, and retirement invalidate local verified authentication state after commit, and retirement revokes every key. V58 combines a globally unique opaque reference with tenant-composite foreign keys and retained credential rows so the tenant/reference binding cannot move.

The non-human `/api/v1/connector-ingress/probe` accepts connector bearer authentication only. Transport authentication performs an exact `(connectorRef, keyId)` verifier lookup and creates an authority-free `ConnectorPrincipal`; the authenticator also issues per-authentication in-process evidence that ordinary beans cannot construct, and the application `ConnectorGuard` verifies it before using a separate verifier-free exact projection to resolve the current active tenant and connector. Human callers, trusted headers, request bodies, and connector principals cannot substitute for one another or supply tenant, actor, or authority. Source, pending-credential, and verified-connector admission maps are independently bounded; rotation keys for one connector share a minute quota, unknown credentials never create connector partitions, and credential or identity storage failures are retryable unavailability rather than secret failures. The registration lock for future ingress writes now requires an active transaction. B22a delivers identity, control-plane lifecycle, and that lock contract; call facts, inbox/outbox, interactions, media, and real provider adapters remain later B22 work.

Enterprise-data OpenAPI uses named safe responses: `EnterpriseDataCapabilityResponse` for readiness, `EnterpriseDataObservationResponse` for search items and exact lookup, `EnterpriseDataAdoptionPreviewResponse` for a caller-bound Customer preview, and `EnterpriseDataAdoptionResponse` for adoption confirmation. These contracts expose only governed enterprise facts and controlled attribution; they never include raw provider payloads, bindings, account data, credentials, or arbitrary extension maps.

Enable Redis with `atom.redis.enabled`; the default is a no-op cache implementation. Flyway migrations live in `infra/persistence/src/main/resources/db/migration`; add a new migration for database changes instead of editing an applied migration.

See [Configuration](docs/configuration.md) for identity, Redis, database, and secret settings.

## Controlled CRM CSV import

Lead, Contact, and Product CSV import uses a private draft protocol rather than a multipart create route. `POST /api/v1/crm-import-drafts` creates a `LEAD|CONTACT|PRODUCT` draft and `GET /templates/{objectType}` returns the fixed columns; Product uses `name,code,categoryId,unit,listPrice,description,availability`. The only source path is the existing `import-draft` attachment target with an upload intent, raw-content upload and inspection status. Draft creation, preview, confirmation and withdrawal require the relevant object-write authority plus `files:write`. Sources are strict UTF-8 CSV, capped at 1 MiB and 200 rows, and each active draft admits exactly one source attachment. `GET /{draftId}/preview` exposes only the valid-row count and row-number/stable-code issues; it never exposes cell data. `POST /{draftId}/confirm` uses the draft version and one transaction to recheck current write scope, field policy and relation visibility. Lead and Contact rows are all-or-nothing; Product deduplicates normalized codes, skipping existing records and repeated source codes without overwriting fields, while remaining creations stay in the transaction. Both confirmation and withdrawal revoke the source attachment, and a lost confirmation response may replay only its minimal completion projection. Raw CSV bytes, names and cells never enter business DTOs, database columns, responses or logs.
